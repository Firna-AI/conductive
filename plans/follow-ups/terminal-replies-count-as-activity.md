# Automatic terminal replies count as activity

- **Severity:** Medium. **Likelihood:** Rare. **Effort:** Small. **Confidence:** High. **Harder later:** No.
- **Kind:** Fix after merge.
- **Added:** 2026-11-08, from PR #54, branch `conductor/boat-native-remote-workspaces-milestone-15i`, round 2, finding 20, with option C of its check.
- **Location:** `terminalFrames` at `worker/terminal/protocol.ts:29-33`, the `recordActivity` call at `worker/terminal/handler.ts:125-127`, and `write` at `src/app/terminal-transport.ts:49-53`.
- **Reason:** Repeated replies need a program that queries through tmux passthrough in a loop. The fix changes no stored data and no public API.

- **Terms:**
  - **Automatic reply:** data that xterm.js, the browser terminal, sends to answer a query of a program, such as a cursor report, without input of the user.
  - **Input listener of the page:** `windowInput` in `src/app/services.ts:94-113`. It hears each `keydown`, `beforeinput`, `pointerdown`, and `wheel` event of the app page in the capture phase.
  - **Input owner:** `InputActivityOwner` in `worker/lifecycle/input-activity-owner.ts`, the one owner of the input times of a workspace object.
- **Background:**
  - Terminal input counts as activity, and an open connection does not, as "Stop and resume" in `docs/protocol/workspaces-and-sandboxes.md` says (decision 29).
  - xterm.js answers some queries of programs by itself, through `onData`, the same event as the keys of the user. `src/terminal/xtermScreen.ts:6-24` lists those queries.
  - Commit `41db629` told the input of the user apart from the replies in the browser. `onActivity` of `TerminalTool` runs only for the input of the user, as `src/terminal/README.md:59-61` says. The workspace screen passes no `onActivity`, at `src/shell/workspace/tools/ToolsPart.tsx:111-115`.
  - The transport sends both kinds as ordinary `0...` input frames, at `src/app/terminal-transport.ts:49-53`.
  - The server counts each `0` frame of more than one byte as activity, at `worker/terminal/protocol.ts:29-33`. It reports the frame to the input owner through `recordActivity`, at `worker/terminal/handler.ts:125-127`.
  - The input listener of the page already hears each key, paste shortcut, and tap in the terminal. The xterm.js text area and the key row are part of the page.
  - While the workspace shows, `WorkspaceModel` posts that input with `source: 'input'` to the `activity` route at most once a minute, at `src/app/workspace-model.ts:105` and `:225-242`.
- **Problem:**
  - The server cannot tell an automatic reply from a key. Shift+F3 and a cursor report have the same bytes, as `src/terminal/xtermScreen.test.ts:11` shows.
  - A probe in memory used the real screen, session, transport, and frame handler. Three queries in the output gave zero input events of the user and three activity updates on the server.
  - ttyd runs each shell inside tmux, at `worker/terminal/scripts.ts:75`, and tmux answers the queries of programs itself. A probe with tmux 3.6a saw only the queries that tmux sends when it attaches, once for each connection.
  - So by default, the replies count once for each connection. The terminal connects at its first show, at Reconnect, and by itself when the sandbox becomes ready in an open tab, at `src/shell/workspace/WorkspaceScreen.tsx:180-196`.
  - Repeated replies need a program that queries through tmux passthrough in a loop. tmux 3.3 and later turn passthrough off by default. The sandbox installs tmux from apt, at `worker/terminal/service.ts:21`, so the tmux version depends on the image.
  - No test carries an automatic reply through the activity check of the server.
- **Impact if no action:** Each terminal connection moves the idle stop to 30 minutes after it, also with no input of the user. A program that queries through passthrough in a loop keeps an idle sandbox running.
- **Root question:** How should terminal activity count user input while automatic replies still reach the shell?
- **Options:**
  - **A.** Connect the existing `onActivity` of the terminal to the `activity` route of the workspace. Remove the activity check from ordinary terminal frames, and keep the input owner as the only sink. Add a regression that carries an automatic reply through the server. Effort: Small.
  - **B.** Keep the source of each input in typed socket messages. The server turns both sources into terminal input, and it counts only the messages of the user. This changes more transport code. Effort: Medium.
  - **C.** Count terminal input only through the input listener of the page. Effort: Small.
    - Remove the activity check from `terminalFrames` at `worker/terminal/protocol.ts:29-33`, and the `recordActivity` call at `worker/terminal/handler.ts:125-127`.
    - Add no browser report. The page listener already posts `source: 'input'` to the same `activity` route, which gives the time to the input owner.
    - Change the assertion at `worker/terminal/handler.test.ts:185-186`: a cursor report frame moves no activity. This test fails on the current code.
    - Update `worker/terminal/README.md:100-102`, the terminal sentence of "Input activity" in `worker/lifecycle/README.md:115-119`, and the `onActivity` lines at `src/terminal/README.md:59-61`.
    - The protocol stays the same, because terminal input still counts as input in the tab.
    - Benefit: a reply is never an input event of the page. So no new reply of xterm.js and no new query of tmux can count.
    - Cost: terminal input with no input event on the page stops counting. Examples are a paste from the Edit menu of the Mac app, and dropped text. Thirty minutes of real work also bring keys or clicks.
    - Cost: a later terminal client outside the web page must report its own activity. Today the web app is the only client of `terminalPaths.socket`.
    - `TerminalTool` keeps `onActivity` for its development page.
- **Left out:**
  - A filter of reply bytes fails the goal, because a key can send the same bytes as a reply.
  - Suppressing the replies fails the goal. Programs need them, and tmux uses the replies to its attach queries to learn colours and features.
  - Keeping the current path breaks decision 29, which counts only user activity. That rule stays.
  - A match of replies to queries in the Worker. It needs a terminal parser in the Worker, and it can still mislabel a key next to a query. B is better on every point.
  - A key time from tmux. It needs a sandbox call at each idle check and an alarm change. C is better on every point.
  - A tmux setup that sends no queries to the browser. It must follow the queries of each tmux version, and passthrough still reaches xterm.js, so it fails the goal.
- **Wider fix:** C. It counts only input events of the page, so no reply of xterm.js and no query of tmux can count. A and B are direct fixes, because they must know which queries xterm.js answers.
- **Previous examples:** Commit `41db629` told user input apart from automatic replies in the browser. `src/terminal/xtermScreen.test.ts:11` checks that the same bytes can have different sources.
- **Related:** [preview-polling-activity.md](preview-polling-activity.md): the same activity rule, for previews, where a request that a page sends by itself counts. The two fixes do not conflict. Both change "Input activity" in `worker/lifecycle/README.md`.
- **Recommendation:** C, not A, which the review first recommended. C removes the same false count as A with less code. A adds a second report for input that the page listener already counts, and it depends on the list of xterm.js replies. A is the next best option if the terminal must report its own input.
- **Action:** fix after merge, apply C, because the product bug is Medium and Rare. Repeated replies need a program that queries through tmux passthrough in a loop.
