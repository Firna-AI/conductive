# A failed repository fetch guesses GitHub access

- **Severity:** Medium. **Likelihood:** Rare. **Effort:** Medium. **Confidence:** High. **Harder later:** No.
- **Kind:** Outside the scope.
- **Added:** 2026-11-20, from the branch `calummoore/follow-up-continue-failures-name-the-6m1b`. A copy check of its Continue stop causes found this problem in the repository change.
- **Location:** `repositoryChangeFailed` in `worker/lifecycle/repository-change-errors.ts:32-35`. Its callers in the `fetch` phase are `worker/lifecycle/repository-change-command.ts:46`, `:61-62`, and `:139-147`, and `worker/lifecycle/repository-change.ts:212-215`. The shared fetch command `continueFetchCommand` in `worker/lifecycle/continue-commands.ts:17-30`, which `repositoryChangeFetchCommand` in `worker/lifecycle/repository-change-commands.ts:24-33` calls. The exact text in `worker/lifecycle/repository-change.test.ts:197-220`. The same words in `fetchWords` of `src/test-support/fake-repository-change.ts:61-63`, and in the masking test of `worker/app-api/repository-change.test.ts:166-192`. The toast words in `src/ui/components/workspace/repositoryMoveCopy.ts:35-39`, and the drawn failure in `docs/mockups/src/entries/app/repository-change/index.mockup.tsx:43-49`. The lock clash of the move at `worker/lifecycle/repository-change-commands.ts:82`.
- **Reason:** The problem is on `origin/main`, outside the Continue change that found it, and each option changes toast words that need the user's choice.

- **Source:** Implementation.
- **Category:** Product bug.
- **Terms:**
  - **Repository change:** The action that moves a workspace to a new branch in the folder of another repository of its org, in the same cloud computer.
  - **Toast reason:** The text of the Worker error `workspace_repository_change_failed`, which the toast "The repository didn't change." shows.
  - **Safe app error:** An `HttpError` from `worker/http.ts`, whose code the poll keeps and whose `workspace_repository_change_failed` text has secret values hidden.
  - **Command journal:** The saved result of a detached command in the cloud computer, which `worker/lifecycle/command-journal.sh` writes and a later step reads again.
- **Background:**
  - The repository change runs as a durable job in the phases `verify`, `resume`, `runner`, `check`, `fetch`, `move`, and `publish`. Its job copies the shape of Continue. `worker/lifecycle/repository-change.md` describes it.
  - `docs/protocol/repository-change.md:221-222` says that after a failure, a toast says "The repository didn't change." and names the reason.
  - `docs/protocol/repository-change.md:176-178` says that the change fetches the latest default branch of the new repository with the GitHub access of the member who changes the repository.
  - `repositoryChangeFailed` in `worker/lifecycle/repository-change-errors.ts:20-39` gives the reason. In the `fetch` phase, lines 32-35 always give "The latest {base} of {repository} could not be fetched. Check your GitHub access, then try again." That branch does not read the exit status.
  - The `fetch` phase reaches that text in four ways:
    - A cancel before the fetch command starts, at `worker/lifecycle/repository-change-command.ts:46`.
    - A cancel after the fetch command started, at `worker/lifecycle/repository-change-command.ts:61-62`.
    - A fetch command that fails, at `worker/lifecycle/repository-change-command.ts:139-147`. It ends with a status other than 0, or with a timeout. A reattach that finds no result in the command journal also ends here, with status 125.
    - An error that is not a safe app error, before the fetch command starts. `retries` at `worker/lifecycle/repository-change.ts:212-215` gives it the fetch text. Examples are a failure of the provider client, at `worker/lifecycle/repository-change-command.ts:47-51`, and of the auto-stop write, at `:89-92`.
  - The provider client throws `ProviderAccountError`, and a provider call throws `ProviderError`. Both extend `Error`, not `HttpError`, so a provider failure before the fetch gets the fetch text.
  - A safe app error keeps its priority. `retries` returns it as it is. An access error that the job kept while a command ran also wins over the fetch text.
  - The `verify` phase reads the default branch of the new repository with the token of the GitHub App installation, at `worker/lifecycle/repository-change-progress.ts:47-51`. Its checks of the member read only stored rows.
  - The fetch uses the GitHub token of the member. So a member whose GitHub account cannot read the new repository can pass `verify`, and then the fetch fails. For that member, the access sentence names the real reason.
  - The fetch command is shared. `repositoryChangeFetchCommand` only calls `continueFetchCommand`, so a change of that command also changes the fetch of Continue.
  - Git ends with status 128 for most fatal errors, such as an access refusal or a network failure. So the status alone does not prove an access problem.
  - The test "keeps the old repository when the fetch fails, and closes the fetch credential" in `worker/lifecycle/repository-change.test.ts:197-220` ends the fetch with status 128. It expects the text with the access sentence.
  - A member or org suspension, or a stop of the cloud computer, cancels the job, as `worker/lifecycle/repository-change.md` says under "Failures and recovery".
  - `repositoryFailure` gives the toast title and the clash reason. The drawn state `failed` shows the clash. No mockup gives the fetch reason, which the Worker owns.
  - Continue had the same guess. Continue keeps a GitHub access hint in its own `fetch` phase until the user chooses its stop words.
- **Problem:** Every stop in the `fetch` phase tells the member to check GitHub access. A cancel, a provider failure before the fetch, and a reattach that finds no result give no access evidence. The fetch may not have run then. A failed fetch command can also have a network or GitHub cause.
- **Impact if no action:** The member can check GitHub access for a failure that has another cause, and miss the real reason. The toast then does not name the reason, as the protocol requires.
- **Root question:** How does the toast of a failed repository change name only a reason that the job established, when its `fetch` phase fails?
- **Options:**
  - **A.** Keep the access sentence only for a fetch command that ran and failed. A cancel, an error before the fetch starts, and a reattach with status 125 get the existing text "The repository change could not finish. Try again." Cost: a network or GitHub failure of the fetch still gets the access sentence. Effort: Small.
  - **B.** Do A, but drop the access sentence too. A fetch command that ran and failed gets "The latest {base} of {repository} could not be fetched. Try again." Cost: a member without GitHub access to the new repository loses the one hint that names the real reason. Effort: Small.
  - **C.** Do A, and keep the access sentence only for a classified access refusal. `continueFetchCommand` keeps the Git text only in a shell variable. It matches the fixed Git messages of an authentication or permission refusal in the C locale, and ends with a reserved status. Each other failed fetch gets the text of B. Cost: the match list must follow the messages of Git and GitHub, and the change reaches the fetch of Continue. GitHub answers a missing private repository and a refused one with the same message. Effort: Medium.
  - **D.** Do A, and after a failed fetch, read the new repository through the GitHub API with the token of the member. Keep the access sentence only when that read is refused. Cost: the reads of `verify` use the installation token, so D needs a read with the token of the member. Each failed fetch costs one more GitHub read, and the access can change between the two reads. Effort: Medium.
  - **E.** Give the repository change a closed stored stop cause, as Continue has. Add an optional cause field to the stored job, and set the cause at each stop site. Reserve exit statuses for known Git causes, and map each cause to one line of a copy function in the mockups. The repository change gives status 81 to a failed copy of the context folder and 82 to a refused checkout. Continue gives 81 to an index lock and 82 to a failed write of the branch comparison. So a shared cause type needs a map for each job. Cost: each stop site changes, and the words of each cause need the user's approval. Effort: Large.
- **Left out:**
  - Change nothing: it fails the goal, because the toast keeps a guessed reason for a cancel, a provider failure, and a network failure.
  - Raw Git text in the toast: it breaks the copy rules, which keep internal detail out of text that users read.
  - A repeat of the fetch to learn the cause: it fails the goal, because it does not classify the earlier failure.
- **Wider fix:** E. One stored cause, with one copy function, removes the guess by phase at each stop site of the repository change. It also covers two other guesses by phase:
  - The move ends with status 82 for every refused checkout, at `worker/lifecycle/repository-change-commands.ts:82`. So an existing `.git/index.lock` gets the clash reason.
  - A cancel in the `runner` phase gets "The cloud computer isn't ready. Try again.", through `worker/lifecycle/repository-change-progress.ts:44`.
- **Previous examples:** Continue also chose its stop text by phase. Every failed Continue move got the clash line, and most other stops got a GitHub access hint. On 20 November 2026, the branch `calummoore/follow-up-continue-failures-name-the-6m1b` gave Continue a closed stored stop cause, in `worker/lifecycle/continue-stop-causes.ts`.
- **Related:**
  - `plans/follow-ups/continue-stop-cause-copy.md` holds the same guessed access cause in the `fetch` phase of Continue. Both items depend on the shared `continueFetchCommand`. Option C of each item classifies an access refusal there, so one classification serves both. Its answer can guide the words here. Neither item waits for the other.
  - `plans/follow-ups/shared-branch-move-job.md` says that Continue and the repository change copy one job. One shared job would carry one cause type and one copy function, so E fits that work.
- **Recommendation:** C. It keeps the access sentence where Git proves an access refusal, and removes it where the job has no evidence. E best protects the codebase, because one stored cause removes the guess at every stop site, and it fits the shared job.
- **Action:** ask the user, because the options have real trade-offs and no option is clearly best. A keeps a guess for a network failure. B drops a hint that is true for a member without access. C and D cost more. Each option also changes toast words that no drawn state gives.
- **Second defect, the lock clash:** The move of the repository change does not classify a refused checkout. Every refusal ends with status 82, the clash marker, at `worker/lifecycle/repository-change-commands.ts:82`. So an existing `.git/index.lock` in the folder of the new repository currently gets the clash reason of `repositoryFailure.clash`. That reason tells the member to commit or discard changed files, which do not cause a lock. A read of the code shows this, and no test reproduces it. Options A to D leave it as it is, and option E covers it. No other item records it.
