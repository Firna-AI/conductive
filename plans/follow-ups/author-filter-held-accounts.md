# A routine save can move trust to another account

- **Severity:** High. **Likelihood:** Rare. **Effort:** Small. **Confidence:** High. **Harder later:** No.
- **Kind:** Needs decision.
- **Added:** 2026-11-10, from branch `calummoore/routines-feature-brainstorm`, finding 1 of its review.
- **Location:** `worker/routines/prepare-routine.ts:45`, `worker/routines/author-filters.ts:18` and `:36`, `worker/routines/stored-triggers.ts:62`, `worker/routines/author-filters.test.ts:46` and `:90`, and `docs/protocol/pull-request-runs.md`, the bullets on account IDs in "Who may start a run".
- **Reason:** The fix changes a requirement of the protocol doc, and no decision of the user covers that change.

- **Terms:**
  - **Routine:** a saved prompt that starts an agent run in a new workspace, on a schedule, on a GitHub pull request event, or with Run now. A run acts with the logins of the routine's owner and the env vars of the org.
  - **Author filter:** the two lists of GitHub accounts of a pull request trigger, "Author is" and "Author is not". An event starts a run only when the author of its pull request passes the filter. "Author is" can also hold the entry "Members of <org>".
  - **Account ID:** the number that GitHub gives an account. It never changes. A login is the name of the account, and the account can change it.
- **Background:**
  - On 9 November 2026 the user chose option C of the decision "whose pull requests may start a run": only members of the org, and each pull request trigger gets an author filter with "is" and "is not".
  - `docs/protocol/pull-request-runs.md` says: "The app matches each account by its GitHub account ID, not by its login. The form takes logins, and the Worker resolves each login to its account ID at each save." Its reason: "a GitHub login can be renamed and then taken by another account."
  - The web editor sends only the changed fields. A save of the name, the prompt, or Active leaves out the triggers. A save that edits any trigger sends the full trigger list.
  - When a save leaves out the triggers, `prepareRoutine` turns the stored accounts back into logins (`prepare-routine.ts:45`). Then `resolveRoutineAuthors` looks up each login on GitHub again. When a save sends the triggers, each login is looked up again too.
- **Problem:** Each save looks up the approved logins again. When an approved account renames itself and another account takes the old login, the next save of the routine stores the new account's ID, also a save that changes only the name. A probe changed account 1010 to 2020 with a name-only save, and the new account's pull request then queued a run. Two more effects have the same cause:
  - When an approved account renames itself and nobody takes the old login, each later save fails with `unknown_github_login`, also a prompt edit or a turn-on (`author-filters.ts:36`).
  - A save moves an "Author is not" entry to the new holder of a taken login, so the pull requests of the renamed account start runs again (`stored-triggers.ts:62`).
- **Impact if no action:** An account that takes a renamed login can start runs that hold the owner's logins and the org's env vars. It also needs push access to the repository, because pull requests from forks never start a run.
- **Root question:** How do routine saves keep the accounts that the owner approved?
- **Options:**
  - **A.** Keep the stored filters when a save leaves out the triggers. A save that sends the triggers keeps the risk. Effort: Small.
  - **B.** Keep account IDs in the editor and in the save request, and look up only new selections. The Worker must also check each ID that a client sends, or a client can store any ID under any login. Effort: Medium.
  - **C.** Refuse a save when a stored login now names another account, and ask the owner to replace the account. This adds a rejection. Effort: Medium.
  - **D.** In the Worker save, reuse the stored account for each login that the routine already holds, compared without case. Look up only the logins that the routine does not hold. Fill the lookup cache in `author-filters.ts:18` from the previous record. Change the tests at `author-filters.test.ts:46` and `:90` to expect the kept ID. Change the protocol sentence to: "The Worker looks up a login once, at the save that adds it. A held account keeps its ID." Update the Worker README of `worker/routines/` and a fixture comment. Cost: to trust the new holder of a held login, the owner removes the login, saves, and adds it again. Effort: Small.
  - **E.** D, and also look up each kept account by its ID at each save, with GitHub's `GET /user/{account_id}`. When GitHub reports another login, keep the stored entry and show the new login next to the chip. A failed lookup does not block the save. It needs a new GitHub route in the Worker and in `worker/test-support/fake-github.ts`, a field, form text, and a mockup. Effort: Medium.
- **Left out:** Logins as the key of trust, because they keep the takeover. A check of both the login and the ID when an event arrives, because the save still moves the ID. A limit of "Author is" to bots and members, because the user's choice lets the owner name any account. A separate route to add and remove accounts, because D gives the same protection in one save.
- **Wider fix:** D. Every save goes through the Worker, so no client can move an approved account.
- **Previous examples:** Invitations use a verified email and not a GitHub login, for the same reason (decision 78 of the project).
- **Recommendation:** D. It keeps each approved account on every save path and for every client, with a change in the Worker only.
- **Action:** ask the user, because D changes the protocol requirement that the Worker resolves each login at each save, and no decision of the user covers that change.
