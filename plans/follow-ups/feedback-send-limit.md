# Feedback has no send limit

- **Severity:** High. **Effort:** Medium. **Confidence:** High. **Harder later:** No.
- **Kind:** Fix after merge.
- **Added:** 2026-11-10, from decision 276 of the plan `plans/command-palette-feedback.md`, branch `calummoore/command-palette-feedback-option`.
- **Location:** `POST /api/feedback` in `worker/app-api/feedback.ts`, the email in `worker/app-api/feedback-mail.ts`, the send of `FeedbackModel` in `src/app/feedback-model.ts`, the dialog in `src/shell/feedback/FeedbackDialog.tsx`, a new table under `migrations/`, and the section "The routes" of `docs/protocol/feedback.md`.
- **Reason:** On 10 November 2026, the user chose to ship feedback with no limit, and to add this limit in a later change.

- **Source:** Design. **Category:** Security.
- **Terms:**
  - **Resend:** the email service that sends every email of the app, through `worker/mail-sender.ts`, from `mail.conductive.build`.
  - **Send quota:** the number of emails that the Resend plan of the deployment allows in a day or a month. The Free plan allows 100 emails a day.
  - **Feedback send:** one `POST /api/feedback` that emails one feedback message to the team inbox, the mailbox in the Worker secret `FEEDBACK_EMAIL`.
- **Background:**
  - The Send feedback row of the command palette opens the Feedback dialog. Each send of the dialog makes one feedback send.
  - The route has no limit on how often a person sends. An operator can suspend a person who misuses it, as the section "Suspend a user" of `docs/protocol/operator-actions.md` says.
  - The feedback emails, the org invitations, and the approval emails of the waitlist share one Resend account, with one send quota and one rate limit.
  - Without pay-as-you-go, Resend refuses each send after the quota runs out. With it, each extra email costs money.
  - An approval email tries again for up to 24 hours, then stops.
  - `docs/deployment.md` does not say which Resend plan the deployment uses.
  - A repeat of a send of the same draft sends one email within 24 hours, because Resend keeps each delivery key for 24 hours. A send of a changed draft sends a new email.
  - The Worker has no rate limit for user requests today. Org invitations have no send limit either.
  - On 10 November 2026, the user chose no limit for the first change. For a later change, the user chose a limit for each person of 10 feedback sends in an hour. It counts only feedback emails. Org invitations and approval emails do not count, and stay outside it.
  - The record of that choice says that a send above the limit gets HTTP 429, and the dialog says when to try again. It needs a table of send times, a dialog state, and its mockup.
- **Problem:** One person can send feedback with no limit.
- **Impact if no action:** A person who sends feedback in a loop can use up the send quota, or run up a bill. The invitation and approval emails then fail, and an approval email can stop for good.
- **Root question:** How do the invitation and approval emails keep working, at a bounded cost, while one person sends feedback in a loop?
- **Options:**
  - **A.** No limit. An operator suspends a person who misuses it. A loop can use a day of the Free plan in seconds, before an operator can act. Effort: Small.
  - **B.** A limit for each person: 10 feedback sends in an hour, which counts only feedback emails. The Worker answers a send above it with HTTP 429, and the dialog says when to try again. It needs a table of send times, a dialog state, and its mockup. Effort: Medium.
  - **C.** A limit for the whole app, such as 50 feedback emails in a day, which keeps the rest of the quota for the other emails. One person can still use all of it. Effort: Medium.
  - **D.** Send feedback through the email service of Cloudflare, to the team inbox as a verified address. Cloudflare sends such email free and outside the Resend quota, with attachments and a reply address. It needs Email Routing on the sending domain. Effort: Medium.
  - **E.** Feedback uses a second Resend team, with its own key, its own sending subdomain, and its own quota. A second team needs a paid plan, such as Pro. Effort: Small.
  - **F.** B and C together, from one table of send times: a limit for each person, and a daily limit for the whole app below the quota of the plan. A send above a limit gets HTTP 429, and the dialog says when to try again. Effort: Medium.
  - **G.** The shared mail sender applies the limits of F to each email that a person's request starts: feedback and org invitations. The approval email stays outside the limits, because an operator starts it. It adds a refusal to the org invitations, so their protocol doc and their screen change too. Effort: Medium.
- **Left out:** A limit in the dialog alone, because a crafted request skips it. The rate limit binding of Cloudflare Workers as the counter, because it counts only over 10 or 60 seconds, apart in each location.
- **Wider fix:** G. D takes only feedback off the shared quota, while org invitations can still use it up. The user chose B, so this item applies B.
- **Previous examples:** The draft files of the chat have no limit for one person either, as `plans/follow-ups/draft-attachment-quota.md` says.
- **Related:** `plans/follow-ups/invitation-email-send-limit.md` records the same quota risk for org invitations. It stays a separate decision, because this limit counts only feedback emails.
- **Recommendation:** B. The user chose it on 10 November 2026, with 10 feedback sends in an hour for each person. G best protects the other emails.
- **Action:** fix after merge, apply B, because the user chose on 10 November 2026 to ship feedback with no limit and to add this limit in a later change.
