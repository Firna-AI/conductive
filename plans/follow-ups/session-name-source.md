# Automatic naming can replace a member's default-looking name

- **Severity:** Low. **Likelihood:** Rare. **Effort:** Small. **Confidence:** High. **Harder later:** No.
- **Kind:** Fix after merge.
- **Added:** 2026-11-08, from review round 1, finding 2, on the branch `calummoore/chat-title-rename`, which names sessions after their first message.
- **Location:** `worker/chat/messages.ts:76`, `worker/chat/session-titles.ts:12`, `src/chat/dev/dev-sessions.ts:78` and `:145`.
- **Reason:** The bug needs a member to type a name that equals an automatic name, and a fix after the merge is no harder, because sessions without the new record can keep today's rule.

- **Source:** Review. **Category:** Product bug.
- **Terms:**
  - **Session:** one agent conversation in a workspace, shown as a tab.
  - **First session:** the session that the first message of a new workspace starts. It starts with the city name of the workspace, such as `delft`.
  - **Later session:** each other session. It starts with the title "New session".
- **Background:** The user chose on 8 November 2026, with decision 143 C of the workspace title plan, that the first session takes the workspace name and then the agent's title, and that each later session takes the first line of its first message with text. `docs/protocol/chat-and-events.md`, under "Sessions", says that the app never replaces a title that a member gave a session. The Worker decides whether a session may still take an automatic name from its current title text. The development page repeats the same text checks, and `src/chat/dev/README.md` says that the page keeps a name that the reader gave.
- **Problem:** A member's name that equals "New session", or that equals the city name of the first session, still counts as an automatic name. So the next text message, or the first workspace title, replaces it.
- **Impact if no action:** A member who types a default-looking name can see it replaced. The member can rename the session again.
- **Root question:** How can automatic naming replace only a name that no member gave, when a member can type the same text as an automatic name?
- **Options:**
  - **A.** Store eligibility flags. Clear them after a member rename or a successful automatic name. Check them in both automatic paths. Effort: Small.
  - **B.** Keep one private naming record for each session, with the source of its name: the first name, a message, the workspace title, or a member. One helper reads it. Effort: Small.
  - **D.** B, with the rule as one pure function in `src/shared/session-title.ts`, beside `sessionTitleFrom`, which the Worker and the development page both call. The Worker keeps the source under a private key, outside the public session record. A message changes the source only when its title differs from "New session", so the protocol needs no change. A session with no record, such as one from before the fix, keeps today's text rule. Add two regression tests: a member's "New session" stays after a text message, and a member's city name stays after the first title. Update `worker/chat/README.md` and `src/chat/dev/README.md`. Effort: Small.
  - **C.** Store member names apart from automatic names, and make the readers prefer the member name. More storage and reader code change. Effort: Medium.
  - **E.** Keep the code, and state the exception in "Sessions": automatic naming can replace a member's name that equals "New session" or the city name. This changes a requirement, so it needs the user. Effort: Small.
- **Left out:**
  - Refusing these names as member names. It adds a rejection, which needs the user, and D keeps every name valid.
  - Removing automatic naming. It drops decision 143.
  - A blank first title that no member can type. It breaks the rule that each later session starts with "New session".
  - Ending automatic naming after a message whose title is "New session". It breaks the rule that the next text message names a session that still has "New session".
- **Wider fix:** D. One rule beside `sessionTitleFrom` serves every title writer.
- **Previous examples:** None found.
- **Related:** Decision 144 of the workspace title plan, about a workspace name that a client sets, has the same cause. Its option F, a mark that a member set the name, matches D.
- **Recommendation:** D. It keeps each member name, it covers the development page too, and it needs no protocol change.
- **Action:** fix after merge, apply D, because the bug is Rare and Low, and the fix is no harder after the merge.
