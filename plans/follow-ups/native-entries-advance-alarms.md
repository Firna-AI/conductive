# Native test entries skip stored alarm delivery

- **Severity:** Medium. **Effort:** Medium. **Confidence:** High. **Harder later:** Yes.
- **Kind:** Fix after merge.
- **Added:** 2026-11-08, from PR #53, branch `conductor/boat-native-remote-workspaces-milestone-8m`, round 1, option C of the check of finding 18. The working agent applied option B of that finding and split C off as its wider fix.
- **Location:** `advanceStartAlarm` in `worker/chat/integration/workspace-review-entry.test-support.ts:54-56`, `worker/chat/integration/journey-entry.test-support.ts:4-6`, `worker/chat/integration/preparation-entry.test-support.ts:6-8`, and `worker/features/entry.test-support.ts:32-34`. The start drives in `worker/chat/integration/workspace-start.test-support.ts` and `worker/chat/integration/workspace-review.test-support.ts:91-103`. The alarm route at `worker/devices/clock.test-support.ts:50-51`.
- **Reason:** C changes native test entries and start drives outside the diff of PR #53, and Milestone 5e holds C beside its one alarm scheduler.

- **Terms:**
  - **Native test entry:** a test subclass of a production Durable Object that Miniflare runs with native storage, such as the `Workspace` entries under `worker/chat/integration/` and `worker/features/`.
  - **Alarm:** the one stored wake-up time of a Durable Object. The runtime deletes it before it calls the `alarm` handler, so a run that sets no new alarm leaves none.
  - **Due-alarm advance:** `advanceScheduledAlarms` in `worker/lifecycle/scheduled-alarms.test-support.ts`. It sets the test clock, runs only the stored alarms that are due, in time order, and deletes each alarm before its handler.
- **Background:**
  - The native tests use a test clock far in the future, so that workerd never fires their alarms on real time. So a test runs the handler itself.
  - Milestone 8m found recovery tests that ran the handler without a stored alarm. Its fix gave the recovery entry a due-alarm advance, at `worker/chat/integration/workspace-recovery-entry.test-support.ts:28-39`, in commit `ead46da`.
  - The checkpoint entry of the feature tests also runs only due stored alarms, at `worker/features/checkpoint-entry.test-support.ts:37-54`.
  - Other entries still call the handler at once through `advanceStartAlarm`: the review, journey, and preparation entries, and the feature entry of Milestone 15i.
  - The start drives `prepareWorkspaceStart`, `driveWorkspaceStart`, `completeWorkspaceResume`, and `driveToRunningStartup` call that method in a loop.
  - The test worker of the device broker runs its handler at once on a POST to `/__test/device-alarm`, at `worker/devices/clock.test-support.ts:50-51`.
- **Problem:** A native test that calls the handler itself runs work that no stored alarm asked for. So the test passes when the code leaves no next alarm, or when it sets that alarm too late.
- **Impact if no action:** A defect that loses the next alarm of a start, an idle stop, a disk keepalive, or a device can pass every native test.
- **Root question:** How does each native test prove that a stored alarm, not a direct call of the handler, continues the work?
- **Options:**
  - **C.** Give every native entry one due-alarm advance method that uses `advanceScheduledAlarms`. Effort: Medium.
    - Remove the direct handler calls from the review, journey, preparation, and feature entries. Give the alarm route of the device broker test worker the same rule.
    - The start drives advance to the next stored alarm. They fail when work remains but no alarm is stored.
    - An entry without a test clock gets one, set in the future, because it uses real time now. The journey, preparation, and feature entries have none.
    - A drive that waits for a runner report must wait for that report. It must not jump to the stored deadline. Every assertion stays.
    - Use the helper that option E of `plans/follow-ups/lifecycle-tests-on-real-object.md` also asks for, so that both fixtures keep one alarm rule.
  - **D.** Let workerd deliver each due alarm. Effort: Medium.
    - An entry method checks that the stored alarm is due on the test clock. Then it moves that alarm to the real present.
    - The test polls until workerd has run the handler as a real alarm event. So the test uses the alarm handling of the runtime itself.
    - Cost: the poll needs a deadline of at least 10 seconds, and the runtime can retry a failed run.
- **Left out:**
  - A check and a delete of the stored alarm in each test, as option A of the finding did for the recovery tests. Each new test can forget it, so C is better on every point.
  - Waiting on the wall clock for the original alarm times. It is slow and not deterministic, against the testing rules.
  - A new scheduler fixture. It repeats `advanceScheduledAlarms`, so C is better on every point.
  - A workerd test pool. It adds a dependency and moves the whole test harness. D gives native delivery without either.
  - An advance that deletes the alarm but ignores its time. It runs alarms early, which production never does, so it fails the goal.
  - A lint against direct handler calls. C removes the same class with no guard, and a new lint needs the approval of the user.
  - A change of production code. The one alarm scheduler of `plans/follow-ups/shared-object-alarm.md` prevents a missing next alarm, but it needs these tests to prove that.
- **Wider fix:** C. No later native test can skip the delivery of the stored alarm.
- **Previous examples:** Commit `2b0928f` gave the lifecycle fixtures `advanceScheduledAlarms`. Commit `ead46da` gave it to the recovery entry, for finding 18 of PR #53. Commit `b1d0385` of Milestone 15i then added the feature entry with a direct handler call again.
