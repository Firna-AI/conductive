# Two quick section moves can save the wrong order

- **Severity:** Medium. **Likelihood:** Rare. **Effort:** Medium. **Confidence:** High. **Harder later:** No.
- **Kind:** Fix after merge.
- **Added:** 2026-11-13, from branch `calummoore/oslo-tq4m`, review finding 1.
- **Location:** `moveSection` in `src/app/section-actions.ts`, and `Resource.write` in `src/app/resource.ts`.
- **Reason:** The defect needs unusual request timing, and its fix needs no stored format or API change, so it gets no harder after the merge.

- **Related:** `plans/follow-ups/list-writes-save-order.md` holds the wider fix: every list write in order. When the user chooses that item's option A, it covers this item too, and this item closes.
- **Terms:**
  - **Section:** a named group of workspaces in the workspace list of an org. General is the default section.
  - **Resource:** the client class in `src/app/resource.ts` that keeps loaded data, applies a write at once, sends it, and takes back only that write when it fails.
- **Background:**
  - A member moves a section by a drag of its name, or by Move section up and Move section down in its menu.
  - `moveSection` applies the move to the page at once through `org.resources.list.write`, then sends `PATCH /api/orgs/:orgId/sections/:sectionId` with `{ position }`. The position is the index in the list, counted without the moved section.
  - The Worker (`updateShellSection` in `worker/app-api/feature-sections-data.ts`) puts the section at that index and numbers the other sections around it.
  - `Resource.write` sends each list write at once. Only `Resource.save` waits for the answer of the save before it (`src/app/data-lifecycle.md`: "List writes do not wait for each other").
- **Problem:** Two moves can reach the server in the reverse order. The page applies them in the order that the member made them. Example, with General, Checkout, and Infra: move General down twice, and the first request arrives after the second. Both requests succeed. The page shows Checkout, Infra, General. The database keeps Checkout, General, Infra. A reviewer reproduced this with the real section write handler on a migrated local D1 database.
- **Impact if no action:** The next read of the list changes the order on the page, and it undoes the member's last move. Other members see the database order meanwhile.
- **Root question:** How does the saved order of the sections end as the order that the member made, when two moves overlap?
- **Options:**
  - **A.** Keep a queue for section moves in the org model. Each move still shows at once, and each request goes out after the answer of the one before. Add a test with a held first request. Effort: Small.
  - **B.** Add an ordered write to `Resource`: a write that shows at once and goes out through the existing save queue of the value, with its own rollback. Route `moveSection` through it. Test overlapping moves and a failed first move. Effort: Medium.
  - **C.** Send a sequence number with each move, and let the Worker hold a later move until the earlier one arrives. This needs a new API field and stored state. Effort: Large.
  - **D.** While a section move waits for its answer, offer no other section move: hide the move items and start no drag. The member waits one round trip between two moves, and the protocol doc needs a rule for the wait. Effort: Medium.
- **Left out:**
  - Change nothing: it fails the goal.
  - Send the whole order, or a neighbour section, in place of an index: the request that arrives last still wins.
  - Take the server order from each answer, or read the list again after overlapping moves: the page then undoes the member's last move.
  - Run the writes of an org one at a time in the Worker: two requests can still reach the Worker in the reverse order.
- **Wider fix:** Make every list write ordered, in `plans/follow-ups/list-writes-save-order.md`. It needs the user, because it changes a rule of `src/app/data-lifecycle.md` on `main`.
- **Previous examples:** Commit `2ce9adcdb` added the save queue of `Resource` after settings saves met the same ordering problem. `src/app/settings-saves.test.ts` covers that case.
- **Recommendation:** B. It reuses the save queue that `Resource` already has, and the wider fix can later make its ordered write the default.
- **Action:** fix after merge, apply B, because the defect needs unusual request timing and the fix needs no stored format or API change.
