# A queued pull request run can start in another repository

- **Severity:** High. **Likelihood:** Rare. **Effort:** Medium. **Confidence:** High. **Harder later:** No.
- **Kind:** Needs decision.
- **Added:** 2026-11-10, from branch `calummoore/routines-feature-brainstorm`, finding 5 of its second review.
- **Location:** `worker/routines/run-starter.ts:91` and `:102-111`, `worker/routines/stored-run.ts:29-52`, `worker/routines/run-record-data.ts:66-76`, `worker/routines/run-admission-data.ts:5`, `worker/routines/pull-request-dispatch.ts:8-73`, `worker/lifecycle/creation-fetch-label.ts:8`, and `docs/protocol/routine-runs.md` (the rule that a run workspace gets the repository of its routine, and the list of reasons why a queued run becomes skipped).
- **Reason:** Each option changes a requirement of `docs/protocol/routine-runs.md`, or adds a new skip or a new refusal, and the user has not chosen one.

- **Terms:**
  - **Routine:** a saved prompt that starts an agent run in a new workspace, on a schedule, on a GitHub pull request event, or with Run now. Each routine names one repository, and each run workspace opens on a new branch of that repository.
  - **Queued run:** a run that waits for its workspace. The webhook route stores the run first, and a background start or the minute scan creates its workspace later. A start can come a minute or more after the event.
  - **Creation attempt:** the stored record of a workspace create. After it exists, the start only repeats the same create.
- **Background:**
  - A pull request run stores its trigger facts: the pull request number and address, its head branch, its head commit, and its base branch. It stores no repository.
  - The owner can change the repository of a saved routine. It is also the repair after an admin removes the repository: the routine turns off, and the note says "Choose another repository, then turn it on".
  - Before the first create, the start checks again that the routine is on, that the owner is still a member and not suspended, and that the org is not suspended or deleted (`run-admission-data.ts`). It does not check the repository, the trigger, or the author filter again.
  - The dispatch picks routines by repository (`pull-request-data.ts:17-24`). The insert of the run then checks only the owner and the triggers (`run-record-data.ts:66-76`).
- **Problem:** The start takes the repository from a fresh read of the routine (`run-starter.ts:91`), and the branch and the commit from the stored event (`run-starter.ts:102-111`). A probe queued an event from repository A, changed the routine to repository B, and started the queued run. It created a workspace in B with the branch, the commit, and the pull request link of A. Two more problems have the same cause:
  - A queued run still starts after the owner removes its trigger, or removes its author from "Author is" (`run-admission-data.ts:5`). The protocol does not say what happens then.
  - The start step of such a run says "Fetching pull request #N of" with the new repository (`creation-fetch-label.ts:8`).
- **Impact if no action:** An opened or pushed run fetches the head branch of A from B. When B has no such branch, the start fails and counts as a failed run toward the turn-off after three failed runs. A merged run fetches the base branch, which B usually has, so it starts in B with the pull request link of A, and the agent works in the wrong repository.
- **Root question:** How does a pull request run start only in a repository that matches its event, when its routine can change before the start?
- **Options:**
  - **A.** Store the event's repository with the run, and skip the run before its first create when the routine's repository changed. Also check the repository in the insert. It adds a skip reason. Effort: Medium.
  - **B.** Store one fixed target with the run: the repository, the branch, and the commit. Use it for every start and retry, and check the repository in the insert. The run then starts in a repository that the routine no longer names, which changes the rule that a run workspace gets the repository of its routine. It can also get a prompt that the owner rewrote for the new repository. Effort: Medium.
  - **C.** Move the match of `dispatchPullRequestRuns` into one function: the repository, the trigger event, the author filter, and the trust rule. Store the event's repository, author, and sender with the run. Call the function at the dispatch and before the first create, only while no creation attempt exists. Skip a run whose event no longer matches, with its reason. Check the repository in the insert. Update the skip list of `docs/protocol/routine-runs.md`, the routines README, and the mockup copy of the new skips. Add regressions for a repository change, a removed trigger, and an author removed from "Author is", each between the event and the start, and one for a change after the creation attempt, where the run must go on. Effort: Medium.
  - **D.** Fix a pull request run at its event: the dispatch stores the event's repository and the run text with the run, and the start reads the routine only for the checks and the agent choice. State in `docs/protocol/routine-runs.md` that a pull request run keeps the repository and the text of its event. A prompt edit no longer reaches a queued run, and the workspace can open in a repository that the routine no longer names. Effort: Medium.
  - **E.** Refuse a repository change while the routine has a queued pull request run without a creation attempt, in the update of the save. It adds a refusal with its copy and mockup, and in the minute after a repository removal a queued run can block the repair save. Effort: Medium.
- **Left out:** An immediate start only, because the protocol requires another start after a minute for a Worker that stopped. A rebuilt event for the new repository, because a pull request of another repository changes the cause of the run. A skip in the save, because a skip during a create in progress leaves a skipped run with a live workspace and no outcome. A repository that cannot change after the first save, because the visual spec draws a repository picker for a saved routine and the repair note needs it.
- **Wider fix:** C. One match function decides at the event and at the start, so any later match condition is checked at both times.
- **Previous examples:** The same branch fixed the same class for the agent choice: a run now records the agent, the model, and the effort of its routine at its first start (`worker/routines/run-choice-data.ts`).
- **Recommendation:** C. It keeps the rule that a run workspace gets the repository of its routine, and it extends the skip that the start already does when the routine is off or has another owner.
- **Action:** ask the user, because each option changes a requirement of `docs/protocol/routine-runs.md` or adds a new skip or refusal.
