# A skill read can outlast workspace access

- **Severity:** High. **Effort:** Medium. **Confidence:** High. **Harder later:** No.
- **Kind:** Needs decision.
- **Added:** 2026-11-25, from branch `calummoore/skill-widget-tab-page-dtzl` (skill tabs), review round 1, finding 21.
- **Location:** `worker/skills/handler.ts:30-55`, `worker/chat/runner-connections.ts:238-272`, `worker/chat/authenticated-runner.ts:35-53`, `worker/members/membership.ts:46-67`, `worker/skills/runner.ts:11`, `worker/chat/runner-read-requests.ts:15-24`, `docs/protocol/skill-tabs.md:78-79`, `docs/protocol/isolation.md:49-54`.
- **Reason:** Every option that closes the window adds a new refusal, and the other option accepts a documented risk, so the user decides.

- **Source:** Review. **Category:** Security.
- **Terms:**
  - **Worker:** the Cloudflare Worker that checks each browser request and serves the data of each workspace.
  - **Runner:** the program `conductive` in each cloud computer. It answers the skill reads that the Worker sends on its connection.
  - **Skill tab:** the workspace tab that shows the `SKILL.md` text of one skill of one agent.
  - **Shared read tracker:** `RunnerReadRequests` in `worker/chat/runner-read-requests.ts`. It holds each pending skill, file, or diff read until its reply, its time limit, a disconnect, or a cancel.
- **Background:**
  - A skill tab reads its text with `GET .../skills/content`. The handler checks the sign-in and the org membership with `gate`, and the workspace with `filesWorkspace` (`worker/skills/handler.ts:30-33`).
  - This is the start check of a file read, as `docs/protocol/skill-tabs.md:78-79` says.
  - The Worker then queues the read on the runner connection (`readSkill` and `sendRead` in `worker/chat/runner-connections.ts:238-272`).
  - The queued send checks only the workspace token of the runner (`AuthenticatedRunner.send` in `worker/chat/authenticated-runner.ts:35-53`). It does not check the caller again.
  - When the reply comes, the handler filters the text and returns it with no second access check (`worker/skills/handler.ts:47-55`).
  - A removal from the org signals only the workspaces that the removed member owns (`removeOrgMember` in `worker/members/membership.ts:46-67`). In each other workspace, the runner stays connected and can finish the read.
  - Since 25 November 2026, the shared read tracker ends each skill read after 30 seconds, and it drops a later reply (`worker/skills/runner.ts:11`, `worker/chat/runner-read-requests.ts:48-51`).
  - So a reply reaches the browser at most 30 seconds after the start check.
  - Decision 70, recorded on 6 November 2026, accepts the same window for an open tab. An open tab loses its workspace connection within 30 seconds after its user loses access (`docs/protocol/isolation.md:49-54`).
  - The file and diff reads have the same start check, as `plans/follow-ups/file-reads-after-access-ends.md` records.
  - Each option changes `docs/protocol/skill-tabs.md`. A change of a protocol doc also needs a read of both legal pages and of each public guide, as `AGENTS.md` says.
- **Problem:** A member who loses access while a skill read waits can still get the text of that read. The access ends at a removal from the org, a sign-out, or a deleted org. The window is at most 30 seconds.
- **Impact if no action:** A former member can receive one private skill text after their workspace access ends.
- **Root question:** How long after access ends may a skill read still return text, and which part of the Worker enforces it?
- **Options:**
  - **A.** Keep the start check and the 30-second limit.
    - State in "The read" of `docs/protocol/skill-tabs.md` that a read can return its text up to 30 seconds after the access ends.
    - Give the reason: decision 70 accepts the same window for an open tab.
    - Cost: a documented risk.
    - Effort: Small.
  - **B.** Give the reads through the runner one shared operation with two access checks.
    - It checks the caller's access before it sends the command, and again before it returns the reply.
    - Build it on the shared read tracker, which already holds the time limit. Use it for the skill route.
    - Add a test where the access ends while the read waits.
    - Cost: a new refusal, and a change of `docs/protocol/skill-tabs.md:78-79`.
    - Effort: Medium.
  - **C.** Check the caller's access again in the outer feature router, `WorkspaceFeatures.fetch` in `worker/features/workspace.ts:112-138`, after each handler returns.
    - Cost: a new refusal on every feature route on `origin/main`, such as the services, the terminal, the desktop, and the previews.
    - Effort: Medium.
  - **D.** Track each pending read under the access grant of its caller. Cancel the read when the grant ends, and check the access again before the reply. Cost: new state for each grant, and a new refusal. Effort: Large.
- **Left out:** A second check written only into the skill route, in the queued send and before the reply. B makes the same two checks for skill reads in one place, which the file and diff reads can also use.
- **Wider fix:** B. The operation that sends each read and returns its reply owns both access checks, so a new kind of read cannot miss them.
- **Previous examples:** Commit `cc6a38f09` added a final access check before the service logs return (`worker/services/handler.ts:102-103`). `plans/follow-ups/desktop-stream-after-access-loss.md` records another path that outlives the loss of access.
- **Related:** `plans/follow-ups/file-reads-after-access-ends.md` has the same class for the file and diff reads. B can serve both. That item waits for the answer here, because the user sets one policy for both.
- **Recommendation:** B. It puts both checks at the points where the Worker acts for the caller. Choose A if the user accepts the documented 30-second window.
- **Action:** ask the user, because B, C, and D add a new refusal, and A adds a new requirement to a protocol doc.
