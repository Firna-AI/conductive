# Terminal setup can pass the start limit

- **Severity:** Low. **Likelihood:** Rare. **Effort:** Medium. **Confidence:** High. **Harder later:** No.
- **Kind:** Fix after merge.
- **Added:** 2026-11-08, a new problem from the check of finding 7, branch `conductor/boat-native-remote-workspaces-milestone-5d`, round 1.
- **Location:** `worker/lifecycle/start-command-execution.ts:87-97` (`prepareStartTerminal`), `worker/terminal/service.ts:109-112` (`startWorkspaceTerminal`), `worker/sandbox/boat.ts:209`, and `worker/sandbox/transport.ts:50-56`.
- **Reason:** The overrun has a fixed bound of about 11 minutes and needs a terminal service start that hangs, so it does not block the merge.

- **Source:** Review. **Category:** Product bug.
- **Terms:**
  - **Whole-start limit:** the 20-minute time limit of each create and each resume of a workspace's sandbox, counted from the moment that the start began.
  - **Terminal setup:** the start step that starts the terminal service in the sandbox and caches its password, after the startup script exits.
  - **Synchronous command:** a provider command call that waits until the command ends, up to the provider's 600-second command timeout.
  - **Detached command:** a provider command that runs in the background. Later alarms read its state by its process ID.
  - **Alarm:** a scheduled call of the workspace object that moves a saved start forward by one step.
- **Background:**
  - The user chose the whole-start limit on 8 November 2026, as decision 128 C. `docs/protocol/workspaces-and-sandboxes.md:167-170` states it.
  - The start runs its fetch, branch, and startup steps as detached commands. Each alarm checks the limit, so a user script that never exits ends at the limit.
  - After the startup script exits, `advanceStartSteps` in `worker/lifecycle/start-progress.ts` calls `prepareStartTerminal`.
  - `prepareStartTerminal` checks the limit, calls `startWorkspaceTerminal`, and checks the limit again only after that call returns.
  - `startWorkspaceTerminal` runs a short privileged script as a synchronous command, through `WorkspaceTools.command` and the provider's `runCommand`. The script runs `install -d`, `touch`, `systemctl start conductive-terminal.service`, and `systemctl is-active`.
  - It then reads the 64-byte password file with `readFile`, and it caches the password.
  - `runCommand` sends a fixed `timeoutSeconds: 600`, at `worker/sandbox/boat.ts:209`. The transport aborts a command request after 610 seconds and a file read after 65 seconds, at `worker/sandbox/transport.ts:50-56`.
  - The start coordinator runs its steps and new start requests one at a time. Its `enqueue` and `advance` methods share one `accepting` chain, in `worker/lifecycle/start-coordinator.ts`.
  - One other synchronous command runs inside a time limit. `clearBuildCommands` in `worker/lifecycle/command-intents.ts:28-39` runs in the 60-minute image build, at `worker/lifecycle/image-build-steps.ts:55`. It only removes a small folder, and this item does not cover it.
- **Problem:**
  - The setup command can start just before the limit and then hang, for example in `systemctl start`.
  - The start then waits up to 610 seconds for the command, and up to 65 more seconds for the password read.
  - The limit error comes only after both replies. A new start request on that workspace waits too.
- **Impact if no action:** A start whose terminal setup hangs fails up to about 11 minutes after its 20-minute limit. The start steps show the step as running past the limit that they show. Once the replies come, the error text is right, and the existing failure handling runs.
- **Root question:** How does the terminal setup of a start end by the whole-start limit?
- **Options:**
  - **A.** Change nothing. Keep the checks before and after the setup. The overrun keeps its bound of about 11 minutes. Effort: Small.
  - **B.** Run the setup command as a detached command in its own start step. Save its process ID in the start job. Let each alarm read its state and check the limit, as the fetch, branch, and startup steps do. At the limit, the start fails through the existing failure handling. That handling stops the sandbox of a failed resume and deletes the sandbox of a failed create, so the command ends. A later alarm reads the password file after the command exits. This uses the existing `startCommand` and `getCommandStatus` routes. It needs a new phase in the saved start job, a split of `startWorkspaceTerminal` into its command and its password read, and tests. The password read stays a short request of at most 65 seconds. Effort: Medium.
  - **C.** Take the provider's command timeout from the time that is left before the limit. `runCommand` then needs a timeout parameter, which changes the provider interface, its fake server, and its callers. A command with no time left also needs a rule that refuses it, which is a new rejection. Both need their own decision. Effort: Medium.
  - **D.** Move the terminal setup out of the start, to the first terminal connection. The first connection then waits for the setup, and the terminal backend must report a setup failure. A workspace then becomes ready before its terminal does, which changes the start contract in `worker/lifecycle/README.md`. Effort: Medium.
- **Left out:**
  - A local timer that stops the wait at the limit. A restart of the workspace object loses the timer, and B gives the same bound with saved state.
  - A provider route that ends one command. The fixed routes in `worker/sandbox/routes.ts` have none, a new route is a new provider interface, and a stop of the sandbox already ends every process.
- **Wider fix:** B. No start step then waits for a long synchronous command, so every alarm can check the limit. C reaches every synchronous command too, but it needs a provider interface change and a new rejection.
- **Previous examples:** The restart near day 14 of a stop keeps a stopped sandbox's disk. Its startup script waited for a synchronous command in the same way. Its fix runs that script as a detached command with a saved process ID, through `worker/lifecycle/disk-retention.ts`.
- **Recommendation:** B. It uses the detached path that the other start steps already use, with no new provider interface and no new rejection.
- **Action:** fix after merge, apply B, because the overrun has a fixed bound of about 11 minutes and needs a terminal service start that hangs.
