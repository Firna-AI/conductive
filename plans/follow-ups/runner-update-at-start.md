# Cloud computers with version pin 1 get real logins

- **Severity:** High. **Effort:** Large. **Confidence:** High. **Harder later:** No.
- **Kind:** Needs decision.
- **Added:** 2026-11-09, the wider fix of the decision about older runners in the brainstorm of the Worker model gateway, on branch `conductor/model-gateway-worker-model-proxy-decision-120`. Rewritten from the goal on 2026-11-10, from finding 100 of round 3 of the final review of that branch.

- **Terms:**
  - **Runner:** Conductive's program in each cloud computer. It runs the agents and connects to the workspace Durable Object.
  - **Runner protocol version:** the number that the runner sends when it connects. A runner of version 1 gets the real agent login with each turn.
  - **Turn token:** the value that a runner of version 2 gets in place of the real login. It works only at the Worker's model gateway, and only while its turn runs.
  - **Version pin:** the lowest runner protocol version that a workspace accepts. The Worker keeps it in the column `workspaces.runner_protocol_version` of D1.
  - **Runner archive:** the file of the current runner. The Worker reads its address and its SHA-256 digest from the variables `CONDUCTIVE_RUNNER_ARCHIVE_URL` and `CONDUCTIVE_RUNNER_ARCHIVE_SHA256`.
- **Background:**
  - `docs/protocol/isolation.md` states the pin rule. The version pin decides whether an agent login can reach a cloud computer. A runner connection does not change the version pin.
  - So a newer runner does not keep the agent logins out of a cloud computer with a version pin of 1. Any process with the workspace token can open a runner connection and claim version 1.
  - `docs/protocol/agent-runner.md` states how a workspace gets its pin. Each new cloud computer of a workspace takes the runner version of the org image that it starts from, before the runner can connect. A stop and a resume keep the pin. A workspace or an image with no recorded version counts as version 1.
  - `allocateWorkspace` in `worker/lifecycle/start-allocation.ts` writes the pin at each allocation of a new cloud computer, before the provider call. No other code writes it. The resume branch of `worker/lifecycle/start-machine.ts` starts the old cloud computer again, and writes no pin.
  - `prepareRunnerHello` in `worker/chat/runner-handshake.ts` closes each runner connection whose version is below the pin, before the `welcome` and before any command.
  - Each build and each refresh of an org image installs the newest runner archive, as the section "The runner archive" of `docs/deployment/runner-archive.md` says. Each records the Worker's `RUNNER_PROTOCOL_VERSION`.
  - At each workspace start, a workspace with an older version of the app's own software gets the current runner before the runner starts, as [Old workspaces](../../docs/protocol/workspace-life.md#old-workspaces) says. That update leaves the version pin unchanged.
  - On 9 November 2026 the user chose that a runner of version 1 keeps getting the real login, and that the access doc states the risk. The user also chose that each workspace refuses a runner below the version of its image.
  - So each workspace with a version pin of 1 keeps the old risk for its whole life. Each process and each member's terminal there can read the real login of a running turn.
  - A runner of version 1 also reads the repository's `.claude/settings.json`, because its Claude adapter sets `settingSources: ['project']`. A check on 8 November 2026 with the pinned `claude` program 2.1.318 and a fake key showed that such a file can replace the endpoint. So in such a cloud computer, a repository file can send the real login to any host.
  - At each create and each resume, the startup command of the workspace runs. It uses `sudo -n` for its setup, and its last command restarts the runner service (`workspaceStartupCommand` in `worker/lifecycle/image-software.ts`).
  - `image/install.sh` shows the install steps of an image build. It downloads the archive, checks its SHA-256 digest, unpacks it, and replaces the installed runner.
  - The Worker knows the current runner archive from its own variables, through `runnerSoftware` in `worker/configuration.ts`. Each deploy from `main` publishes the archive of the same commit as the Worker, and sets both variables to it.
  - Since 11 November 2026, a workspace start updates the runner of an older workspace and keeps the version pin. That is the first approach under **Left out**, so this item may be partly obsolete. Plan decision 30 of `plans/software-image.md` answers the root question, and its answer updates or deletes this item.
- **Problem:** A cloud computer whose workspace has a version pin of 1 can get real agent logins, with no end date. A newer runner in that cloud computer does not change this.
- **Impact if no action:** The old risk stays in each such workspace until a member archives it. The Worker keeps the version 1 code for as long as one such workspace lives.
- **Root question:** How does an existing cloud computer stop getting real agent logins?
- **Options:**
  - **A.** Update the runner at each start, and raise the pin from the Worker's own record. At each create and each resume, the Worker gives the cloud computer the address and the digest of the current runner archive. Before the provider call of that start, it raises the version pin of the workspace to its own `RUNNER_PROTOCOL_VERSION`. It takes the version from its own record of the archive that it sends, not from the install result, because sandbox code controls that result. The startup command checks the digest, installs the archive, and restarts the runner service. The fact in the Worker that ends the real login: the raised pin, so the handshake refuses each runner of version 1. The pin rises before the provider call, so the handshake also refuses the old runner that starts with the cloud computer. Cost: it changes the rule that a stop and a resume keep the pin. Each first start after a runner release downloads and checks the archive. A newer runner must read the saved state of an older one. An honest install failure stops agent turns in that workspace until a later start succeeds, because the old runner is below the raised pin. An archive that lags the Worker fails in the same way. Effort: Large.
  - **B.** A one-time move. Each org image gets a new build. Members replace their older workspaces. Then the Worker refuses version 1 in every workspace. The fact in the Worker that ends the real login: a release of the Worker whose lowest accepted runner version is 2, whatever the pin. Cost: members must move their work to new workspaces, and each workspace that nobody moves loses its agent turns. Effort: Medium.
  - **C.** Refuse version 1 after a fixed date, with a notice in each workspace with a version pin of 1 before that date. The fact in the Worker that ends the real login: that date, from which its lowest accepted runner version is 2. Cost: as B, on a schedule. Effort: Medium.
- **Left out:**
  - Change nothing, because it fails the goal of keeping every agent login out of every cloud computer.
  - A runner update at each start that keeps the pin, because a runner connection does not change the pin. Any process can still claim version 1 and get the real login.
  - A pin from the install result that the cloud computer reports, because sandbox code can report any result.
  - A refresh that installs the newest runner, because it reaches only new workspaces, not existing cloud computers.
  - Turn tokens for a runner of version 1, because that runner sends its credential straight to the provider, which refuses a turn token.
- **Wider fix:** A. Each later runner change then reaches each existing cloud computer at its next start, and the pin follows from the Worker's own record.
- **Previous examples:** `docs/protocol/agent-runner.md` rejects a pin by the first runner connection, because a program that the org image or the startup script starts can connect first. That rule has the same class: the protection must rest on a fact that sandbox code cannot change.
- **Related:** `plans/follow-ups/agent-login-in-tool-processes.md` covers the tool processes of runners of version 1, which keep the real login.
- **Recommendation:** A. At the next start of each existing cloud computer, the Worker's own pin ends the real login there, and no member loses a workspace.
- **Action:** ask the user, because each option changes a requirement in force. A changes the rule that a stop and a resume keep the pin. B and C refuse runners of version 1 against the user's choice of 9 November 2026.
