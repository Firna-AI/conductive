# The Worker keeps encrypted copies of machine tokens

- **Severity:** Medium. **Effort:** Small. **Confidence:** High. **Harder later:** Yes.
- **Kind:** Needs decision.
- **Added:** 2026-11-24, from branch `calummoore/own-computers-milestone-8-builds-over-ef32` (pull request #686), review round 1, finding 106. Review round 2, finding 154, and a second check of finding 106 corrected the retention facts on the same day.
- **Location:** `docs/protocol/host-connection.md:60`, `docs/protocol/access-and-security.md:117`, `docs/architecture/data-and-trust.md:26`, `plans/own-computers.md:480-482` and `:708-710`, `worker/lifecycle/start-allocation.ts:85`, `worker/lifecycle/archive-begin.ts:42-49`, `worker/lifecycle/build-machine-token.ts`, `worker/software-image/machine-token.ts`, and `migrations/202611241100_build_command_routes.sql`.
- **Reason:** The protocol promises that the Worker keeps only a digest of each machine token, and only agent calls chose the encrypted copies, so the user decides which side is right.

- **Source:** Review.
- **Category:** Docs or spec.
- **Terms:**
  - **Machine token:** the secret in the env of a sandbox that opens its host connection to its machine object. The machine object checks it against a stored digest.
  - **Replayed create:** a second create request with the same idempotency key, after the reply of the first was lost. The code sends the same body again as a precaution: the repository does not record how Boat answers a replay with a changed body (`plans/follow-ups/unresolved-computer-request-ownership.md`).
- **Background:**
  - `docs/protocol/host-connection.md:60` and `docs/protocol/access-and-security.md:117` say that the Worker keeps only a digest of each machine token. The table at `docs/architecture/data-and-trust.md:26` lists only the digest. Two plan sentences say the same: `plans/own-computers.md:480-482` and `:708-710`.
  - On Boat, a create sends the token in the env of the create body, so a replay must send the same token. The E2B client writes the env after the create, and it finds a lost create by its key (`worker/sandbox/e2b/client.ts:54-61`, `worker/sandbox/e2b/allocation.ts:36-50`).
  - So the Worker keeps an encrypted copy of the token of each create. A resume token gets no copy.
    - **Workspace creates.** The start job keeps the token in its encrypted create payload in the workspace object (`worker/lifecycle/start-allocation.ts:85`), also after the reply, until the start ends. A Milestone 4 agent call of the own computers plan, of 23 November 2026, chose this. Delete org keeps the create body in the create checkpoint (`worker/members/workspace-receiver.ts:80-84`), and so does Archive during a create (`worker/lifecycle/archive-begin.ts:42-49`), also when the sandbox ID is known. The Archive state and the cleanup job of a failed start also hold the body. Only an accepted resume or the org purge deletes a checkpoint (`worker/members/creation-checkpoint.ts:131-135`).
    - **Org builds.** The job keeps it in `image_build_jobs.machine_token_ciphertext` until it saves its sandbox ID. A trigger of the Milestone 8 migration clears it when the job reaches `done` by any writer, also the Delete org write. A failed cleanup recovery keeps it until `done`. Milestone 8 agent calls, of 24 November 2026, chose this.
    - **Software image builds.** The attempt keeps it in `software_images.machine_token_ciphertext`. Each save of the attempt clears it when the attempt has a sandbox ID or reaches `done`.
  - Each copy uses the Worker's key `BOAT_KEY_ENCRYPTION_KEY`, the same key that protects the stored GitHub tokens of source copies.
  - No legal page and no public guide restates the digest-only sentence.
- **Problem:** The protocol says that the Worker keeps only a digest of each machine token. The Worker also keeps an encrypted copy of the token of each create: for a build until the build saves its sandbox ID, and for a workspace until its start ends, or longer in the checkpoint of an interrupted create.
- **Impact if no action:** The protocol and the code disagree on what the Worker stores. A reviewer cannot tell which rule the code must meet.
- **Root question:** What may the Worker keep of each machine token, and for how long, so that the sandbox of a create whose reply was lost still opens its host connection?
- **Options:**
  - **A.** Approve the encrypted copy, and state the rule that the code meets. Change the two digest-only sentences, the table, and the two plan sentences: the Worker keeps a digest of each machine token, and an encrypted copy of the token of a create until the start or build that sent the create ends, also while Delete org or Archive keeps an interrupted create for a resume. The digest stays the value of the check. Read both legal pages and every guide in full, as `CLAUDE.md` asks. Effort: Small.
  - **B.** Derive a stable token for each create from a dedicated key and its saved identity, so no copy is stored. Anyone with the key and the saved IDs can then rebuild each live token, and key rotation needs support for open creates. Effort: Large.
  - **C.** Give the token to the sandbox in a separate step after the create. On Boat, this needs a provider call that the host connection doc does not keep, or a change of the first boot. E2B already writes the env in a separate step. Effort: Large.
  - **D.** A, but keep the copy of a pending build create in the machine object beside its digest, not in D1. The object gives the same token to each replay, and drops it when the sandbox ID is saved and at the revoke. Remove the two `machine_token_ciphertext` columns before the migration reaches `main`. After a Delete org with a lost create reply, the object keeps the copy, because no revoke by build ID reaches it (`plans/follow-ups/build-machine-token-lifetime.md`) and the purge deletes no machine object (`plans/follow-ups/purged-org-machine-objects.md`). Effort: Medium.
  - **E.** Put a single-use enrollment code in the create in place of the token. The host program trades it for its token at its first connection. Costs: each replay must send the same code, so the Worker still keeps an encrypted copy of the code; the host program keeps its token in memory only, so a restart of the host program needs a new code. Effort: Large.
  - **F.** A, and make one short window true for every create. The workspace start drops its saved create body when it saves the sandbox ID. Delete org and Archive keep the body in the create checkpoint only while the sandbox ID is unknown, and Archive clears it when it finds the ID. Then the rule of A can say "until the create gets its reply" for every create. Cost: changes to the Milestone 4 start, checkpoint, and Archive code, with a test for each path. Risk: the allocation calls its input builder whenever no body is saved, and that builder issues a new token, so F must skip that call when the sandbox ID is known. Effort: Medium.
- **Left out:** A fresh token for each replay: on Boat, the replay can be refused, or it can return the first sandbox with a token whose digest the new token replaced. A new create with a new key after a lost reply: the first sandbox keeps no record that leads to it. A replay without the machine variables, or a lookup of the first sandbox by its create key: each needs a Boat fact that the repository records as open; bring it back if that provider check succeeds.
- **Wider fix:** None. The `documentation` skill already asks the protocol and the code to agree.
- **Previous examples:** The Milestone 4 copy in the workspace create payload.
- **Related:** `plans/follow-ups/build-machine-token-lifetime.md` ends the build tokens. `plans/follow-ups/org-deletion-lost-build-allocation.md` must replay a saved build create before the Delete org write, because the trigger clears the copy at `done`. Under B, C, or D, the two token columns of the Milestone 8 migration go, and under E they hold the code, so the answer must come before the own computers branch merges into `main`.
- **Recommendation:** A. It is the only Small option, and it documents what the code keeps for every create. F best protects the codebase, because it makes one short window true for every create.
- **Action:** ask the user, because the protocol promises digest-only storage, and only agent calls chose the encrypted copies.
