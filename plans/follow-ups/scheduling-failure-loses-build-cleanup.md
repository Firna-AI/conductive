# Scheduling failure can lose build cleanup

- **Severity:** Medium. **Likelihood:** Rare. **Effort:** Small. **Confidence:** High. **Harder later:** No.
- **Kind:** Fix after merge.
- **Added:** 2026-11-09, from `calummoore/box-auto-build-onboarding`, review finding 2.
- **Location:** `worker/lifecycle/build-admission-data.ts:11`, `worker/lifecycle/image-build-failure.ts:24`, `worker/lifecycle/image-allocation.ts:6`, and `worker/lifecycle/image-maintenance-data.ts:1`.
- **Reason:** The bug needs unusual scheduling failure and alarm timing, and its fix costs the same after the merge.

- **Terms:**
  - **Image build:** A job that prepares the saved cloud computer image of an org.
  - **Allocation:** The provider request that creates the temporary computer for an image build.
  - **Image coordinator:** The org's Durable Object that advances image builds through alarms.
  - **Job phase:** The saved build step, such as `allocating`, `sources`, or `cleanup`.
- **Background:**
  - `startImageBuild` fails a new build when its first scheduling call fails.
  - The coordinator queues its own calls, but the caller's failure writes go directly to D1.
  - A saved alarm can run before a lost scheduling reply reaches the caller.
  - An earlier pending alarm or a second start request can also advance the build when its first scheduling call fails.
  - `worker/lifecycle/image-builds.md` requires each build to delete its temporary computer and retain cleanup ownership during allocation.
- **Problem:**
  - An alarm reads a running job once and waits for `provider.create`.
  - The scheduling reply then fails, and `failUnscheduledBuild` marks the build failed.
  - `finishUnscheduledBuild` retains `allocating` while no sandbox ID exists.
  - Allocation saves the sandbox ID, then `completeBuildPhase` writes `sources` without checking the failed state.
  - `readImageSchedule` finds no running build, and `pendingImageCleanup` excludes the failed `sources` job.
  - An alarm can also overwrite `done` or `cleanup` after the failure writer chose either phase.
  - The same unchecked phase writes occur after sources, software, install, and snapshot work.
- **Impact if no action:** The app drops cleanup ownership of a temporary computer. The computer stops after 30 minutes, but the app does not delete it.
- **Root question:** How does a build retain cleanup ownership when a scheduling failure overlaps an alarm at any step?
- **Options:** Each option includes a regression with explicit operation gates and a held allocation reply.
  - **A.** Make allocation completion choose `cleanup` for a failed build and `sources` for a running build. Other phase writers retain the same risk. Effort: Small.
  - **B.** Make `pendingImageCleanup` select every finished build whose job phase is not `done`. Keep allocation recovery in `cleanupBuild`. Existing failed rows in other phases also receive cleanup. Effort: Small.
  - **C.** Serialize scheduling failure through the image coordinator and save a durable fallback request when it cannot answer. This needs broader lifecycle changes. Effort: Medium.
  - **D.** Make `completeBuildPhase` atomically select the next phase for a running build and `cleanup` for an ended build. A future writer can bypass the helper. Effort: Small.
  - **E.** Give the caller and alarm guarded D1 writes that let only one claim a job still in `create`. Return the build ID when an alarm claimed it first. This changes the immediate scheduling failure rule in `worker/lifecycle/image-builds.md`. Effort: Medium.
  - **F.** Add a periodic provider sweep for build computers without a cleanup owner. The allowed provider routes contain no list route. This option needs a user decision about that boundary. A wrong filter can delete live work. Effort: Large.
- **Left out:** A delay or a scheduling retry only reduces the race window. One batch for the failure writes still permits a later phase overwrite. Keeping every unscheduled build running loses the immediate retry for a build that no alarm owns.
- **Wider fix:** B. Cleanup follows the saved build result instead of a list of phases.
- **Previous examples:** Commit `43320068`, `fix(lifecycle): finish readiness and retain timeout cleanup`, retained ownership of unresolved allocations. `plans/follow-ups/org-deletion-lost-build-allocation.md` records a separate cleanup ownership failure.
- **Related:** `plans/follow-ups/added-build-can-be-lost.md` changes the same cleanup query for a different cause. Apply its query edit against B's phase-independent selection. `plans/follow-ups/late-scheduling-failure-build-log.md` records a separate effect of a late failure writer.
- **Recommendation:** B. One query change covers every phase without new storage or a new provider route.
- **Action:** fix after merge, apply B, because the timing is Rare and the fix is not harder after the merge.
