# Agent logins are readable inside the sandbox

- **Severity:** High. **Effort:** Large. **Confidence:** High. **Harder later:** No.
- **Kind:** Needs decision.
- **Added:** 2026-11-07, from the user's request on branch `calummoore/conductor-alternative-architecture`, after a read of Conductor's sandbox worker.
- **Location:** `providerEnvironment` in `runner/src/providers/environment.ts:15`, the Codex model provider in `runner/src/providers/codex.ts:40`, the `RunnerLogin` type in `src/shared/runner.ts:88`, the login read in `worker/chat/queries.ts:52`, and the section "Agent logins in a sandbox" of `docs/protocol/access-and-security.md`.
- **Reason:** the access protocol records that the user rejected a login proxy as a much larger build, so only the user can bring it back.

- **Terms:**
  - **Agent login:** the Claude subscription token from `claude setup-token`, the Anthropic API key, or the OpenAI API key of a member. The app stores it encrypted in the table `agent_logins`.
  - **Turn login:** the agent login that a turn runs on. Decision 105 F of 7 November 2026 makes it the login of the member who started the session. Before it, each turn ran on its sender's login (decision 49).
  - **Turn token:** a placeholder key that the agent program sends in place of the real login. It works only while its turn runs.
  - **Tool process:** a program that the agent starts for a tool, such as a shell command or a dev server.
- **Background:**
  - With each turn, the Durable Object sends the turn login to the runner, in the field `login` of the turn command. The type is `RunnerLogin` in `src/shared/runner.ts`.
  - The runner puts the login in the environment of the agent program. Claude gets `CLAUDE_CODE_OAUTH_TOKEN` or `ANTHROPIC_API_KEY`, and Codex gets `OPENAI_API_KEY`.
  - Every process in the sandbox runs as the system user `user`, with passwordless sudo. The runner, the agent's tools, and the terminal run as `user` too (`image/README.md` and `worker/terminal/service.ts`).
  - The access doc accepts two risks. Each process and each member's terminal in the sandbox can read the login of the running turn. A process that a tool starts can keep the login after the turn (decision 114).
  - The access doc also says: "A proxy that keeps every login out of the sandbox was rejected, because it is a much larger build." Decision 49 of 6 November 2026 offered that proxy as option E, and the user chose D.
  - Both agent programs can send their model requests to another address. Claude reads `ANTHROPIC_BASE_URL`. The runner already gives Codex its own model provider, with `base_url` set to `https://api.openai.com/v1`.
  - Conductor, a similar product, keeps the real key out of its sandboxes. Its sandbox worker puts a placeholder in `ANTHROPIC_API_KEY` or `CLAUDE_CODE_OAUTH_TOKEN`, and its network edge puts in the real key. This comes from a read of its worker code on 7 November 2026.
  - Decision 37 records that Anthropic gave the operator permission to use `claude setup-token` tokens. Anthropic's legal page says that "developers may not collect, store, or intermediate Claude.ai credentials or session tokens". Nobody has checked that the permission covers a proxy. If it does not, options A, B, and C cover API keys only.
- **Problem:** The real login is inside the sandbox while a turn runs. Each process, and each member with a terminal there, can read it. A tool process can keep it after the turn.
- **Impact if no action:** A member, or code that the agent runs, can copy another member's login and use it outside the product, also after the turn. The owner of the login must then revoke it.
- **Root question:** How does a turn use a member's agent login, so that nothing in the sandbox can use that login outside the product or after the turn?
- **Options:**
  - **A.** A model proxy in the Worker. Effort: Large.
    - With each turn, the Durable Object gives the runner a turn token, not the login.
    - The runner points the base URL of the agent program at a Worker route, and puts the turn token in place of the key.
    - The route checks that the turn still runs. It puts in the turn login, forwards the request to Anthropic or OpenAI, and streams the answer back. It forwards only a fixed list of model routes.
    - A turn token stops working when its turn ends. A process that stays can still read the token of a later turn while that turn runs.
    - Cost: each model request goes through the Worker, with one more network hop.
    - Cost: model requests are larger than the Worker's default body limit of 1,000,000 bytes in `worker/http/request-body.ts`, so the route needs its own limit.
    - Cost: the privacy page in `src/marketing/privacy.ts` says that code stays in the cloud computers of the org's Boat account. It must say that model requests pass through the app.
    - Risk: a request that an agent program sends with the login to another host fails, because it carries the turn token. Check these requests with both Claude login kinds and with Codex. Boat documents the same base URL design for both Claude login kinds and for Codex, which lowers this risk. Unchecked.
    - Risk: check Cloudflare's limits for answers that stream for many minutes.
  - **B.** An HTTPS proxy on a new server outside the sandbox. Effort: Large.
    - The agent programs send all their traffic through the proxy, for example with `HTTPS_PROXY`. The proxy replaces the turn token in each request to the provider hosts.
    - It also covers requests that do not use the base URL. A process that goes around the proxy holds only a turn token.
    - Cost: the proxy must read HTTPS traffic, so the agent programs must trust its certificate authority.
    - Cost: a new server to run and secure. A Worker cannot run such a proxy. Unchecked.
  - **C.** Boat's AI credentials proxy. Effort: Large.
    - Boat documents a proxy for AI credentials. With it on, a sandbox gets placeholder keys and `ANTHROPIC_BASE_URL` set to Boat's proxy, and the real keys stay with Boat. It covers the Claude sign-in, the Anthropic API key, the ChatGPT sign-in, and the OpenAI API key.
    - Each workspace gets its own Boat environment with `proxyAiCredentials` on, and its own credential profile.
    - At the start of a turn, the Worker writes the turn login into the profile and unblocks the AI access of the sandbox with `PUT /sandboxes/{id}/ai-access`. When no turn runs, the Worker removes the login and blocks the access. Boat then refuses the placeholders with `403`.
    - Cost: each org's Boat key needs the scope `account.admin`, and the app needs one Boat environment for each workspace.
    - Cost: the org's Boat wallet pays $1 for each day that the proxy is on, and $1 for each 1,000 model requests.
    - Risk: a Boat placeholder belongs to a sandbox start, not to a turn. Only the block between turns limits it to a turn.
    - Risk: two sessions in one workspace that run on different logins need one Boat custom API each.
    - Risk: Boat's call that sets a key refuses a sign-in with `400 not_an_api_key`, so a `claude setup-token` token may need a custom API. Nobody has tried it.
    - Risk: logins then depend on Boat. The provider doc wants the app to be able to move to another provider later.
    - Source: Boat's documentation of AI credentials, read on 5 November 2026.
  - **D.** Run the agent programs outside the sandbox. Effort: Large.
    - The agent programs run in a place that no member and no sandbox code can reach. Their file and shell tools act in the workspace sandbox through the runner.
    - The sandbox then holds no login and no turn token. Requests to other hosts keep working.
    - Cost: a new place to run the agents, new tools in place of the agents' own tools, and agent sessions outside the sandbox.
    - It changes decision 36 D and the rule of `docs/architecture.md` that agents work only in the sandbox. Unchecked: whether Codex lets the runner replace its own tools.
- **Left out:**
  - Change nothing: it fails the goal. Today the access doc accepts the risk, and `plans/follow-ups/agent-login-in-tool-processes.md` limits it for tool processes.
  - A process in the sandbox that holds the login under another system user: the real login still enters the sandbox, and each member with a terminal has root through passwordless sudo.
  - A short-lived token for each turn: the app accepts API keys and `claude setup-token` tokens, and neither can make a short-lived token.
  - An org-owned login: it fails the goal, because code that the agent runs can still copy the shared login.
- **Wider fix:** A. It keeps every agent login out of the sandbox, whatever the agent program does with the login. D also keeps the turn token out, at a much larger cost.
- **Previous examples:** the idle agent process that kept the login between turns, fixed by Milestone 7u in PR #30, and the tool processes that keep the login after the turn, in `plans/follow-ups/agent-login-in-tool-processes.md`.
- **Related:**
  - `plans/follow-ups/agent-login-in-tool-processes.md` has the same cause: the login is in the environment of the agent. Each option of this item also fixes that item. If the user chooses one, drop that item.
  - `plans/follow-ups/github-token-readable-in-sandbox.md` has the same class: a member's secret that sandbox code can take. The Worker proxy of option A and a Git proxy can share the check of the running turn.
- **Recommendation:** A. It ties each turn token to one turn and its login, also when sessions run in parallel, and it needs no wider Boat key and no Boat fee.
- **Action:** ask the user, because the access protocol records that the user rejected a login proxy as a much larger build, and each option reverses that rule.
