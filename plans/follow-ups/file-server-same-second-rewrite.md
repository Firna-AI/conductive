# A rewrite in the same second can show a stale page

- **Severity:** Medium. **Likelihood:** Rare. **Effort:** Small. **Confidence:** High. **Harder later:** No.
- **Kind:** Fix after merge.
- **Added:** 2026-11-18, from the review of branch `calummoore/preview-html-file-c42r`, finding 1.
- **Location:** `crates/cnd-runner/src/file_server/response.rs:36-52`, `crates/cnd-runner/tests/file_server/content_tests.rs:52`, `crates/cnd-runner/src/file_server/_tests_/policy_tests.rs:92`, `docs/protocol/file-server.md`.
- **Reason:** A Rare product bug of Medium severity waits for a later branch under the fix rule, and a later runner release fixes it at the same cost.

- **Terms:**
  - **File server:** the part of the agent runner that serves the files of the repository folder on `127.0.0.1:7683`, for the preview of HTML files. `docs/protocol/file-server.md` states its rules.
  - **Files preview:** the preview on the preview domain that loads the page of an HTML file and its files from the file server.
  - **Last-Modified and If-Modified-Since:** HTTP headers. The server gives the time of the last change of a file in whole seconds, and the browser asks with that time whether its copy is still current.
  - **ETag and If-None-Match:** HTTP headers. The server gives a version value of a file, and the browser asks with that value whether its copy is still current.
- **Background:**
  - Each reply of the file server carries `Cache-Control: no-cache` and `Last-Modified`. A request with `If-Modified-Since` for a file that did not change since then gets 304. The user decided on 2026-11-11, in commit `cad68800a`, that preview replies keep the cache rules, because `no-store` made each reload a full load.
  - The file tab of an HTML file reloads its frame when the workspace reports a change of the file. The browser then sends its stored date in `If-Modified-Since`.
  - `unchanged` in `response.rs` compares whole seconds, and the file server sends no ETag.
- **Problem:** A file read at 1000.1 s and written again at 1000.9 s keeps the date 1000 s. A request with that date gets 304, so the browser shows the old content. Two writes in one second with a page load between them cause it. The watcher reports a change only after 100 ms with no file events, so normal agent edits do not meet it.
- **Impact if no action:** After two quick writes, the page and each file that it loads can show the old version until the next write of the file.
- **Root question:** How should each reload show the current content of the page and of each file that it loads, without sending an unchanged file again?
- **Options:**
  - **A.** Compare the full modification time with `If-Modified-Since`. This avoids the false 304, but it sends most unchanged files again, and it still answers 304 when a tool sets a file time back. Effort: Small.
  - **B.** Build one version value from the inode, the size, and the full modification and change times. Send it as an ETag. Let `If-None-Match` win over `If-Modified-Since`, and keep the date as a careful fallback. Use the same value for whole files, ranges, and HEAD. Update the cache sentence of `docs/protocol/file-server.md`. Add a regression test that writes two versions of equal length in one second, and update the two tests that expect the whole-second 304. Effort: Small.
  - **C.** Build the ETag from a hash of the content. This also covers a change that keeps the metadata, but it needs a full read before the reply streams. Effort: Medium.
  - **D.** Keep only date validators: take the later of the modification and change times, send `Last-Modified` only when that date is at least two seconds before the reply, and answer 304 only when `If-Modified-Since` equals it. A file that changed in the last two seconds then goes in full. Effort: Small.
- **Left out:** No change, because the stale page stays until the next write. No browser cache, because it breaks the low-cost reload that the user chose on 2026-11-11. No validator for HTML files only, because a style file or a picture can still go stale. A version query in the frame address, because it renews only the page and not the files that it loads.
- **Wider fix:** B, because its version value also covers a file time that a tool sets back, and the same fixed time that an archive writes again.
- **Previous examples:** None found.
- **Related:** The same branch fixed `If-Range` with an exact date match, as the direct fix of review finding 2. The wider fix of finding 2 waits here: once B adds the version value, check every conditional header that the Worker forwards in one step, in the order of RFC 9110. A false `If-Match` or `If-Unmodified-Since` then gets 412, which the file server ignores today. A false `If-None-Match` or `If-Modified-Since` gets 304, and a false `If-Range` gets 200 with the whole file.
- **Recommendation:** B. It keeps a 304 for each unchanged file, and it uses headers that the Worker already forwards.
- **Action:** fix after merge, apply B, because a Rare product bug of Medium severity waits for a later branch under the fix rule.
