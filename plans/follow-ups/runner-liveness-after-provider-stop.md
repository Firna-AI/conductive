# A message to a computer that the provider stopped waits five minutes

- **Severity:** Medium. **Likelihood:** Rare. **Effort:** Medium. **Confidence:** High. **Harder later:** No.
- **Kind:** Needs decision.
- **Added:** 2026-11-08, from the smoke test of the deploy of `18753f9` on the primary branch `calummoore/conductor-alternative-architecture`, before the first pull request into `main` (decision 141). An options check on the same day added C to F and changed the recommendation from B to C.
- **Updated:** 2026-11-23, from the review of `calummoore/agent-scheduling-wake-future-nlp0`. The same window can lose a scheduled wake-up.
- **Location:** `registerTrustedTurn` at `worker/lifecycle/runner-lifecycle.ts`, `reconcileReply` at `worker/lifecycle/workspace-actions.ts`, `stopDispatchedTurns` at `worker/chat/workspace-stop.ts`, the idle stop at `worker/lifecycle/durable-alarm.ts`, wake delivery at `worker/chat/wake-resume.ts`, the connection at `worker/chat/runner-connections.ts` and `worker/chat/runner-channel.ts`, alarm rules at `worker/lifecycle/durable-scheduling.ts` and `worker/lifecycle/durable-types.ts`, the runner connection at `crates/cnd-runner/src/link/connection.rs`, and `docs/protocol/agent-runner.md`.
- **Reason:** the behaviour existed before the reviewed commits, and option B adds a protocol rule.

- **Terms:**
  - **Runner:** the program in the cloud computer that runs the agent turns. It keeps one WebSocket connection to the workspace object.
  - **Provider stop:** a stop that the sandbox provider makes without a call from the app, such as its own auto-stop.
  - **Turn heartbeat:** the alarm of the workspace object that checks a running turn every 5 minutes.
- **Background:** The app stops an idle computer itself after 30 minutes. The provider can also stop it. A stop freezes the computer, so the runner sends no close frame, and the connection looks open to the workspace object. Neither side checks that the connection is still alive. When the connection closes, the workspace object checks the provider within 5 seconds.
- **Problem:** On 8 November 2026, the smoke test stopped a computer through the provider and sent a message 22 seconds later. The workspace still showed Unread, so the object sent the turn to the frozen runner. No turn started. After 5 minutes, the turn heartbeat found the stopped computer and ended the turn as Stopped, with no reply. A resume and a new message then got a reply at once.
- **Scheduled wake-up case:** A stop can freeze the runner while its WebSocket still appears open. `worker/chat/wake-resume.ts` can then flush the wake-up to that socket and report handoff. The wake-up clears its retry record. A confirmed stop ends the dispatched turn. The queued-message recovery keeps only messages whose state is still queued, so it can lose the wake-up marked sent to the frozen runner.
- **Impact if no action:** After a provider stop, a message waits up to 5 minutes and ends with no reply. The user must send it again. Until then, the tab shows a running workspace whose computer is stopped. During an idle stop, a scheduled wake-up can leave a fired line without its agent work.
- **Root question:** How does the app soon treat a computer that stopped without the app as stopped, so that a new message waits for the resume?
- **Options:**
  - **A.** When a sent turn has no `turn.started` after 30 seconds, check the provider at once. If the computer stopped, end the turn as Stopped and show the stopped state. Effort: Small.
  - **B.** Add a liveness rule to the runner connection: the runner sends a ping every 15 seconds, and the workspace object closes a connection that is silent for 45 seconds. The close starts the provider check within 5 seconds. State the rule in "The agent runner" of `docs/protocol/agent-runner.md`. Effort: Medium.
  - **C.** Treat a stop under way as a stop for new work. When a provider read reports that the computer is stopping, the workspace object sends no turn, keeps the message queued, and closes the runner connection. The provider check then runs every 5 seconds until the stop ends, and the message runs after the resume, as decision 14 says. The reads are the read before a turn, the read at user activity, and the read at the turn heartbeat. It changes no requirement. It needs a one-time check that the provider reports `archiving` during a stop. Effort: Small.
  - **D.** Receive the provider's signed `archived` and `error` webhook events at a new Worker route. The workspace object then reads the provider state at once, so a forged event causes one read at most. The user registers the webhook and stores its signing secret. D changes the statement "The app does not depend on Boat webhooks" in `docs/architecture/components.md`, whose reason went away with decision 80. A turn sent during the stop still needs C. Effort: Medium.
  - **E.** When the workspace object finds a stop, it keeps each turn that the runner never started, and the turn runs after the resume. The runner keeps a record of each accepted turn, so a resent turn does not run twice. E changes the rule "The agent stopped" in "Messages" of `docs/protocol/messages-and-attachments.md` for a turn that never started. Effort: Medium.
  - **F.** Set `TURN_HEARTBEAT_MS` to 30 seconds. It also finds a stop during a started turn, but it makes ten times more provider calls for each working workspace. Effort: Small.
- **Left out:** WebSocket ping frames, because the WebSocket API of Workers cannot send a ping or report a pong. A provider read on a timer while a tab is open, because each activity report of a tab already reads the provider at most once a minute.
- **Wider fix:** D, in place of B. D finds each stop and error that the provider reports, for every runner version, also with no turn and no open tab. B works only for a runner from a newer image, and it needs a version gate. C stays necessary with B or D.
- **Previous examples:** None found.
- **Related:** `plans/follow-ups/queued-turn-start-at-accept-boundary.md` covers durable start intent. The wake retry for a runner that has already disconnected also applies while the workspace still shows Ready.
- **Recommendation:** C, in place of B. The message of the smoke test then waits and runs after the resume, for every runner version, with no new requirement. D best protects the codebase against later provider stops.
- **Action:** ask the user later, because the user deferred this choice on 8 November 2026. The options check found that C needs no new rule, so the user can also choose C to apply without a decision.
- **Done when:** Test a stop that freezes the runner while the socket stays open. Queue a member message and a scheduled wake-up during that window. With option C they stay queued until the stop completes. They reach the resumed runner once each.
