# A missed repository webhook leaves old values

- **Severity:** Low. **Likelihood:** Rare. **Effort:** Medium. **Confidence:** High. **Harder later:** No.
- **Kind:** Needs decision.
- **Added:** 2026-11-18, from branch `calummoore/firna-ai-user-interface-discrepancy-lsqt`, the code options of review finding 9 of round 2.
- **Location:** `worker/github/repository-change.ts`, `worker/github/webhook.ts`, and `docs/protocol/repository-changes-on-github.md`.
- **Reason:** every option adds automatic behaviour that the user has not chosen, and the branch already corrected the doc.

- **Source:** Review. **Category:** Product bug.
- **Terms:**
  - **Saved values:** the `full_name` and `default_branch` columns of the `repositories` table.
  - **Org image:** the saved copy of a cloud computer of an org, with its repositories copied in. New workspaces start from it.
- **Background:**
  - On 17 November 2026 the user chose that a GitHub `repository` webhook saves the new name or default branch of a repository. The webhook reads the current values from GitHub and saves them.
  - While the org image holds values that differ from the saved values, the image coordinator starts a build. This check compares the saved values with the image. It reads no GitHub data.
  - GitHub does not send a failed webhook again by itself. Only an owner of the GitHub App can send it again, for 3 days. A webhook can also never arrive, for example while the app is not subscribed to the Repository event.
  - Every push, pull request, check, and status webhook payload of the repository also holds its `full_name` and `default_branch`.
- **Problem:** When the repository webhook never reaches the Worker, the saved values and the org image keep the old name or default branch.
- **Impact if no action:** Members see the old name, and builds copy the old values, until a later change of the repository or a manual redelivery.
- **Root question:** How do the saved values catch up when the repository webhook never arrives?
- **Options:**
  - **A.** Change nothing. The doc already says that the old values stay until a later change or a redelivery. Effort: Small.
  - **B.** At each other webhook of the repository, compare the payload's `full_name` and `default_branch` with the saved values. When they differ, run the read, the guarded save, and the wake of the repository webhook. A failed read only warns. Effort: Medium.
  - **C.** A step of the 15-minute cron lists recent failed `repository` deliveries through `GET /app/hook/deliveries` and asks GitHub for one re-send of each through `POST /app/hook/deliveries/{id}/attempts`. It cannot recover an event that GitHub never sent. Effort: Medium.
  - **D.** A daily step reads the current values of every saved repository from GitHub, and saves each difference through the guarded writer. Check the Privacy page, because the Worker then reads GitHub on a schedule. Effort: Medium.
- **Left out:** A save from the repository list of a member was rejected by the user on 17 November 2026, because a read then changes saved data.
- **Wider fix:** D, because it repairs old values whatever their cause.
- **Previous examples:** None found.
- **Related:** `plans/follow-ups/repository-values-guarded-writer.md`: each writer that B or D adds must use its guarded writer.
- **Recommendation:** B. Webhooks stay the only trigger, and B reuses the existing read and the guarded save.
- **Action:** ask the user, because each option except A adds automatic behaviour at a boundary that no requirement covers.
