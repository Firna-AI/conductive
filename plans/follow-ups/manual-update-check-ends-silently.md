# A manual update check can end silently

- **Severity:** Low. **Effort:** Small. **Confidence:** High. **Harder later:** No.
- **Kind:** Needs decision.
- **Added:** 2026-11-09, from decision 6 of the Mac app update plan on branch `calummoore/desktop-app-auto-update`. The user deferred the whole choice to this item on 9 November 2026, with the answer "6 = follow up", and chose no option.
- **Location:** `check` at lines 115 to 127 and `updateFailed` at lines 85 to 87 of `desktop/src/updates.ts`, the tests in `desktop/src/updates.test.ts`, and the section "Updates in the app" of `docs/protocol/desktop-app.md`.
- **Reason:** the user deferred this choice on 9 November 2026 without an answer, so the update change shipped with the current silent behaviour.

- **Terms:**
  - **Manual check:** the menu item Help → Check for updates of the Mac app.
  - **electron-updater:** the npm package that reads the GitHub releases, downloads a new version, and hands it to macOS.
  - **Squirrel.Mac:** the macOS update framework inside Electron. It accepts a downloaded version, and it replaces the app when the update installs.
  - **Read-only copy:** a copy of the app that runs from its mounted DMG, or from the hidden read-only place where macOS runs a downloaded app until the user moves it.
- **Background:**
  - The Mac app updates itself from the GitHub releases of `Firna-AI/conductive`. It checks at launch and every 4 hours, and it downloads a new version automatically.
  - The app shows "The update is ready." with Restart now and Later only after Squirrel.Mac accepts the downloaded version.
  - On 9 November 2026, the user chose a dialog for each manual check. With no new version, it says "Conductive is up to date.". After a failed check, it says "Conductive could not check for updates. Try again later.".
  - When a manual check finds a new version, the dialog says "Downloading the new version. Conductive tells you when it is ready.". When a downloaded version waits, the check shows "The update is ready." again. Automatic checks stay silent.
  - The download is about 130 MB. It can fail, for example when the network drops.
  - After the download, macOS can still refuse the version. It always refuses on a read-only copy.
  - electron-updater 6.8.9 reports a failed download and a refusal by macOS through the same download promise. Its own `update-downloaded` event fires between the download and the handoff to macOS, so the app can tell the two apart.
  - Evidence, read on 9 November 2026: in electron-updater 6.8.9, lines 253 to 474 of `AppUpdater.js` end `checkForUpdates` before the download ends, and the download promise rejects on a failure. Lines 207 to 227 of `MacUpdater.js` emit `update-downloaded`, and then wait for the `error` event of the native updater.
  - Lines 299 to 308 of `SQRLUpdater.m` in Squirrel.Mac refuse a read-only copy before they fetch the ZIP file. Electron only logs a promise rejection in the main process that nothing handles.
  - In `desktop/src/updates.ts`, `check` gives its answer when `checkForUpdates` ends. A later download or install error reaches `updateFailed`, which only writes "Conductive: A desktop operation failed." to the standard error stream.
  - `docs/protocol/desktop-app.md` says that a failed check, download, or install does not stop the app, and that only a failed manual check shows an error.
  - After a short failure, the next automatic check, at most 4 hours later, downloads again and shows "The update is ready.".
  - All options keep two rules. The app downloads a new version automatically, as the protocol says. Automatic checks stay silent, as the user chose on 9 November 2026.
- **Problem:** After "Downloading the new version.", a failed download or a refusal by macOS leaves the person without an answer.
- **Impact if no action:** The person waits for a message that never comes. When the failure lasts, as on a read-only copy, they never learn why.
- **Root question:** How does a person who chose Check for updates learn the final outcome, also when the new version never becomes ready?
- **Options:**
  - **A.** Change nothing. The person can choose Check for updates again. Effort: Small.
  - **B.** When a download that a manual check started fails, show "Conductive could not download the update. Try again later." A refusal by macOS stays silent. Effort: Small.
  - **C.** Change the found-version text that the user chose on 9 November 2026 so that it promises nothing, such as "Downloading the new version.". A failure then stays silent. Effort: Small.
  - **D.** Answer a manual check once, with its final outcome. After a found version, no dialog shows until macOS accepts the version or a step fails. The person gets no answer during the download. Effort: Small.
  - **E.** Keep the found-version answer, and follow that version until macOS accepts it. A failed download shows B's text. A refusal by macOS shows "Conductive could not install the update. Try again later." On a read-only copy, it shows "Move Conductive to Applications to install the update." instead. Automatic downloads stay silent. Effort: Small.
  - **F.** Answer a manual check in a small progress window, as the Mac update framework Sparkle does. The window shows the download, then the ready state or the failure. It needs a new window, a mockup, and a protocol change. Effort: Large.
- **Left out:**
  - The text of a failed check: it names the wrong failure, and the copy rules of the `product-ui` skill say that an error names what failed. B is better on every point.
  - A notification, a Help menu label, or a Dock progress bar as the answer: the user rejected on 9 November 2026 an answer that the person can miss.
- **Wider fix:** E. It ends each manual check with one true answer, whatever step fails after the promise.
- **Previous examples:** None found.
- **Related:** `plans/follow-ups/read-only-copies-never-update.md` adds an offer at launch to move a read-only copy into Applications. E's read-only text only explains a refusal after a manual check. Either item can ship first.
- **Recommendation:** E. It costs the same as B, and its answer stays true for every failure after the promise, also on a read-only copy, where B's "Try again later." never helps. The first recommendation was B.
- **Action:** ask the user, because B, D, E, and F add or change answers that no requirement covers, and C changes the found-version text that the user chose. The user deferred this choice on 9 November 2026, so it is still open.
