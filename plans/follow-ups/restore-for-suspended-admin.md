# Cron can finish a suspended admin's Restore

- **Severity:** Medium. **Likelihood:** Rare. **Effort:** Small. **Confidence:** High. **Harder later:** No.
- **Kind:** Fix after merge.
- **Added:** 2026-11-08, from PR #54, branch `conductor/boat-native-remote-workspaces-milestone-15i`, round 1, finding 16.
- **Location:** `saveRestoreRequest` at `worker/members/restore-data.ts:36-37`, `pendingRestoreRequest` at `worker/members/restore-data.ts:66-70`, and `restoreOrgRecords` at `worker/members/restore-data.ts:88-91`. The Cron entry at `worker/application.ts:165`.
- **Reason:** A Restore handoff must fail, and its admin must be suspended before the Cron retry. The Small fix costs the same after the merge.

- **Terms:**
  - **Restore intent:** the saved Restore request of an admin, in the `org_deletions` row of a deleted org, which scheduled cleanup can finish later.
  - **Cron Trigger:** the scheduled Cloudflare call of the Worker. Its `scheduled` entry runs `cleanupDeletedOrgs`.
  - **Active admin:** an admin who is not suspended, as "Owners and admins" in `docs/protocol/operator-actions.md` says. `activeAdminMemberPredicate` in `worker/data/active-admin.ts` gives the SQL of that rule.
- **Background:**
  - Delete org stops every sandbox of the org and hides the org at once. The app deletes everything of the org after 7 days, unless an admin restores it, as "Delete org" in `docs/protocol/orgs-and-members.md` says.
  - Restore saves a Restore intent bound to its admin. It stops the sandboxes, plans the disk dates, and hands the maintenance back. Only then does it clear the deletion marker, in `worker/members/restore.ts:18-99`.
  - A failed handoff keeps the intent. Milestone 15i added the Cron entry, which retries the intent through `cleanupDeletedOrgs` and `finishPendingRestore`, at `worker/members/cleanup.ts:49-52`.
  - That retry does not pass the gate of an HTTP request. The HTTP Restore refuses a suspended user through `requireOrgAdmin`, which calls `requireActiveUser`, at `worker/members/restore.ts:25`.
  - While an org is deleted, the members gate allows only the org read, Restore, and Delete, at `worker/members/gate.ts:31-34`. So role changes, leaves, and removals wait, and a suspension is the main way for an admin to lose authority.
  - The protocol applies the active-admin rule only to owner moves and to the last-admin count. The user chose that rule on 8 November 2026, as decision 123, option E.
- **Problem:**
  - The three Restore queries check only `role = 'admin'`: the save at `worker/members/restore-data.ts:37`, the read of the pending intent at `:68-70`, and the activation at `:91`.
  - A suspension leaves the role as it is. So a Cron retry after the suspension of the admin still activates the org.
  - A check in memory returned `activated: true` after the suspension, and it cleared the deletion marker of the org.
- **Impact if no action:** A Restore that an admin asked for before a suspension can still reopen the deleted org to its members. The suspended admin gains no access, and another admin can delete the org again.
- **Root question:** When a Restore takes effect after the admin asked for it, must that admin still be an active admin?
- **Options:**
  - **A.** Check the suspension in the read of the pending intent and in the final activation. Add a Cron regression. Effort: Small.
  - **B.** Use `activeAdminMemberPredicate` when the code saves, retries, and activates a Restore intent. Effort: Small.
    - The read of the pending intent already joins `org_members` as `m`. The save and the activation can use the alias `org_members`. The predicate accepts both aliases.
    - Add a regression test that suspends the admin between a failed handoff and `cleanupDeletedOrgs`. The org must stay deleted.
    - Add a line to "Owners and admins" in `docs/protocol/operator-actions.md`: a Restore takes effect only while the admin who asked for it is an active admin.
    - Add "not suspended" to the sentence "An invalid admin or an expired window cannot activate a pending Restore." in `worker/members/README.md:144`.
    - A and C need the same two doc changes, because no protocol line states this behaviour today.
  - **C.** Cancel the Restore intents of an account at its suspension, and keep an atomic active-admin check at the activation. This adds cleanup to the suspension. Effort: Medium.
  - **D.** Keep the code, and record a decision that a Restore which an admin asked for before a suspension still takes effect. Effort: Small.
    - State it in "Delete org" of `docs/protocol/orgs-and-members.md` and in `worker/members/README.md`.
    - Benefit: when the only admin is suspended during a failed Restore, the members keep the org and their unpushed work.
    - Cost: Restore becomes the only admin write that ignores a suspension. Delete, rename, settings, invitations, member writes, and the HTTP Restore all refuse a suspended admin.
    - On 8 November 2026, decision 124, option A, accepted a similar risk for copied workspace tokens.
- **Left out:**
  - A check only in the HTTP request. The Cron retry never passes that check, so it fails the goal.
  - A check in the Cron loop before `finishPendingRestore`. A read before the write is not atomic, and B makes the same check inside the write, so B is better on every point.
  - A database trigger on `users.suspended_at`. It is C in a migration, and it still needs the check at the activation.
  - An intent bound to the sign-in session of the admin. Each sign-out or session expiry would then cancel a valid Restore, so it fails the goal.
  - No Cron retry. A failed handoff would then cancel the intent, and the admin would have to ask again. B is better on every point. It keeps the automatic completion of commit `29af3ce`, and a Restore inside one request still needs its check at the activation.
- **Wider fix:** B. The shared active-admin rule already exists, and B applies it to Restore. The shared predicate carries each later change of the meaning of "active".
- **Previous examples:** Commit `de86ced` added `activeAdminMemberPredicate` and `worker/members/active-admin-guards.test.ts`.
- **Recommendation:** B. One shared atomic predicate covers the Cron retry and a suspension during one HTTP Restore. Its rare cost is that of a suspension before the request. When the only admin is suspended, the app deletes the org after 7 days.
- **Action:** fix after merge, apply B, because the bug needs a failed handoff and a suspension before the Cron retry. The suspended admin gains nothing, and the fix costs the same later.
