# A resent turn can move the idle stop

- **Severity:** Medium. **Likelihood:** Rare. **Effort:** Medium. **Confidence:** High. **Harder later:** No.
- **Kind:** Fix after merge.
- **Added:** 2026-11-08, from PR #53, branch `conductor/boat-native-remote-workspaces-milestone-8m`, round 1, finding 16, with the new problem and option E of its check.
- **Location:** `applyLifecycleTurn` at `worker/lifecycle/durable-turns.ts:20`, `DurableLifecycle.turn` at `worker/lifecycle/durable.ts:180-191`, `flushPending` at `worker/chat/runner-delivery.ts:82-101`, and `turnDispatching` and `turnDispatchFailed` at `worker/chat/workspace-integration.ts:107-117`.
- **Reason:** The bug needs a rare order of reconnect, resend, and replay, and E changes the lifecycle turn code that Milestone 5e also changes.

- **Terms:**
  - **Runner:** the program in the cloud computer that runs the agent turns and sends their events to the workspace object.
  - **Turn command:** the stored command that gives one turn to the runner. It stays pending until the workspace stores the `turn.started` event of that turn.
  - **Idle time:** `lastActivityAt` in the lifecycle state of the workspace object. The idle stop comes 30 minutes after it, when no turn runs.
  - **Committed chat summary:** the turn facts that the chat stores with its events. `readChatRecovery` gives the running turns and `lastTurnEndedAt`, the stored time of the newest turn end.
- **Background:**
  - A sandbox stops after 30 minutes without user activity and without a running agent turn, as `docs/protocol/workspaces-and-sandboxes.md:202-203` says.
  - Milestone 8m made the stored turn times set the idle time. A repair, a `hello`, a heartbeat, or a restart never starts a new idle period, as `worker/lifecycle/workspace-object.md:192-194` says.
  - On the normal path, a runner turn event gives `DurableLifecycle.turn` its stored `occurredAt`. Without a time, `turn` uses the current time, at `worker/lifecycle/durable.ts:184`.
  - `applyLifecycleTurn` and `recoverLifecycleTurns` always keep the later time, at `worker/lifecycle/durable-turns.ts:20` and `:34-37`.
  - At each runner `hello`, the workspace repairs the turns from the committed chat summary. Then it sends each pending command again, at `worker/chat/runner-channel.ts:139-150`.
  - Replayed runner events queue when they arrive, so the resend and the replay race.
  - A turn command stays pending until `turn.started` arrives, at `worker/chat/turn-events.ts:78-86`. `canDispatch` accepts a running turn, at `worker/chat/turn-lifecycle.ts:62`. So each new connection sends the command again.
  - The runner ignores a repeated command, at `runner/src/engine.ts:25` and `runner/src/engine-turns.ts:46-47`.
- **Problem:**
  - The connection drops before the workspace stores `turn.started`. The runner stores the turn end on its own disk. At the reconnect, the resend runs before the replay.
  - The resend calls `turnDispatching`, at `worker/chat/runner-delivery.ts:82-94`. It registers the turn again through `registerTrustedTurn`, which passes no time, at `worker/lifecycle/runner-lifecycle.ts:63`. So the idle time becomes the current time.
  - The replayed older end and the repair keep that later time.
  - A failed resend has the same effect. When the connection closes during the `turnDispatching` of a resend, `turnDispatchFailed` ends the lifecycle turn at the current time, at `worker/chat/runner-delivery.ts:95-101`. The chat turn still runs.
  - After a failed resend, the workspace also shows `ready` while the agent works, until the next alarm or `hello` repairs the turns.
  - No test sends the command again before its replayed end.
- **Impact if no action:** The idle alarm moves to the reconnect time plus 30 minutes, at `worker/lifecycle/durable-scheduling.ts:31`. The sandbox runs longer by the time between the turn end and the reconnect, up to 30 minutes. A manual stop is the only workaround.
- **Root question:** Which sources may set the idle time, and how does each other lifecycle turn update leave it unchanged?
- **Options:**
  - **A.** Pass the stored start time of the turn through each repeated registration. This adds time handling to the dispatch path. Effort: Small.
  - **B.** Make the running-state update idempotent for the idle time, so that a repeated registration does not count as new activity. Add the reconnect regression with a late `turn.started`. B does not cover the failed resend. Effort: Small.
  - **C.** Derive the running state and the idle time from the committed chat at each lifecycle use. This removes the timing of callbacks as a source. Effort: Large.
  - **D.** Treat the resend of a begun turn as a transport retry. Effort: Small.
    - In `RunnerDelivery.flushPending`, call `turnDispatching` and `turnDispatchFailed` only while the chat turn is `queued`. For a begun turn, check only the lifecycle state.
    - The `hello` repair has already restored the turn record and the running session from the committed chat.
    - D also removes the short `ready` state of a failed resend.
    - Cost: the resend then depends on that repair order, which `worker/lifecycle/workspace-object.md` documents.
  - **E.** Take the turn part of the idle time only from the committed chat summary. Effort: Medium.
    - `applyLifecycleTurn` reads `lastTurnEndedAt` through a read-only hook over `readChatRecovery`. `DurableLifecycle.turn` takes no time from its caller.
    - Remove the `occurredAt` parameters of `turn`, `finishLifecycleTurn`, `reportRunnerLifecycle`, and `applyRunnerLifecycle`. Milestone 8m added them.
    - Then no registration, resend, failed send, or later caller can move the idle time. The normal path and the repair use one source.
    - E keeps the running sessions as they are. So the short `ready` state of a failed resend stays until the next repair.
    - Cost: one summary read for each turn update. The read runs inside the chat queue that each caller already holds. The tests in `worker/lifecycle/durable.test.ts` need a stub of the hook.
    - Test: disconnect before `turn.started`, let the runner store the turn end, and reconnect with the resend before the replay. Advance only due stored alarms. Assert that the stop comes 30 minutes after the turn end.
    - Test: close the connection during the `turnDispatching` of the resend. The idle time must not move.
  - **F.** Send the pending commands again only after the replay. Effort: Medium.
    - The `hello` of the runner reports its last stored event number. The Worker sends pending commands only when the stored cursor reaches that number.
    - The replayed `turn.started` then removes the command. So the runner gets no second command for a turn that it already has.
    - Cost: a runner protocol change in `src/shared/runner.ts`, the runner link, the parser, and `docs/protocol/agent-runner.md`. It needs a new runner build, and it delays new commands after each reconnect.
    - It does not stop another caller from passing the current time.
- **Left out:**
  - A reconnect alone repeats the same update, so it fails the goal.
  - Ignoring the stored end times breaks the rule that keeps the original idle time.
  - Never sending a begun turn again breaks a requirement that stays. A send that the disconnect lost would never reach the runner, against the forward rule at `docs/protocol/agent-runner.md:77-78`.
  - A fixed wait before the resend fails the goal. A slow replay still loses the race.
  - A runner reply to a repeated command. D is better on every point, because it covers the same paths with no protocol message.
  - A fix in the browser fails the goal, because the idle stop is server state.
- **Wider fix:** E. B works only when the bad update is a repeated start. E works for any update, because no caller supplies a turn time.
- **Previous examples:** Before Milestone 8m, every turn update used the current time. Option D of the deleted item `plans/follow-ups/confirmed-runner-projection-retry.md`, at commit `d0faa94`, set the rule that a reconnect keeps the original idle time. Milestone 8m applied it.
- **Related:**
  - [native-entries-advance-alarms.md](native-entries-advance-alarms.md): the regression of E must check the stored idle alarm with a due-alarm advance. Use the advance of `worker/chat/integration/workspace-recovery-entry.test-support.ts`, or the shared method of that item when it lands.
  - [shared-object-alarm.md](shared-object-alarm.md): both items change the lifecycle in Milestone 5e, and they do not conflict. E changes where the turn time comes from. That item changes how the object keeps its due times.
- **Recommendation:** E. It makes the committed chat the one source of turn times, so no resend and no later caller can move the idle time. D is the Small alternative. It also removes the short `ready` state, and it does not conflict with E.
- **Action:** fix after merge, apply E, because the product bug is Medium and Rare, and E changes the lifecycle turn code that Milestone 5e also changes.
