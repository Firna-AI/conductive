# Held answer text keeps an ended secret copy

- **Severity:** High. **Effort:** Medium. **Confidence:** High. **Harder later:** No.
- **Kind:** Outside the scope.
- **Added:** 2026-11-18, from review round 2 of branch `calummoore/follow-up-tool-detail-cuts-precede-env-q1hv`, under Outside the scope.
- **Location:** `worker/chat/output-filter-records.ts:78`, `pruneSavedOutputSecrets` in the same file, `OutputSanitizer.delta` and `retain` in `src/shared/output-sanitizer.ts`, `scanSecretText` in `src/shared/secret-text.ts`, and `filterRunnerOutput` in `worker/chat/runner-output.ts`.
- **Reason:** The gap is in the answer filter on `origin/main`, and the tool-detail branch that found it keeps that behaviour.

- **Source:** Review.
- **Category:** Security.
- **Terms:**
  - **Durable Object:** the server-side object of one workspace in the Worker, which keeps the chat and the saved filter state of that workspace.
  - **Answer filter:** the exact-copy filter of agent answer text, `OutputSanitizer` in `src/shared/output-sanitizer.ts`, which `filterRunnerOutput` runs at each runner event.
  - **Held text:** the end of an unfinished answer that the answer filter keeps back, because it can still start a secret value. The Durable Object saves it encrypted.
  - **Active values:** the values that the filter hides at a runner event: secret env values, current values of used org secrets, and live temporary values.
  - **Temporary value:** a value that a member gives an agent for 15 minutes or for the workspace. It ends at expiry, at removal, or at archive.
- **Background:**
  - The answer filter holds back the end of an answer that can still start an active value. It saves that held text with the whole values that it can still start, in `OutputSanitizer.delta` and `retain`.
  - The scanner holds the rest of the text when a longer active value can still start with it. It checks this before it checks for a whole match at the same place.
  - That check is in `scanSecretText` of `src/shared/secret-text.ts`, which `OutputSanitizer` calls through `filterSecretText`. On `origin/main` at `221df8ca0`, the same check is in the private `filter` method of `OutputSanitizer`.
  - So held text can be a whole copy of a shorter active value, when a longer active value starts with it. Its saved list then names only the longer value.
  - When a temporary value ends, `pruneSavedOutputSecrets` runs `retainActiveSecrets` over every saved record. It drops ended values from the lists, and keeps the held text as it is.
  - At the next runner event, `filterRunnerOutput` filters the held text and the new text with the active values only. So the whole copy of the ended value shows. A turn end also releases the held text.
  - The same release happens when an org secret changes, or when a new start changes an env value. The next runner event then uses the current values.
  - The gap needs two active values where one starts with the other. It also needs an answer event that ends with the shorter value just before that value ends.
  - Reproduction with synthetic values: a temporary value `short-token` and an active value `short-token-longer`. An `assistant.delta` with the text `short-token` shows nothing. Its saved held text is `short-token`, with only `short-token-longer` in its list.
  - After `retainActiveSecrets` with only `short-token-longer`, the held text is still `short-token`. The next delta `!` then shows `short-token!`, and a turn end shows `short-token`.
  - Without the removal, the same delta `!` shows `[redacted]!`, and a delta `-longer` shows `[redacted]`.
  - A read-only probe gave these results on `origin/main` at `221df8ca0` and on branch head `043eebc3c`. It used the real `OutputSanitizer` and `retainActiveSecrets`.
  - Rule: "The exact-copy filter" in `docs/protocol/secret-requests.md` says: "For a temporary value, the filter keeps its copy for the time of that value."
  - Rule: "Secrets that users enter" in `docs/protocol/tokens-and-secrets.md` says that the Durable Object "hides each exact copy of a secret value in the text that screens show from each runner event". It does this "before it checks, stores, or sends the event".
  - Rule: the Privacy page in `src/marketing/privacy.ts` says that a value given "for 15 minutes stays for 15 minutes". It also says that the app hides each exact copy "in the text of the chat".
  - `worker/secrets/README.md` says that the cleanup "removes temporary copies from encrypted saved filter state".
  - The test `filters temporary values for their lifetime and prunes saved copies at expiry` in `worker/secrets/output-filter.test.ts` asserts that saved filter state holds no copy of the value after expiry. It also asserts that a copy whose end arrives after expiry shows. Each option below keeps both assertions.
- **Problem:** When a temporary value ends while held text holds a whole copy of it, the copy stays, encrypted, in the saved filter state. The next text of that answer, or its turn end, then shows the copy in stored chat. That copy arrived while the value was secret.
- **Impact if no action:** A whole copy of a secret value outlives its lifetime in workspace storage, and then shows in stored chat and in each browser replay. This breaks the lifetime rule, the exact-copy rule for the event that carried it, and the Privacy page.
- **Root question:** How does held answer text keep no whole copy of a secret value past its lifetime, while a longer secret value can still complete?
- **Options:**
  - **A.** Change the rules to allow the copy. `docs/protocol/secret-requests.md`, `docs/protocol/tokens-and-secrets.md`, and the Privacy page then say that a whole copy that a longer value holds back can outlive its value, and then show. This changes requirements and a legal page, so it needs the user. Effort: Small.
  - **B.** Finish the held scan at each cleanup. Before expiry, removal, or archive changes the temporary values, scan each saved held text with the full value set from before the change. `storedAgentOutputSecrets` in `worker/secrets/output-values.ts` already reads that set. Mask each whole copy of an ending value, also when a longer value could still complete it. Cost: if the answer then completes the longer value, the rest of that value shows after the mask, though no whole copy shows. The answer scanner holds no part of a literal `[redacted]` marker. So when an ending value lies inside a split literal marker, the finish masks it as the scanner masks an active value there today. It does not cover an org secret or env value change, which runs no cleanup. Effort: Small.
  - **C.** Save no whole copy of an active value raw in held text. When held text holds a whole copy only because a longer active value can still follow, mask that copy before the save. Keep the match of each such longer value as symbolic state, such as a reference and the count of its characters that already matched. Later text that completes a longer value must still be masked. The exact form of that state stays open, but it must add no raw text that can hold a whole copy of an active value. A raw rest of a longer value does not qualify, because it can contain a whole shorter value. Then no cleanup or value change can leave a whole copy, for any value source. Cost: it changes the shared record type `HeldOutput` and its encrypted format. The previous Worker must still read the new records after a rollback. A completed longer value can then show as two masks. Effort: Medium.
- **Left out:**
  - No change. A whole copy of an ended value stays and then shows, which breaks the lifetime rule.
  - Keep the ending value in the saved list until its held copy resolves. It keeps the value past its lifetime, which breaks the same rule.
  - Drop the held text at cleanup. It loses text of the answer, which the chat must show.
  - Hold no text across events. It breaks the rule that the filter hides a copy that two events of one answer split.
- **Wider fix:** C. No saved text can hold a whole copy raw, so no cleanup or value change can leave one.
