- **Reason:** the production D1 records and Worker logs are unread, because no read-only Cloudflare request was approved, and the check of the fix needs a deploy run after the merge.

- **Terms:**
  - **Software image:** one saved snapshot for each version of the app's own software. A first build of an org starts from it. `docs/protocol/software-image.md`, section "The software image", gives its rules.
  - **Poll request:** one request of the deploy step "Build software image" to `POST /v1/deploy/software-image` on `api.conductive.build`. Each request advances the build in the Worker.
  - **Attempt:** one row of the D1 table `software_images`, one build of one software version. Its phases are `create`, `allocating`, `software`, `journal`, `snapshot`, `publish`, `cleanup`, and `done`.
  - **Provider:** the sandbox provider, Boat. Its API creates, reads, and saves the cloud computers.
  - **Transient provider error:** a provider error of the kind `unavailable`, `invalid_response`, `conflict`, or `rate_limited`. The attempt keeps its phase, and a later request tries again.
- **Background:**
  - The deploy step. The fix did not change it.
    - Two different limits apply to the deploy step. The request limit is 30 seconds for each poll request. The total wait is 900 seconds, or 15 minutes, for all requests together. Near the end of the total wait, the last request gets only the seconds that remain.
    - The step waits 10 seconds after each answer or failed request, then sends the next one. A request with no answer within the request limit counts as a network error. The step then tries again.
    - The step also retries the HTTP statuses 409, 429, and 5xx. It prints a phase only when the phase changes.
    - When the total wait ends with no `ready` answer, the result of the step is `timeout`. The job "Check the software image result" then fails the run. The new Worker stays live.
  - The fix in the Worker, on 18 November 2026.
    - The user chose a fix in the Worker. These stay unchanged: `.github/workflows/deploy.yml`, the request limit, the total wait, the ready-image gate, the 30-minute window of the deploy token, and the 60-minute time limit of a build.
    - Each poll request gets a reply budget of 20 seconds. The budget starts before the token check, the release lookup, and the admission of the attempt.
    - At 20 seconds, the route answers with the attempt as the request last read it from D1, and the output that the request took from D1. While the token check, the release lookup, or admission still runs, it answers the retryable `503 service_unavailable`.
    - `ExecutionContext.waitUntil` keeps the work running after the answer. The work then starts no new release lookup or provider call. A call that already runs can end, and the work saves its result.
    - Each network call stops 45 seconds after the request starts, also a long journal command. Cloudflare keeps work for at most 30 seconds after the answer or a disconnect of the client, so about 5 seconds stay for D1 writes. The Cloudflare doc of `ctx.waitUntil()` gives this limit.
    - Saved progress. A slow call that succeeds after the answer keeps its result, so a later poll goes on from it:
      - Before its main provider call, a step can need the readiness read, the auto-stop update, or a snapshot lookup that finds no snapshot. The Worker saves each finished call in the D1 table `software_image_operations`, for the phase and revision of the attempt. A later poll skips it.
      - Each save of the attempt changes its revision, also a save by the previous Worker. The saved calls then no longer apply, and the next step starts again with the readiness read.
      - A transient provider error clears the saved calls. A call that the 45-second stop ends keeps them for the next poll.
      - After admission, each poll of the deploy finds its attempt in D1 and uses the release that the attempt saved. It then makes no release lookup. When admission reused an attempt of an earlier deploy, the table `software_image_deploys` links the token digest of the deploy to that attempt. Each link expires with the 30-minute window of the deploy token.
      - A linked attempt that failed under an earlier deploy goes through admission again, with the release that it saved. So a failed attempt still restarts only for another token digest, as before the fix. A failed attempt of the same deploy does not restart.
    - Saved output. Each command status saves its output offsets and its new output in one D1 batch. The output then waits in the table `software_image_output`. Before it answers, a deploy poll takes all waiting output of its attempt, with bounded D1 statements, one for each saved command status. The answer puts that output in the same `output` field as before. After its answer, a poll takes no output, so a later poll returns that output.
    - The Cron work saves output in the same way, but takes none. A later deploy poll of the same attempt returns it.
    - The Cron work deletes expired links and the saved calls of ended attempts. It also deletes the waiting output of an ended attempt that started more than 30 minutes ago and that no link names. Deleting an attempt deletes its rows in the three tables, through `ON DELETE CASCADE`.
    - The migration `migrations/202611181709_software_image_poll_progress.sql` adds the three tables. It changes no existing table, column, or phase name, so the previous Worker keeps working.
    - Limits that stay: the fix makes no exactly-once promise for output. The deploy log can miss output when an answer is lost, or when a poll takes output at its deadline. The attempt keeps the last 64 KiB of its output, and a failed attempt returns it as `keptOutput`.
    - The fix bounds the requests that get the full 30 seconds. The last request of the total wait can get less than 20 seconds, and can still end with no answer. The fix does not make the total wait longer.
    - A provider call that does not end within 45 seconds of the start of its poll cannot finish in any poll. A very slow journal command is an example. The Cron work has no such stop, so it can still advance the attempt.
    - Route tests use the local D1, the fake provider, fake timers, and captured event order. One test holds a provider create until its 30-second deadline. It expects the answer at 20 seconds, with the phase `allocating`.
    - Other route tests hold slow calls that succeed after 20 seconds: the readiness read, the auto-stop update, the command start and status, a snapshot lookup that finds no snapshot, and the release lookup. They expect later polls to go on from the saved state, and late output in a later answer. One of them also lets a reused attempt of an earlier deploy fail. It expects the next poll to start a new attempt.
    - History of the fix: its first version, commit `3ad7038e3`, refused each provider call after the answer. A step saved its progress only after its last call. So a readiness read or an auto-stop update that ended after the answer was lost. A late command status saved no output offset. Each poll also read the release before its first checkpoint. Review then found that slow calls that succeed could stall every poll, and that a release lookup over 20 seconds gave `503` on every poll. The saved progress and the saved output above replace that first version.
    - Nobody has checked the fix on the deployed Worker yet.
  - History: the route before the fix.
    - The route first looks up the newest release on `runner.conductive.build`. That lookup has no deadline of its own. Then `requestSoftwareImage` advances the attempt step by step in the same request.
    - The request stops only when a step waits, a transient provider error stops it, or the attempt ends. Only then does the route answer. No deadline covers the whole request.
    - A provider call that passed its deadline failed with a transient provider error. The route then answered with the current phase.
    - In the phase `allocating`, the request saves the attempt in D1, then awaits the create of the sandbox. After a create succeeds, the same request saves the sandbox ID. It then goes on to the phase `software` and reads the state of the sandbox.
    - Proved by the code: the request limit of the step equals the deadline of one provider call. The step starts its 30 seconds before the Worker starts a provider call. So a provider call that uses its full deadline always ends after the step stopped waiting.
    - Also proved by the code: one slow provider call, plus the release lookup, the D1 work, and the answer, can pass the request limit. Several provider calls in one request can pass it too. The step then sees no phase and no error.
  - Still true after the fix.
    - The Worker gives each provider call 30 seconds. Only the operations `command` and `readFile` get more. A call that passes its deadline fails with a transient provider error.
    - In the phase `snapshot`, each request asks the provider to save the snapshot, or reads the saved snapshot. It answers `snapshot` until the provider reports the snapshot as ready. The snapshot step itself adds no output.
    - Allocation is bounded, because each provider call ends after its deadline. Repeated requests are safe. The create uses the idempotency key `software-image-<attempt ID>`, and the attempt row is saved before each create.
    - The D1 writes of an attempt are guarded by phase and revision. Cleanup finds a lost create through the same key. No evidence shows a duplicate or a leaked sandbox.
    - The Cron trigger also advances an unfinished attempt every 15 minutes. A newer deploy run ends an unfinished attempt of an older version.
