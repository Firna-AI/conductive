# Keep the account data of an open tab current through one guarded source

- **Severity:** Medium. **Likelihood:** Rare. **Effort:** Medium. **Confidence:** High. **Harder later:** No.
- **Kind:** Fix after merge.
- **Added:** 2026-11-11, the wider fix of finding 44 of review round 1 on branch `calummoore/cli-proxy-setup`, which fixed the reported case for own endpoint model lists. Finding 106 of review round 2 merged into it. Extended on 2026-11-18 with findings 1 and 2 of review round 1 on branch `calummoore/follow-up-account-login-status-owner-om90`, and with two more races that the checks of those findings reproduced. Their options keep their meaning under the letters of this item: option B of both findings is part of B, option A of finding 1 is F, option A of finding 2 is G, option C of finding 2 is H, option C of finding 1 is I, and option D of both findings is J.
- **Location:** `observe` at `src/app/account-login-reads.ts:74-92`, `readAgent` at `:121-131`, `start` at `:134-147`, `read` at `:149-157`, and `follow` at `:197-219`. `invalidateReads` at `src/app/agent-logins.ts:70-72`, `putReply` at `:84-86`, and `mark` at `:96-108`. `readDefaults` at `src/app/account-login-writes.ts:82-87`, `orgLoginChanged` at `:97-101`, `refreshModels` at `:140-155`, and `setNoReuse` at `:167-178`. `contradictsLogin` at `src/app/login-observation.ts:31-55`. `followSources` at `src/chat/state/sources.ts:69-104`. `refuseOperator` at `src/app/account-model.ts:152-155`, `setDefaultChoice` at `:244-253`, `setNewWorkspaceView` at `:255-264`, and `saveShortcuts` at `:272-285`. `Resource` in `src/app/resource.ts` and `Refresher` in `src/app/refresh.ts`.
- **Reason:** Each remaining race needs a session fact during another account request, and a page return repairs it. The order of the login requests now keeps two account replies from showing in reverse order.

- **Source:** Review. **Category:** Product bug.
- **Terms:**
  - **Account data:** the reply of `GET /api/account` that `AccountModel` keeps: agent logins, default logins, default model, New workspace view, shortcuts, and operator role of the user.
  - **Own endpoint login:** an agent login that sends the model requests of an agent to a gateway or a proxy that the user chose, with the user's key. The Worker reads the endpoint's model list in the background, and the account data names the app models that the list does not name.
  - **Login data:** the agent logins and the default logins, which name the login that a new session takes for each org and agent.
  - **Session fact:** the login state that one session record gives, which the workspace chat reports through `AccountModel.observeLogin`, and which the code calls an observation.
  - **Mark:** two counters of each agent that `AgentLogins.mark` copies before a read: local login changes, and session facts that make older reads old.
- **Background:**
  - The browser reads the account data at boot and after its own writes.
  - The own endpoint change added a read of the logins each time the page becomes visible again, and once a minute while the account has an own endpoint login and the page shows. That direct fix reads only the login data.
  - Today `AccountLoginReads` in `src/app/account-login-reads.ts` owns every read of the login data after the app opens. It reads at each open of the Agents list, at each return to the visible page, after each local change of a login, and when an org joins the orgs of the user. It also reads after a session fact that contradicts the cached login data, and when a missing-login notice appears.
  - Its timer reads once a minute while the page shows and one reason holds. The reasons are an own endpoint login, an org login in use as `orgLoginsInUse` in `src/app/default-logins.ts` says, and a shown missing-login notice. `modelListWait` in `src/app/endpoint-models.ts` gives the wait. A hidden page stops the timer. When the page shows again, the owner reads once and resumes.
  - Each read shows the login data of its reply only for each agent whose mark still holds. A save, a remove, a connected sign-in, a share change, an org login change, and an org join each count as a local change. So a read never undoes a newer save, removal, or share change of this tab.
  - The default logins change only through a complete account reply. The agent logins also change through the reply of a login write of this tab. A session fact writes neither. It only makes older reads old, or starts a read. The screens show the default login that the server names, and do not work it out, as "The default login" in `docs/protocol/org-logins.md` says.
  - The workspace chat reports the session fact of each session record through `followSources` in `src/chat/state/sources.ts`. The key of a fact includes its record. `observe` accepts a fact unless it repeats the same state of the same record, or names the personal login of another member.
  - An accepted fact that says a login cannot serve, or that contradicts the cached login data, moves the fact counter of its agent. So every older mark of that agent is old. Only a contradicting fact starts a new read.
  - `AgentLogins.putReply` shows a share reply while no later local change of its agent came first. A session fact is not a local change, so a fact keeps a pending share reply.
  - The record of an own empty session can say that no login serves. That session takes the default login of the account only after a complete reply that names the default logins shows after its fact. `AgentLogins.readVersion` counts such replies for each agent.
  - `start` takes the mark of a whole-account read at once, before the read waits for its turn. `AccountLoginRequests` in `src/app/account-login-requests.ts` runs that read after the earlier login requests of both agents. Each later login request or read waits until it ends. A save, a remove, a share change, and an org login change count their change at once, also while they wait for their turn. `readAgent` runs in the turn of its caller, sends its GET with the mark of its caller, and shows only the agent of that caller. No rule compares two replies.
  - `refreshModels` in `src/app/account-login-writes.ts` takes its mark before the POST of Refresh. So a login change during Refresh blocks the later GET of Refresh. That GET starts only after the POST answers.
  - A repair read is an account read that a newer state needs, so that a reply newer than that state shows. Examples are the read after a local change, after a contradicting fact, after the POST of Refresh, and when a notice appears.
  - `Resource` in `src/app/resource.ts` numbers each read when it starts, and drops an answer older than the shown answer. Its answer replaces the whole value. `Refresher` in `src/app/refresh.ts` shares one read, reads at each return to the page, and keeps a timer, but it has no visibility rule.
  - `createApiClient` in `src/app/api/client.ts` sets no time limit on a request. So one GET can stay open for a long time.
  - Before the session-fact reads of 2026-11-18, only an org join started a second whole read while one ran. It counted a change of every agent first, so the older read showed nothing.
  - A change of the default model, the New workspace view, or the operator role in another tab or on another device still shows only after a reload. The same holds for the shortcuts.
  - `setDefaultChoice`, `setNewWorkspaceView`, and `refuseOperator` set the account with no guard. `saveShortcuts` does too. A repeated read of the whole account that answers after one of them would put the old value back. Commit `ec33f56b` fixed this class for kept chats.
  - **Late read after Refresh:** Resolved by the order of the login requests. Refresh now waits until an earlier account read ends, and a read that starts during Refresh waits until Refresh ends. The rest of this point records the race before that order. Refresh is not a local change. It asks the Worker to read the endpoint's model list again, then reads the account. A timed or focus read that started before Refresh and answers after it puts the older model list and its time back. Another read or a reload restores the new list.
  - **Share change during Refresh:** Resolved by the order of the login requests. The share change still counts at once, so the read of Refresh shows nothing of its agent. Its PATCH and its read now follow Refresh, so they carry the new list. The rest of this point records the race before that order: a share change during a Refresh also drops the Refresh's read, and the share reply can carry the list from before the Refresh.
  - **Late reply for another agent:** Resolved by the order of the login requests. A whole-account read now waits until an older one ends, so two whole-account replies cannot show in reverse order. The rest of this point is historical evidence from before that order: an older reply puts back the login data of an agent that a newer reply already showed. A check reproduced it on 2026-11-18, in memory, with the real `AppModel`, the fake API of the tests, and held replies:
    1. A read of a return to the page starts, and its answer waits. The server gives a usable Codex login, and the own login as the Codex default.
    2. The server changes to a Codex login with `unusableCause: refresh_denied`, and the org login as the Codex default.
    3. A session fact says that the Claude org login serves. The cached Claude default names no login, so the fact contradicts it and starts a second read.
    4. The second read shows the org default and the cause `refresh_denied` for Codex.
    5. The older answer then shows. The Codex default goes back to the own login, and the cause goes away. The fact moved only the Claude counter, so the older mark still held for Codex.
  - **Recovery fact:** a fact that says a login serves again stops no older read when the cache also says that it serves. A check reproduced it on 2026-11-18, in the same way:
    1. The chat starts. The personal Codex login serves, and the Codex default is that login.
    2. The server fails the login, with the org login as the fallback. A record with `loginAvailable: false` contradicts the cache and starts a read. Its answer waits.
    3. The server recovers. The same record now says `loginAvailable: true`. That agrees with the cache, so the fact starts no read and makes no read old.
    4. The held answer shows. The cache gets `unusableCause: refresh_denied`, and the Codex default of the org becomes the org login.
    5. With the org fallback, the next timer read repaired the cache. Without an org fallback, the default became none, and one timer period read nothing. Only another account read repaired it.
  - **Dropped repair read:** a fact that says a login cannot serve, and that agrees with the cache, makes a repair read old and starts no read. A check reproduced it on 2026-11-18, in the same way:
    1. The cached Codex login has failed, and no Codex login serves the user.
    2. An admin connects a Codex org login in this tab. `orgLoginChanged` counts a change and starts a repair read. Its answer waits.
    3. A record says that the personal Codex login cannot serve. That agrees with the cache, so the fact makes the repair read old and starts no read.
    4. The repair answer names the org login as the default, but it shows nothing. The default stays none, and no timer reason holds.
    5. Only a return to the page or an open of the Agents list repaired it. In a second run, the cache named the org default, and the admin removed the org login. The stale org default stayed until the next timer read.
  - **Fact during the Refresh POST:** a fact that says a login cannot serve, sent during the POST of Refresh, drops the read of Refresh. A check reproduced it on 2026-11-18, in the same way:
    1. The user presses Refresh on an own Codex endpoint login. `refreshModels` takes its mark, and the POST waits.
    2. A record says that a Codex login cannot serve. The fact moves the fact counter of Codex.
    3. The POST answers. The GET of Refresh starts after the fact, and its answer holds the new model list.
    4. The answer shows nothing for Codex, because the mark of Refresh is older than the fact. The older list stays until the next read.
  - No observation regression covers two agents. Each fact test in `src/app/account-login-observations.test.ts` reports a Codex fact.
  - The test "a Refresh of an own endpoint shows its new list before a queued page-return read" in `src/app/account-login-refresh.test.ts` now covers the order of the login requests. A page-return read that starts while the POST of Refresh waits sends its GET only after Refresh ends. Both reads show the new list, and no older list shows during the POST.
  - The mixed empty-session test is "an empty session excludes cached own and org defaults until a newer complete account reply confirms the org default" in `src/app/account-empty-login.test.ts`. It has two empty sessions of the user. One record says that no login serves, and the other says that a login serves.
  - A later save in that test reads the account again. So the test still passes when each fact that says a login serves makes older reads old and starts no read in their place. Without that save, the view stays missing, although the server names the org login.
  - With a read in place of each dropped read and no batching, that test sees 3 reads, and the cached-own case shows the org login before the save.
- **Problem:**
  - Only the login data of the account data follows changes that the tab did not make. The default model, the New workspace view, the shortcuts, and the operator role do not.
  - The order of the login requests now keeps the account replies in order. So an older reply no longer puts back an older model list after Refresh, or older login data of another agent.
  - The session facts order the replies only in part. A fact that agrees with the cache stops no older reply, also when that reply contradicts the fact. A fact that says a login cannot serve also makes old a read whose GET starts after it, or a repair read, and starts no read in their place.
- **Impact if no action:** A model that Refresh brought back can stay missing from the pickers until the next read. The default model, the New workspace view, the shortcuts, and the operator role can stay stale in an open tab until a reload. The views can show a failed login as usable, a recovered login as failed, the wrong default login, or a Connect notice for a member whom the org login serves. That lasts until a return to the page, an open of the Agents list, a reload, or a timer read while a timer reason holds.
- **Root question:** How does an open tab follow each change of the account data that it did not make, with no older reply that undoes a newer write, a newer reply, or a newer session fact?
- **Options:**
  - **A.** Keep the read of the logins only. It keeps every race and every stale field above. Effort: Small.
  - **B.** Give the account data one guarded source, with one order for every account GET and every accepted session fact. Effort: Medium.
    - Read the whole account through the existing `Refresher`. It needs a visibility rule, as the **Related** line says. Keep every current read trigger and every timer reason: own endpoint logins, org logins in use, and shown missing-login notices. Keep the rule that no timed read runs while the page is hidden.
    - Put every write of the other fields through `Resource.write`, with a commit that sets only the fields of its own answer. These writes are `setDefaultChoice`, `setNewWorkspaceView`, `saveShortcuts`, and `refuseOperator`.
    - Give each GET of `read` and of `readAgent` an order number when the GET starts, apart from the mark of its caller. Give each accepted session fact a place in the same order.
    - Show the login data of an agent from a reply only when no newer reply already showed that agent, and no accepted fact of that agent came after the GET started.
    - Keep the local-change counter in the mark of the caller. So `putReply` still shows a pending share reply, and the mark from before the POST of Refresh still blocks a login that changed during Refresh.
    - When a fact makes a repair read old, start one read in its place, or batch the facts before the next GET. B can take the content check of H instead. Then a fact makes old only the data that contradicts it, and B needs no batching.
    - Keep the record in the key of each fact, the rule that only complete account replies change the default logins, and the rule that an own empty session waits for a newer complete reply.
    - Add a regression with held replies for each race above, except the share change during Refresh. Hold the repair reply of the mixed empty-session regression with no later save. Keep the test of the mark from before the POST green.
    - B keeps the local-change guard, which can still drop the read of Refresh after a share change. D also orders that case.
  - **D.** Order each model list by the Worker's stamps: a reply sets the model list of a shown login only when its `updatedAt` is the same and its `modelList.checkedAt` is newer, and a list counts as newer than no list. The Worker lets only the newest list read save, so `checkedAt` only grows. It fixes the share change during a Refresh too. Cost: it orders only the model list. Effort: Small.
  - **E.** Make the Refresh and save routes answer the login with its model list, as the share route does, and remove the account read after them. Cost: a change of the Worker routes, the shared types, the dev routes, and their tests. Effort: Medium.
  - **F.** Number the GETs of `read` when they start, and drop an older whole reply after a newer one showed. Add the regression of the late reply for another agent. It leaves the order of `readAgent` apart, so the late read after Refresh stays. It does not change how the facts order the replies. Effort: Small.
  - **G.** Make each newly accepted fact that says a login serves make the older reads of its agent old too. Number each GET when it starts, apart from the mark of its caller. Start a read in place of each repair read that a fact makes old, or batch the facts before the next GET. Add the held regression of the recovery fact, and the mixed empty-session regression with no later save. Effort: Small.
    - Without the GET number, such a fact during the POST of Refresh drops the read of Refresh. A check saw the older list stay. The first records of a newly opened workspace chat are such facts.
    - With the number, the batching, and the new reads, G comes close to the effort of B. It does not order two replies.
  - **H.** Number each GET when it starts, apart from the mark of its caller. Before a reply shows, drop the data of each agent that a later accepted fact contradicts. `contradictsLogin` in `src/app/login-observation.ts` can check the reply. Then start one repair read, unless a read that started after the fact is open. Add the held regression of the recovery fact. Effort: Small.
    - A fact that agrees with the reply drops nothing. So the mixed empty-session case needs no batching, and a read of Refresh that starts after a fact still shows.
    - H does not order two replies, so the late reply for another agent and the late read after Refresh stay.
  - **I.** Send the account GETs one at a time through one reader, and batch the facts before the next GET. Keep the local-change guards apart. A slow older request delays each recovery. The client sets no time limit, so one GET that never answers blocks every later read. Effort: Medium.
  - **J.** Order the replies by the server, with a login revision that the Worker adds to each account reply. Effort: Large.
    - The revision grows at each write of a personal login, an org login, a switch, and a membership. A read time is not enough, because separate Worker instances have separate clocks.
    - The tab shows the data of an agent only when its revision is not older than the newest that it showed. It keeps the local-change marks.
    - Put the same revision in each session record, so that a fact gets the same order. Without it, the facts still need the order of B.
    - J also orders two GETs that the Worker answers in the other order.
    - Cost: a change of the account API, the generated `Session` type, the protocol docs, the dev fake, the tests, and probably the D1 schema. It adds a requirement at a boundary, so only the user can choose it.
- **Left out:**
  - A push of account changes on the workspace socket, because it reaches only tabs of that workspace, and its events go into the history that every member reads.
  - An event stream of login changes alone, because each pushed change is one more fact that needs an order against the open replies.
  - The local-change counters alone, because two reads that overlap then get the same permission to show.
  - Count each shown reply as a local change. It orders the replies, but `putReply` then drops a pending share reply. B gives the same order without that loss.
  - A Worker route that reads one agent, because it adds a boundary, and B covers the same cases and the older `readAgent` cases without a new route.
  - Move the login data onto `Resource` alone. Its answer replaces the whole value, so the marks of each agent and the order of the facts are still needed. Its `confirm` overlay also breaks the rule that only complete account replies change the default logins. B keeps `Resource` for the other fields.
  - A login overlay from a fact, because the screens must show the default login that the server names, and must not work it out.
  - Facts that make reads old with no read in their place, because they drop the repair read of the mixed empty-session case.
  - A check after an older reply shows, with one more read, because the recovered login then shows as failed for the time of one read. H prevents that at the same effort.
- **Wider fix:** B. One guarded source keeps every field current, and one order covers every account GET and every session fact. B stays the wider fix while one helper sends every account GET of the owner. A read path that calls `api.get` directly would skip that order.
