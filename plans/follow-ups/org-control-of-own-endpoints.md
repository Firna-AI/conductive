# Org admins cannot see or limit personal endpoints

- **Severity:** Low. **Effort:** Medium. **Confidence:** Medium. **Harder later:** No.
- **Kind:** Outside the scope.
- **Added:** 2026-11-09, from the options check of decisions 5 to 7 of the own endpoint plan on branch `calummoore/cli-proxy-setup`.
- **Location:** "Agent logins" in `docs/protocol/tokens-and-secrets.md`, `docs/protocol/org-logins.md`, `docs/protocol/model-gateway.md`, and the org settings under `src/shell/settings/`.
- **Reason:** the own endpoint change gives each member a personal login kind, and a rule for org admins is new behaviour that the user must choose.

- **Terms:**
  - **Own endpoint login:** an agent login that holds the address of a gateway or a proxy, and its key. A turn on it sends the messages and the files of the turn to that endpoint.
  - **Personal endpoint:** an own endpoint login that a member connects on their own account page. It serves all of that member's orgs.
  - **Org login:** an API key or an own endpoint login that an admin connects for one agent of an org, on the Agents tab of the org settings. `docs/protocol/org-logins.md` states its rules.
  - **Use for every member:** the switch under each org login. While it is on, each new session in the org takes the org login, also for a member with a login of their own.
  - **Org admin:** a member who can change the shared settings of an org, such as its scripts, its env vars, and its org logins.
- **Background:**
  - The own endpoint plan adds the own endpoint login on 8 November 2026. Each member saves it on their own account page, and it serves all of that member's orgs.
  - A turn on an own endpoint login sends the messages and the files of the turn to that endpoint. The repository code of the org can be in those files.
  - A new personal endpoint is shared by default (choice of 9 November 2026). So the turns of other members can also go to it.
  - On 16 November 2026 the user chose an org login for each agent. An admin connects it, also as an own endpoint. So an admin can send the code of the org to a server that the org chose.
  - On the same day the user chose the switch "Use for every member". It starts off. While it is off, a member's own login comes first, and the org login serves only the members without a usable login of their own.
  - While the switch is on, each new session in the org takes the org login. Older sessions keep their login, also a personal endpoint. While the org login cannot be used, the member's own login serves.
  - So a personal endpoint can still get the code of the org: in older sessions, in every session while the switch is off, and while the org login cannot be used.
  - No rule lets an org admin see which personal endpoints receive the code of the org, or limit them. The org login change left out an admin list of allowed endpoint hosts for personal logins, and kept this item for it.
- **Problem:** An org cannot fully control where its code goes when a member uses a personal endpoint. The switch "Use for every member" covers only new sessions.
- **Impact if no action:** An org with rules about where code may go cannot enforce them in the app for older sessions, or while the switch is off.
- **Root question:** How does an org learn, or limit, which servers receive its code through personal endpoints?
- **Options:**
  - **A.** State in the protocol that an org admin cannot see or limit personal endpoints, and that the switch "Use for every member" covers only new sessions. Effort: Small.
  - **B.** An org setting that turns personal endpoints off for the turns of that org. Cost: a setting, its check at each turn, and a mockup state. Effort: Medium.
  - **C.** An org list of allowed endpoint hosts. Turns on other hosts are refused in that org. Cost: as B, plus a host list to manage. Effort: Medium.
  - **D.** Show org admins the hosts of the personal endpoints that the org's turns used. Cost: a new record of hosts for each org. Effort: Medium.
- **Left out:** A rule for API keys and subscription tokens too. Those logins send code only to Anthropic or OpenAI, so they do not raise this question.
- **Wider fix:** None.
- **Previous examples:** The switch "Use for every member" of the org logins, chosen on 16 November 2026, controls the login of new sessions only.
- **Recommendation:** A now. The switch already lets an admin send the new sessions of the org to the org login, so a statement of the rest of the gap costs little. B or C can follow when an org asks for control.
- **Action:** ask the user, because each option sets new behaviour for orgs that no requirement covers.
