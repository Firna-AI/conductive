# One failed save stops later runner events

- **Severity:** High. **Likelihood:** Rare. **Effort:** Small. **Confidence:** High. **Harder later:** No.
- **Kind:** Fix after merge.
- **Added:** 2026-11-06, from PR #12, branch `conductor/boat-native-remote-workspaces-milestone-7r`, two new problems of the round 2 check of finding 9.
- **Location:** `EventStore.save` in `runner/src/state.ts:154`, and `Runner.emit` in `runner/src/runner.ts:112`.
- **Reason:** on 6 November 2026 the owner told the branch that built the runner to record this note with no fix and no storage recovery rule.

- **Terms:**
  - **Runner:** the agent runner, the Node program in `runner/` that runs the agents in a cloud computer and reports to the workspace Durable Object.
  - **State file:** the JSON file of `EventStore` in `runner/src/state.ts`. It holds the unconfirmed events, the event counter, and the conversation references.
  - **Chain:** a field that holds the last pending promise, so that each new step waits for the step before it.
- **Background:**
  - `EventStore` saves the whole state for each append, confirm, and session record. `save` chains each write after the one before, through the field `writes`.
  - `append`, `confirm`, and `remember` change the state in memory before they save it. Other code sees only the last state that a write saved.
  - `Runner.emit` chains each event after the one before, through the field `emitted`. One call can save more than one event, because the output filter can release held text first.
  - The runner sends an event only after its save. The workspace answers a gap in the event numbers with a resend from the first missing number.
  - Commit `5a22dd5` made the store show only saved state, so a resend cannot send an unsaved event. That fix stays in force.
  - `AgentEngine.enqueue`, `RunnerLink.enqueue`, and `FileReporter.refresh` already continue their chains after a failure.
- **Problem:**
  - When one write fails, `writes` keeps the rejected promise. Each later save then rejects with no write, so each later append, confirm, and welcome fails until the process restarts.
  - When one save in `Runner.emit` fails, `emitted` keeps the rejected promise. Each later event then stops before it reaches the store, also after the disk works again.
  - A probe with memory storage showed the first part. After one failed write, the next append failed although the storage worked again, and a reconnect then published nothing. A read of the code shows the second part.
- **Impact if no action:** One short disk error, such as a full disk, stops the chat and the file lists until the runner restarts. Each welcome fails, so the runner connects again each second.
- **Root question:** After one save fails, how do later saves and events work again without a restart?
- **Options:**
  - **A.** Let each chain continue after a failure. The failed call still rejects for its own caller. A later save writes the whole state, so it also saves the changes of the failed call, and the resend rules then deliver its event. `Runner.emit` gives each part of one event to the store, also after an earlier part failed. Effort: Small.
  - **B.** As A, and the store tries a failed save again after a short wait, until a save works. The event of a failed save then does not wait for the next change of the state. This adds a retry timer. Effort: Small.
  - **C.** Exit the runner process after a failed write, so that systemd starts it again from the last saved state. Each running turn and agent process is lost, and a lasting disk error repeats the restart. Effort: Small.
- **Left out:**
  - Change nothing: it fails the goal, because only a restart recovers.
  - Undo the change in memory of a failed call: later calls can already hold the next event numbers. The saved outbox must stay without gaps.
- **Wider fix:** A, through one small serial queue that both chains use. No chain of the runner can then keep a rejection.
- **Previous examples:** None found.
- **Related:** `plans/follow-ups/runner-file-and-save-errors.md`, same code. That item decides what a turn or a connect reports when one of its steps fails, a save included. This item only makes later saves and events work again. A failed save can end its turn only after this item is fixed.
- **Recommendation:** A. It restores later saves and events, and it adds no new rule at the runner boundary.
- **Action:** fix after merge, apply A, because on 6 November 2026 the owner told the branch that built the runner to record this note without a fix.
