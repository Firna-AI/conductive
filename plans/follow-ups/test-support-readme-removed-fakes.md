# Test-support README lists two removed fakes

- **Severity:** Low. **Effort:** Small. **Confidence:** High. **Harder later:** No.
- **Kind:** Outside the scope.
- **Added:** 2026-11-19, from the docs pass of branch `calummoore/follow-up-worker-tests-leave-storage-2sof`.
- **Location:** `worker/test-support/README.md:214` and `worker/test-support/README.md:215`, the **Key code** entries of `fake-durable-object.ts` and `fake-runner-files.ts`.
- **Reason:** The entries were wrong on `main` before that branch, and that branch changes only where the test fixture folders live.

- **Terms:**
  - **Key code:** the list of entry points at the end of `worker/test-support/README.md`. Each entry names a file of the folder and says what it does.
  - **Native workspace harness:** the test runtime that `createHarness` in `worker/test-support/harness.ts` starts. It runs the production workspace object in Miniflare, with native SQLite.
- **Background:**
  - The **Key code** list says that `fake-durable-object.ts` "supplies the workspace endpoint without Cloudflare". It says that `fake-runner-files.ts` "joins valid file report parts for the endpoint".
  - Neither file is in the repository. Commit `a20746b99`, "feat: Rust sandbox software that updates itself (#342)", deleted both on 2026-11-16.
  - `fake-durable-object.ts` held `FakeDurableObject`, an in-memory workspace endpoint for runner tests. `fake-runner-files.ts` held `FakeRunnerFileReports`, which joined the parts of each runner file report for that endpoint.
  - The same commit rewrote the README paragraph about that endpoint. The paragraph now says that tests of the production workspace object check validation, ordering, storage, replay, and masking. The commit left the two **Key code** entries.
  - Commits `1f19917dc` and `d46c855ae` added the two entries on 2026-11-06.
  - On 2026-11-19, no code, configuration, or other doc names `FakeDurableObject`, `FakeRunnerFileReports`, `fake-durable-object`, or `fake-runner-files`. Every other **Key code** entry names a file that exists.
  - Tests now reach the production workspace object through the native workspace harness, with `harness.native.actor(name)`. `native-runtime.ts` owns these objects and their fake outbound fetch path. `native-workspace-entry.ts` adds test controls around the production constructor.
  - The top of the README describes both of these files, but **Key code** has no entry for them.
  - The production class `RunnerFileReports` in `worker/files/runner-reports.ts` now joins the parts of each runner file report. The README already names `recordedMultipartRunnerFileEvents` in `src/test-support/recorded-files.ts`, the multipart samples of its checks.
- **Problem:** Two **Key code** entries name files that do not exist. The work that they describe now belongs to the native workspace harness and to production code.
- **Impact if no action:** A reader who opens these entry points finds no file, and can lose time on a search or think that a fake is missing. The list also leaves out the native harness files that took over the work.
- **Root question:** How does the **Key code** list of the test-support README point readers to the test entry points that exist?
- **Options:**
  - **A.** Delete the two entries. The list then names only files that exist, but it still has no entry for the native harness files. Effort: Small.
  - **B.** Replace the entry of `fake-durable-object.ts` with entries for `native-runtime.ts` and `native-workspace-entry.ts`, the current native test-support entry points. Delete the entry of `fake-runner-files.ts`, because production code now joins the parts and the README already names the samples. Effort: Small.
- **Left out:**
  - Only two approaches are real, because each wrong entry can only go or point to its replacement.
  - Change nothing. It fails the goal, because the wrong entries stay.
  - A check that fails when a **Key code** entry names a missing file. Such a check is a new gate, which needs the user's approval. A and B remove the wrong entries without one.
  - A review of every other entry. Each one names a file that exists, as the search of 2026-11-19 shows.
- **Wider fix:** None. The repository rules already require a search of every `README.md` for the name of a deleted file, in the same change. Commit `a20746b99` missed that search for these two names.
- **Previous examples:** `plans/follow-ups/files-readme-broken-anchor.md`, a README link to a missing heading. `plans/follow-ups/mockups-readme-wrong-catalogue-pages.md`, a README list that names wrong pages.
- **Recommendation:** B. It removes the wrong entries and points readers to the files that now do the work.
