# A Mac app change of an install returns to the web app

- **Severity:** Low. **Likelihood:** Common. **Effort:** Medium. **Confidence:** Medium. **Harder later:** No.
- **Kind:** Outside the scope.
- **Added:** 2026-11-10, from `calummoore/manage-access-redirect`, found while that branch fixed the browser return after Manage access.
- **Location:** `src/shell/account/githubInstall.ts:13`, `src/shared/github-setup.ts:37`, `worker/github-setup.ts:94`, `desktop/src/navigation.ts:74`.
- **Reason:** The fix needs a new exception in the Mac app's navigation rules and a new Mac app build, which the browser fix of that branch does not touch.

- **Terms:**
  - **`state`:** a value that the app adds to the install link of the GitHub App. GitHub gives it back to the Setup URL after a new install.
  - **Setup URL:** `/github/setup` on the app hostname, where GitHub sends the browser after an install or a change of the GitHub App.
  - **Start address:** `/github/install?from=<screen>` on the app hostname. The Worker keeps the screen in the return cookie of the browser, then sends the browser to GitHub.
  - **Mac page:** the page that the Setup URL shows for `state=mac`. It tells the person to go back to the Mac app.
- **Background:**
  - The Mac app opens every GitHub link in the person's default browser. The browser does not share the cookie store of the Mac app.
  - In the Mac app, Install the GitHub App, Manage on GitHub, and Manage access link straight to the install page of the GitHub App, with `state=mac`. `useGitHubInstallLink` in `src/shell/account/githubInstall.ts` and `githubInstallLink` in `src/shared/github-setup.ts` build these links.
  - In a browser, the same links go to the start address. The return cookie carries the screen through GitHub, so the browser comes back to the screen where it started.
  - `githubSetupResponse` in `worker/github-setup.ts` shows the Mac page when `state` is `mac`. Otherwise it sends the browser to the screen of the return cookie, or to Home.
  - GitHub drops `state` when the person changes an install that exists, for example with Configure and then Save on the GitHub page. Reports in the GitHub community from March 2025 and June 2025 describe this, and GitHub has not answered them.
  - `docs/protocol/desktop-sign-in.md`, section "GitHub App install", says: "After the install, the browser shows a page that tells the user to go back to the Mac app." `docs/protocol/github-banner.md` says that the Mac app has its own return.
  - The Mac app reads the installs again when its window gets the focus, so it shows the change when the person comes back to it.
  - `docs/protocol/desktop-app.md`, section "Navigation", says: "A link to a page of the app hostname opens that page in the window, from the desktop origin." `navigationTarget` in `desktop/src/navigation.ts` loads such a link in the window. It drops a request for a new window to the app hostname.
- **Problem:**
  - A person changes the repositories of an existing install from the Mac app, and saves on GitHub.
  - GitHub sends the browser to the Setup URL without `state`. The browser has no return cookie, because the Mac link did not pass the start address.
  - So the browser opens the web app's Home, not the Mac page. A browser without a sign-in shows the sign-in page.
- **Impact if no action:** The person sees the web app, maybe its sign-in page, in the browser. The person may not know to go back to the Mac app, though the Mac app shows the change there.
- **Root question:** After a change of an install that starts in the Mac app, how does the browser learn that it should show the Mac page?
- **Options:**
  - **A.** The Mac app opens the start address in the default browser, with a Mac marker in place of a screen. The Worker keeps the marker in the return cookie of the browser, and the Setup URL shows the Mac page for it. This adds an exception to the navigation rule of the Mac app for the start address, as the launch address of a port preview has. It needs a new Mac app build, Worker and desktop tests, and a protocol doc change. Effort: Medium.
  - **B.** Change nothing. The person switches back to the Mac app, which reads the installs on focus. Effort: Small.
- **Left out:**
  - Show the Mac page for each return without `state` and without a return cookie: a browser whose cookie expired would then show the Mac page, which is wrong there.
  - A `conductive://` address that opens the Mac app after the return: `docs/protocol/desktop-sign-in.md` rejects it, because the Mac app accepts only the address of its sign-in.
- **Wider fix:** A. It gives the Mac app the same start as a browser, so every install or change returns to the right place.
- **Previous examples:** The browser return had the same cause: Manage access and every change of an install opened Home, until `calummoore/manage-access-redirect` added the start address and the return cookie.
- **Recommendation:** A. It meets the protocol rule for the Mac return also after a change, with the mechanism that browsers already use.
- **Action:** ask the user, because option A changes the protocol rule that a link to the app hostname opens in the window of the Mac app.
