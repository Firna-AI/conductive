# Tabs show Sandbox stopped while their Resume runs

- **Severity:** Medium. **Likelihood:** Common. **Effort:** Small. **Confidence:** High. **Harder later:** No.
- **Kind:** Needs decision.
- **Added:** 2026-11-25, from branch `calummoore/skill-widget-tab-page-dtzl` (skill tabs), review round 1, the wider fix of finding 61 and of its repeat, finding 42. It also holds a later review line on `src/shell/workspace/files/files-features.tsx:70`.
- **Location:** `src/shell/workspace/sandbox-view.ts:44-49` (`contentState`), `src/shell/workspace/files/page-placeholder.tsx:13-24`, `src/shell/workspace/files/files-features.tsx:70` and `:122`, `src/shell/workspace/previews/preview-centre.tsx:117`, `src/shell/workspace/WorkspaceScreen.tsx:183`, `src/shell/workspace/WorkspaceHeader.tsx:72`, `src/shell/workspace/files/tab-open-resume.tsx:31-37`, `docs/protocol/stop-and-resume.md:55-82`.
- **Reason:** The recommended fix changes how the tabs on `origin/main` show a start and a pressed Resume, so the user decides.

- **Source:** Review. **Category:** Product bug.
- **Terms:**
  - **Open Resume:** the Resume that the open of a stopped workspace sends. While it runs, `resumingAtOpen` of the workspace context is true.
  - **Tab-open Resume:** the Resume that `ResumeOnTabOpen` in `src/shell/workspace/files/tab-open-resume.tsx` sends when a visit opens a file, diff, Preview, or skill tab in a stopped workspace.
  - **`resume.pending`:** the flag of the Resume action of the workspace context. It is true while any Resume request runs: a tab-open Resume, or a press on Resume.
  - **`contentState`:** the helper in `src/shell/workspace/sandbox-view.ts:44-49` that says what a part shows in place of its content. It gives the wait of a start or the panel of the sandbox state.
- **Background:**
  - While the open Resume runs, the header shows Starting. The tools and each tab without content show "Waiting for the sandbox", with no Resume (`docs/protocol/stop-and-resume.md:55-64`).
  - The open of a file, diff, or skill tab in an open, stopped workspace also resumes the sandbox (`docs/protocol/stop-and-resume.md:74-82`). The user chose this for file and diff tabs on 10 November 2026 (decision 247). A Preview tab does the same (`tab-open-resume.tsx:4-12`).
  - The header reads only `resumingAtOpen` (`src/shell/workspace/WorkspaceHeader.tsx:72`). So does `contentState`.
  - Four parts call `contentState`:
    - the page of a file, diff, or skill tab, through `pagePlaceholder` (`page-placeholder.tsx:14`), which the file and diff tabs use at `files-features.tsx:70`
    - the wait of a file list (`files-features.tsx:122`)
    - the Preview tab (`preview-centre.tsx:117`)
    - the tools (`WorkspaceScreen.tsx:183`)
  - The page of a tab draws the panel with a Resume button, which is busy while `resume.pending` is true (`SandboxPanel` in `src/shell/workspace/SandboxNotice.tsx:152`).
  - Since 25 November 2026, a skill tab acts as a file tab does during the start that its open asks for (`docs/protocol/skill-tabs.md:200-202`). No protocol doc gives a wait for the time before the reply of a tab-open Resume.
  - The catalogue screen of a stopped skill tab draws the start after it began. The header shows Starting, and the tab waits with no Resume (`docs/mockups/src/entries/app/skill-mentions/tab/stopped/index.mockup.tsx`).
  - Each option except A changes `docs/protocol/stop-and-resume.md`. A change of a protocol doc also needs a read of both legal pages and of each public guide, as `AGENTS.md` says.
- **Problem:**
  - From a tab-open Resume until its reply or the start event, the header shows Stopped. A tab without content shows "Sandbox stopped" with a busy Resume button.
  - This holds for the skill tabs of the skill tabs change, and for the file, diff, and Preview tabs on `origin/main`. A held Resume reply showed it in the review.
  - The app tests check the state only after a reply that leaves the sandbox stopped (`src/shell/workspace/skills/SkillTabNotices.test.tsx:211-233`, `src/shell/workspace/files/TabOpenResume.test.tsx:45-72`). No test holds the reply.
- **Impact if no action:** Members see a prompt to start a cloud computer that already starts. A held start after a stop can make this window a few seconds long, as `plans/follow-ups/held-start-after-stop-gaps.md` records.
- **Root question:** How does a member see that the open of a tab has started the cloud computer?
- **Options:**
  - **A.** Change nothing. The protocol already says that a skill tab acts as a file tab does. Cost: the prompt to start stays for the time of each reply. Effort: Small.
  - **B.** Carry the tab-open Resume as a flag of its own from `ResumeOnTabOpen` to `pagePlaceholder`.
    - The page of a file, diff, or skill tab then shows the wait until the reply. A pressed Resume keeps its busy button.
    - Cost: the header, the Preview tab, and the tools still show the stopped state then.
    - Effort: Small.
  - **C.** Treat `resume.pending` as `resumingAtOpen` in `contentState` and in the header.
    - Until the reply or the start event, each part that shows the state of the sandbox then shows the wait. The header shows Starting.
    - Test with a held reply: the wait, no Resume, the header Starting, and no file or skill read.
    - State the rule in `docs/protocol/stop-and-resume.md`.
    - Cost: after a press on Resume, a panel shows the wait in place of a busy Resume button, also on a phone.
    - Effort: Small.
  - **D.** Let `WorkspaceModel.resume` in `src/app/workspace-model.ts:222` show a local Starting state from the request until the reply or the start event.
    - Every reader of the workspace state then shows the start, also the bar of the chat.
    - Cost: it also changes the manual Resume in each place.
    - Effort: Medium.
  - **E.** Give the workspace lifecycle view one shared state for each automatic start: the open Resume and each tab-open Resume.
    - The header and each content part read it until the start reply, the start event, or a failure. A pressed Resume keeps its busy button.
    - Cost: a new state that replaces `resumingAtOpen`.
    - Effort: Medium.
- **Left out:**
  - A change of the Resume reply alone. The time before the reply still shows the stopped state.
  - A navigation that waits for the reply. It hides the page that the member chose during the wait.
  - A wait for the skill tab only. It breaks the rule that a skill tab acts as a file tab does (`docs/protocol/skill-tabs.md:200-202`).
- **Wider fix:** C, when `contentState` and the header read one shared flag, so that each part gets the pending start from one place. E also prevents the class, and it also covers a later kind of automatic start.
- **Previous examples:** Commit `8c49081e3` fixed the same stopped bar during the open Resume. `plans/follow-ups/held-start-after-stop-gaps.md` records the same stopped state after the reply of a held resume.
- **Related:**
  - `plans/follow-ups/held-start-after-stop-gaps.md` has the same symptom at a later time. Its option B makes the reply of a held resume show Starting. This item covers the time before any reply. No options conflict.
  - `plans/follow-ups/mockup-start-hides-tab-content.md` gives the app and the catalogue one rule for when a tab keeps its content. That rule takes the result of `contentState` as an input, so C or E here changes its input. No options conflict.
- **Recommendation:** C. One small change gives every tab and the header the wait that the open Resume already shows.
- **Action:** ask the user, because C changes how the tabs on `origin/main` show a start and a pressed Resume, beyond what the protocol states.
