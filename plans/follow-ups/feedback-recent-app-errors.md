# Feedback carries no recent errors of the app

- **Severity:** Low. **Effort:** Large. **Confidence:** High. **Harder later:** No.
- **Kind:** Needs decision.
- **Added:** 2026-11-10, from option D of decision 271 of the plan `plans/command-palette-feedback.md`, branch `calummoore/command-palette-feedback-option`.
- **Location:** The Feedback dialog in `src/shell/feedback/FeedbackDialog.tsx`, the request of `FeedbackModel` in `src/app/feedback-model.ts`, the request type in `src/shared/feedback.ts`, the check and the email in `worker/app-api/feedback-input.ts` and `worker/app-api/feedback-mail.ts`, `docs/protocol/feedback.md`, and the Privacy page in `src/marketing/privacy-uses.ts`.
- **Reason:** On 10 November 2026, the user chose to add the recent errors of the app in a later change, and their collection and their data and keep limits still need a design.

- **Source:** Design. **Category:** Docs or spec.
- **Terms:**
  - **Feedback dialog:** the dialog that the Send feedback row of the command palette opens. The Worker emails its message, screenshots, and context to the team inbox through Resend.
  - **Team inbox:** the mailbox of the operator that gets each feedback email. The Worker secret `FEEDBACK_EMAIL` holds its address.
  - **Recent errors of the app:** the errors that the app met shortly before a send, which the Feedback dialog of Conductor can add to a message.
- **Background:**
  - Today a feedback message carries the text and up to 7 MB of screenshots. Its context holds the org ID and the open workspace ID when the person can reach them, the app version, and whether the page runs in the Mac app. The Worker adds the user ID, the GitHub login and ID, and the `User-Agent` header. `docs/protocol/feedback.md` states it.
  - On 10 November 2026, the user chose the screenshots and that context for the first change. Reason: screenshots carry most bug reports about screens, and the context lets the team find the workspace.
  - On the same day, the user chose the recent errors of the app behind a checkbox, as in Conductor, for a later change. Its recorded effort is Large.
  - So the person chooses to add the errors with a checkbox. The app sends none without that choice.
  - The app must capture no private code and no credentials automatically. An automatic capture of the page was rejected: a capture inside the page shows the frames of a port preview and of the live desktop as blank, and the Mac app does not let the page capture the screen.
  - A message carries no page address and no name of an org or a workspace. Reason: the address of a file view holds the file path, and a name can hold private words. Error data can hold such addresses and names too.
  - The app keeps no copy of feedback. The Privacy page says that the team keeps each feedback email while it helps to improve Conductive, and deletes it when it stops helping or when the sender asks.
  - The Worker already reports its own uncaught errors, `5xx` replies, and error log lines to Cloudflare Issues, as the Issues bullet of `docs/deployment.md` says. Cloudflare keeps the details of each occurrence for 7 days.
- **Problem:** A feedback message cannot carry the recent errors of the app, so the team must ask the person what failed. Which errors the app collects, how long it keeps them, and which fields a message can carry have no design yet.
- **Impact if no action:** The team gets less detail with a report of a failure. The person describes the error in words or in a screenshot.
- **Root question:** How does a feedback message carry the recent errors of the app, by the choice of the person, with no private code and no credentials?
- **Options:**
  - **A.** Change nothing. The person describes the error, and the team reads the errors of the Worker in Cloudflare Issues. Effort: Small.
  - **B.** The recent errors of the app behind a checkbox in the Feedback dialog, as in Conductor. A brainstorm at the start of the work designs which errors the app collects, how long the tab keeps them, which fields a message carries, and the changes of the protocol doc and the Privacy page. Effort: Large.
- **Left out:** An automatic capture of the page or of the screen, because it can hold private code and it fails in frames and in the Mac app. Errors sent without a choice of the person, because the user chose a checkbox. Fewer than three approaches remain, because the user already chose the approach of B, and only its details stay open.
- **Wider fix:** None. A new feature has no class of defect to prevent.
- **Previous examples:** None found.
- **Recommendation:** B. The user chose it on 10 November 2026 for a later change, and a brainstorm then designs its open limits.
- **Action:** ask the user, because the design of B adds data to each message and changes the Privacy page, and no requirement covers that data yet.
