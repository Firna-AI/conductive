# Older runners run new Codex models below the choice

- **Severity:** Medium. **Likelihood:** Common. **Effort:** Small. **Confidence:** High. **Harder later:** Yes.
- **Kind:** Needs decision.
- **Added:** 2026-11-18, from the review of the branch `calummoore/kyoto-votd`, finding 1, and its check.
- **Location:** `wrangler.jsonc:38`, `runner/sdk-helper/package.json:16`, `docs/protocol/agents-and-sessions.md:85`, `docs/protocol/sandbox-software.md:110`.
- **Reason:** Each option changes a requirement or adds a gate, so the user decides.

- **Source:** Review. **Category:** Product bug.
- **Terms:**
  - **Runner:** the program of Conductive in each cloud computer. It runs the turns, with the Codex program that its SDK helper pins.
  - **Fallback settings:** the generic settings that Codex uses for a model that its built-in catalogue does not have.
  - **Hello:** the first message of a runner to its workspace. It names what the runner can do, such as its login kinds.
- **Background:**
  - The Worker publishes one model list, `CONDUCTIVE_MODELS` in `wrangler.jsonc`, for every cloud computer.
  - The branch `calummoore/kyoto-votd` added GPT-6.2 Sol and GPT-6.2 Astra, with Low to Ultra and Fast. It also moved the pinned Codex from 0.167.0 to 0.170.0, because 0.167.0 has no catalogue entry for these models.
  - A cloud computer keeps its installed software until an update applies. A running computer checks every 10 minutes and installs after 2 idle minutes. A stopped computer runs its old software for its first turns after a resume, until it is idle for 2 minutes. `docs/protocol/sandbox-software.md` states these rules.
  - On 2026-11-18, local probes ran the real Codex 0.167.0 with an API key against a fake gateway. For GPT-6.2 Sol it used fallback settings. It sent Ultra as Medium and Fast with no `service_tier`. The runner still reported fast speed, so the chat showed no "Standard speed" note. High and Max stayed as chosen.
  - A ChatGPT sign-in reads the model list from ChatGPT online. The probes showed the chosen effort and Fast for it on both Codex versions.
- **Problem:** On a computer that still runs Codex 0.167.0, an API key or own endpoint login runs the new models with fallback settings. Ultra runs as Medium and Fast runs at standard speed, with no sign in the chat.
- **Impact if no action:** A member who chooses Ultra or Fast on a new model gets less, without knowing it. It happens after each deploy for running computers for minutes, and for each stopped computer at its first turns after a resume. Each later model addition repeats it.
- **Root question:** How does a member get the effort and speed that they chose, or learn why not, while the cloud computer still runs older software?
- **Options:**
  - **A.** Accept the short gap. Add a requirement that a model newer than the computer's software can run below its chosen effort and speed until the update. Effort: Small.
  - **B.** Before dispatch, check that the runner's software keeps the chosen effort. Fail the turn with update steps when it cannot. This needs a new optional hello field. Effort: Medium.
  - **C.** Runners report the model and effort choices that they support. One compatibility rule drives the model list and dispatch. Runner message, Worker, and app changes. Effort: Large.
  - **D.** Offer the new models without Ultra and Fast for now. Add them back later with H or I. Nobody gets Ultra or Fast on the new models until then. Effort: Small.
  - **E.** The model gateway refuses a model request from a Codex version below the model's lowest version. It reads a version header that Codex owns and does not promise. Effort: Medium.
  - **F.** Run the turn. The Worker sends Fast as off and Ultra as Max to older software. The end of the turn shows a note, as fast mode does for older software. Needs a hello field, a mockup, and a protocol change. Effort: Large.
  - **G.** Hold the turn until the runner installs the update, with a waiting state in the chat. Waits of 2 to 12 minutes or more. Effort: Large.
  - **H.** The runner reports its agent program versions in an optional hello field. Each model list entry can name the lowest version that runs it. Below that version, the Worker fails a turn of that model before dispatch, with "Restart the software, then try again." Effort: Medium.
  - **I.** H, plus a check in the new runner before each turn against the `model/list` of Codex. It also catches a gap that nobody recorded in the model list. Effort: Large.
- **Left out:**
  - Change nothing and keep the requirement: it breaks "Each message runs at one effort of its model" in `docs/protocol/agents-and-sessions.md`.
  - Rely on the package pin alone: computers that hold 0.167.0 keep it until their update.
  - Force a restart at deploy: it stops each running turn and each process that an agent started.
  - Deploy Codex 0.170.0 first and the models later: a stopped computer can resume weeks later with the old runner.
  - Rewrite the effort in the gateway: Ultra's task delegation is a mode of the Codex program, not a field of the request.
- **Wider fix:** H, then I. H gives each later model one list field. I checks the catalogue that Codex really uses.
- **Previous examples:** Fast mode for older runners: the Worker sends Fast as off and shows "Standard speed · Older cloud computer software", as `docs/protocol/fast-mode.md` says.
- **Recommendation:** A. The gap lasts minutes for a running computer and one turn or so for a resumed one, and only for API key and own endpoint logins. H best protects later model additions, and it can follow in its own branch.
- **Action:** ask the user, because each option changes a requirement or adds a turn rejection, and no recorded decision covers it.
