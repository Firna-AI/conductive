# Popover answer top lost after a late change

- **Severity:** Medium. **Likelihood:** Rare. **Effort:** Medium. **Confidence:** Medium. **Harder later:** No.
- **Kind:** Fix after merge.
- **Added:** 2026-11-24, from the branch `calummoore/auto-scroll-final-message-knfd`, finding 2 of review round 1. Extended the same day with finding 6 of review round 2 (late history), and with a phone case that the check of finding 5 of round 2 found.
- **Location:** `src/chat/components/reading-place.ts`, `answerTop` and its effect in `useReadingPlace`. `src/chat/explain/MarkParts.tsx`, where the open mark registers its box. `src/chat/explain/popover-place.ts`, `placePanel` and `usePanelPlace`. `src/chat/explain/PopoverChat.tsx`, where it gives `answer`. `src/chat/explain/useExplain.ts`, which loads the history of an explanation when its popover opens. `src/ui/components/explain/ExplainPopover.module.css`, the heights of the phone sheet. `src/test-support/fake-workspace-routes.ts`, the fake history.
- **Reason:** Each case needs an unusual browser, a late history load, or a resize before the member scrolls, and one keeper change fixes all of them.

- **Source:** Review. **Category:** Product bug.
- **Terms:**
  - **Explain popover:** the small chat panel by a marked quote, which shows the chat of an explanation session.
  - **Fallback positioning:** on a desktop browser without CSS anchor positioning, `placePanel` measures the room by the mark and sets the place and the height of the panel.
  - **Reading-place keeper:** `ReadingPlace` in `src/chat/components/reading-place.ts`, which keeps the row that the reader reads in place for each change of size. The chat scrolls in a box that keeps its bottom in place.
- **Background:**
  - When a turn ends, or the popover opens on an ended turn, the popover chat shows the top of the answer, while the chat is at the bottom (`docs/protocol/explain.md`, asked by the user on 24 November 2026). The keeper places the answer once for each new answer ID.
  - A reopened popover can show a finished answer from history at once. With fallback positioning, the panel can get its final height only after the marked text registers its box, which is after the first placement.
- **Problem:** The keeper places the answer once, for each new answer ID, and then reads its own scroll as the place of the reader. So a later change before the member scrolls leaves the start of the answer out of view. These cases are known:
  - **Late size.** The keeper places the answer at the first height. If the answer fits then, the chat stays at the bottom and the keeper notes no row. When the panel then shrinks, the box keeps its bottom, and the start of the answer goes above the view. A long answer loses its first lines by the amount of the shrink. Any other change of size before the member scrolls, such as a window resize or a notice in the footer, has the same effect. A simulated layout confirmed that the answer start moved above the view after a resize.
  - **Late history.** A tab can get the end of a turn through the stream before it loads the earlier messages of the explanation, because the history of an explanation loads only when its popover opens, and the newest page of the Worker ends at the newest workspace event (`worker/chat/chat-transaction.ts`). So the popover can open with only the second message of a two-message answer. It shows the top of that message. When the history gives the first message, `newestAnswer` gives the right start, but the keeper does not move, because its first scroll left the bottom. A scratch test reproduced this on two paths: the end of the turn through the stream, and a newest history page that held only the second message. The first message stayed 122 px above the view.
  - **Phone sheet drag.** On a phone, the chat can show the start of a long answer under older rows, for example after a follow-up. A drag of the sheet to full height keeps the distance from the bottom, so older rows show above the answer and its end stays hidden, also when the whole answer now fits. The public guide tells phone members to drag the handle up. This was found by reading the code, not in a browser, and browser scroll anchoring can change the result.
- **Impact if no action:** In this case, the member reopens a finished explanation and sees the end of its answer, or a cut start.
- **Root question:** How can the popover show the start of the newest answer until the member scrolls, also when that start or the size of the chat changes late?
- **Options:**
  - **A.** Delay the first placement until fallback positioning signals that it has sized the panel. Effort: Small.
  - **B.** Repeat the first placement on each resize while the popover opens. Stop when the member scrolls or the opening ends. Effort: Medium.
  - **C.** Size the fallback panel before its chat mounts. Effort: Medium.
  - **D.** Keep the start of the answer as the place of the keeper until the member scrolls the popover chat or sends a message. After each change of size of the box or the transcript, show the start again when the answer does not fit, or the bottom when it fits. The keeper must tell a scroll of the member from its own scroll, for example through wheel, touch, and key events. `layOutChat` in `src/chat/components/reading-place-test-kit.tsx` needs a box height that changes, and the test needs a resize observer that calls back. One sentence in `docs/protocol/explain.md` states the rule. The keeper holds the start of the newest answer by its turn, and shows the current start again after each new start of that answer, after each change of size, and after a sheet drag, until the member scrolls or sends. The keeper can tell a scroll of the member from its own by the position that it set, so a missed input event never moves a reader. Each later placement uses `revealRowTop` of `src/chat/components/chat-place.ts`, so an answer whose top shows keeps the bottom. The popover tests also need a held history: the fake in `src/test-support/fake-workspace-routes.ts` ends the parent history before the stored events, so no popover test opens on a partial transcript today. Effort: Medium.
  - **F.** For late history only: `newestAnswer` gives null while the transcript lacks the `turn.started` event of the newest turn, so the keeper places only a whole answer. The fold needs a start flag for each known turn. Effort: Small.
  - **G.** For late history only: keep the loading state of the popover until the `turn.started` event of the newest turn arrives or the history load ends. No text shows until then. Effort: Small.
  - **E.** Let the popover chat flow from the top while no turn runs, so that the browser keeps the top of the view when the box shrinks. Every keeper function assumes the reversed box, so each needs a second flow. Effort: Large.
- **Left out:** A fixed delay, because it fails when the mark registers late. Keeping the read row through a change of size of the box alone, because an answer that fit at first leaves no row to keep. Scroll snapping on the answer row, because it pulls a reader who reads higher up.
- **Wider fix:** D. It does not need to know when fallback positioning sizes the panel. C, the first recommendation of the review, is a direct fix for that detail only.
- **Previous examples:** Commit `42c238a0c`, which fixed the follow-up field that this variable-height popover pushed out of view.
- **Related:** `plans/follow-ups/explain-answer-top-misses-split-answer.md` changes the same placement, which row it targets. One change can do both.
- **Recommendation:** D. F is the Small direct fix of late history alone, if it is wanted before D. It keeps the start of the answer through each change of size until the member scrolls, whatever the cause, and it lives in the keeper, which already observes both sizes.
- **Action:** fix after merge, apply D, because the defect needs an unusual browser, timing, or resize, which is rare.
