# An escaped `<` breaks a Markdown angle address

- **Severity:** Medium. **Likelihood:** Rare. **Effort:** Small. **Confidence:** High. **Harder later:** No.
- **Kind:** Fix after merge.
- **Added:** 2026-11-20, from branch `calummoore/follow-up-typed-markdown-addresses-lose-nxbt`, the docs report of the fix for the escapes of typed Markdown addresses.
- **Location:** `src/markdown/markdown-destination.ts:81`, the check `/[\n<]/` in `readInlineTarget`, and `:38`, `angleEnd`. The readers that call it through `lineTargets`: `src/chat/links/chat-tokens.ts:96`, `tokens`, for sent messages. `src/markdown/web-links.ts:95`, `webAddressParts`, for the message field in `src/chat/components/chip-field/field-nodes.ts:54` and `field-text.ts:25`, and for the mockups in `docs/mockups/src/components/chat/WebLinkText.tsx:89`, `answerNodes.ts:67`, and `workspaceLinks.ts:34`.
- **Reason:** Only an escaped `<` inside an address in angle brackets meets the bug, and members seldom write one.

- **Terms:**
  - **Angle address:** the address of a Markdown link in angle brackets, such as `[x](<https://example.com/a>)`.
  - **Shared destination reader:** `readInlineTarget` in `src/markdown/markdown-destination.ts`. Sent messages, the message field, and the mockups read each Markdown address with it.
  - **Bare fallback:** when no Markdown link starts at a `[`, the readers go on through the text, and a web address in it links as a bare address.
  - **Answer parser:** the shared `markdown-it` 15.0.3 parser of `src/markdown/parser.ts`. It reads agent messages and the file preview.
- **Background:**
  - `docs/protocol/chat-links.md` says that a sent message shows a Markdown link as typed, and that its address is a link as a bare address is.
  - The shared destination reader decodes backslash escapes, such as `\<` to `<`. A sent message shows the source of the address as typed, and its link opens the decoded address.
  - `angleEnd` scans an angle address. It skips the character after each backslash, and it ends at the first `>` that no backslash escapes, as CommonMark does.
  - After that scan, `readInlineTarget` tests the whole source with `/[\n<]/`. It refuses the target when the source holds any `<` or any line break.
  - That test skips no escapes, so it refuses an escaped `\<` too. CommonMark refuses only a `<` that no backslash escapes.
  - The test was already on `main` at `924df6da6`, before the fix of the escaped `>`.
  - The answer parser reads each address with `parseLinkDestination`. It skips the character after each backslash, so an escaped `<` stays in the address. It refuses a `<` that no backslash escapes.
  - A bare address ends at a space or an angle bracket, as `docs/protocol/chat-links.md` says.
- **Problem:**
  - A sent message with `[x](<https://example.com/a\<b>)` makes no Markdown link. The bare fallback then links `https://example.com/a\`, which ends at the `<`.
  - The URL parser turns that `\` into `/`, so the link opens `https://example.com/a/`.
  - In an agent message, the answer parser reads the full decoded address `https://example.com/a<b`. Its link opens `https://example.com/a%3Cb`.
  - `webAddressParts` gives the same bare fallback, so the message field and the mockups read the same wrong address.
  - A probe of 20 November 2026 confirmed the sent message and the `webAddressParts` results. A read of `parseLinkDestination` in `markdown-it` 15.0.3 confirmed the answer result.
- **Impact if no action:** The link of such an address in a sent message opens another page than the one that the member wrote. The same text in an agent message opens the right page.
- **Root question:** How does each reader of typed Markdown keep an escaped `<` inside an angle address, as CommonMark does, so that its link opens the decoded address?
- **Options:**
  - **A.** Keep the test after the scan, but make it skip an escaped `<`. It then refuses an unescaped `<` and any line break, also a line break right after a backslash. Cost: a second pass reads the escapes again, and it must stay in step with `angleEnd`. Add regression cases for a sent message and for `webAddressParts`. Effort: Small.
  - **B.** Move the refusal of an unescaped `<` and of any line break into the scan of `angleEnd`, which already skips the character after each backslash. The scan refuses a line break also right after a backslash. Remove the test of the whole source. One scan then holds every boundary rule of an angle address. Add the same regression cases, with a line break after a backslash. Effort: Small.
  - **C.** Read each Markdown address with `parseLinkDestination` of the answer parser. Keep the source offsets, the cache of `lineTargets`, the one-line rule, and the 2000-character limit around it. Sent messages, the field, and the mockups then end and decode an address as agent messages do. Cost: the parser also decodes HTML entities, such as `&amp;` to `&`, which the shared reader keeps today. So a sent link with an entity then leads elsewhere. This item does not cover that change, so it needs the user. Effort: Medium.
- **Left out:**
  - Change nothing: the link keeps opening another page, which fails the goal.
  - A rule in `docs/protocol/chat-links.md` that an angle address with a `<` is no Markdown link: the bare fallback still opens another page, and sent messages and agent messages then read the same Markdown differently.
  - Show the whole refused link as text, with no link: it breaks the rule of `docs/protocol/chat-links.md` that each `http` and `https` address in chat text is a link.
- **Wider fix:** B, for the class of tests that read an escaped source again as raw text. The escape-aware scan of `angleEnd` then is the one place that reads the end and the refused characters of an angle address.
- **Previous examples:** The escaped `>` in an angle address. `angleEnd` stopped at the first `>`, also at an escaped `\>`. So `[x](<https://example.com/a\>b>)` in a sent message linked `https://example.com/a\`, which opened `https://example.com/a/`. The branch that added this item fixed it: `angleEnd` now skips the character after each backslash. The same branch made a sent message show the source of each Markdown address as typed.
- **Recommendation:** B. It fixes the bug at Small effort, and one escape-aware scan then holds every boundary rule of an angle address. C best protects against other differences from the answer parser, but it costs more and changes entity decoding.
- **Action:** fix after merge, apply B, because only an unusual input meets the bug.
