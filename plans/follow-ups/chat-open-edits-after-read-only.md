# Open chat edits survive a read-only chat

- **Severity:** Medium. **Likelihood:** Rare. **Effort:** Small. **Confidence:** High. **Harder later:** No.
- **Kind:** Fix after merge.
- **Added:** 2026-11-08, from PR #52, branch `conductor/boat-native-remote-workspaces-milestone-15o`, review round 2, finding 8.
- **Location:** `src/chat/WorkspaceChat.tsx:57`, `ChatBody`, which passes the stored overlay at lines 99 and 121. `src/chat/components/SessionTabs.tsx:28`, `Tab`. `src/chat/state/controller.ts:200`, `write`. `src/chat/components/RenameField.tsx:15`, the `done` latch. The lines are those of commit `f8e1e56`.
- **Reason:** Only another request's refusal or another member's archive during an open edit meets the defect, so the fix rule defers this Medium and Rare bug.

- **Terms:**
  - **Overlay:** the chat state that says what lies open over the chat: a session rename, the close question, the session history, or nothing. `ChatController` keeps it in its store.
  - **Close question:** the dialog "Stop the turn and close the tab?" with Cancel and Stop and close, in `src/chat/components/ChatOverlays.tsx`. It opens when the user closes a tab whose turn runs.
  - **Kept controller:** a `ChatController` that the app shell keeps across the pages of a browser tab, in `src/shell/workspace/shown-workspaces.ts`. `WorkspaceChatView` draws it.
  - **Read-only chat:** a chat that shows its history and sends no write. An archived workspace has one, and so does a workspace whose org the page knows to be suspended.
- **Background:**
  - These rules apply. `docs/protocol/chat-and-events.md` says that an archived workspace shows its chat read-only. `docs/protocol/operator-actions.md` says that no member can change anything in a suspended org.
  - A design call of the org suspension, of 8 November 2026, applies too. Each org request uses the org client, so a refusal makes an old page read-only at once.
  - An open page learns of a suspension only from an `org_suspended` refusal of a request of the org client, through `noteOrgRefusals` in `src/app/suspension.ts`. The org list loads only at boot. The set of refused orgs only grows. Only an operator lifts a suspension, and an open page learns of the lift at its next load. No route takes a workspace out of the archive.
  - `ChatBody` in `src/chat/WorkspaceChat.tsx` draws both chat hosts, `WorkspaceChat` and `WorkspaceChatView`. It derives `readOnly` from the archive state and from the host. It then passes the stored overlay unchanged to `SessionTabs` and to `ChatOverlays`.
  - In a read-only chat, the `write` method of `ChatController` skips each write and keeps the overlay. `select`, `reopen`, and `requestClose` change the tabs in the browser only. The kept controller holds the overlay across pages.
  - `renameSession` and `confirmClose` in `src/chat/state/session-actions.ts` set the overlay to none before they send. So when the save of the edit itself gets the refusal, the edit ends, and the page shows the refusal. That flow does not meet this defect.
  - The org suspension change added the `write` guard. Before it, a rename or a close in this state ended the edit, sent its request, and showed the refusal of the server.
  - Why it is rare: another request must get the refusal in the seconds that an edit is open. That request is the activity report or the read mark of the workspace. The page stops the activity report once it shows the sandbox stopped or in error. The org suspension stops each workspace, and a pending stop tries again after 30 seconds.
  - Evidence: a read of the code at commit `f8e1e56`. No fix and no test exists for this defect yet.
- **Problem:** When the chat turns read-only while a rename or a close question is open, the edit stays. `Tab` in `SessionTabs.tsx` draws the rename field before it reads `readOnly`, and `ChatOverlays` draws the close question from the stored overlay. Enter or Stop and close then does nothing, because `write` skips the action and keeps the overlay.
- **Impact if no action:** The screen offers an action that it cannot perform, and it gives no result. After Enter, the `done` latch of `RenameField` also ignores Escape and blur. So the field stays until the user selects another tab or opens the session history. Cancel still ends the close question.
- **Root question:** How does each open chat edit end, with a visible result, when the chat turns read-only during a visit?
- **Options:**
  - **A.** Hide an open rename and an open close question in their own renderers while the chat is read-only. `Tab` checks `readOnly` before it draws the rename field, and `ChatOverlays` gets `readOnly` and skips the close question. Each renderer must keep its own check. Add a mounted case for the change to read-only. Effort: Small.
  - **B.** Derive one permitted overlay in `ChatBody` from its `readOnly` value. While the chat is read-only, a rename or a close question counts as none, and the session history stays.
    - Pass that one value to `SessionTabs` and to `ChatOverlays`. `ChatBody` is the only reader of the overlay in both chat hosts.
    - It also hides an edit that any entry opens while the chat is read-only.
    - The visible result is the bar in place of the composer, which says why. The tab keeps its old name.
    - The store keeps the edit, which matters only if write access comes back. No route gives it back today.
    - Add a mounted case for the change to read-only, beside the read-only case in `src/chat/components/ReadOnlyChat.dom.test.tsx`. That case already expects no write. Effort: Small.
  - **C.** End the open edits in the chat state when the chat turns read-only.
    - The controller follows the read-only value of the host, as it follows the app sources at `src/chat/state/controller.ts:110`. It also follows the archive state of its stream.
    - It sets a rename or a close question to none, and it keeps the session history. Each reader of the state then sees no edit, also if write access comes back later.
    - Cost: the read-only option changes from a getter to a followed value at both hosts, at `src/shell/workspace/shown-workspaces.ts:106` and `src/chat/useChatController.ts:51`.
    - It clears the edit only at the change, so `startRename` also needs a guard. Effort: Medium.
  - **D.** Keep the close that the user asked for. When the chat turns read-only, an open close question closes its tab in the browser, as `closeLocally` in `src/chat/state/archive-view.ts:91` does for a read-only close. A rename ends as in B. Cost: a tab closes that the user did not confirm, and no requirement asks for that close. A user who meant Cancel reopens the session from the session history. Effort: Small.
- **Left out:**
  - Keep the write controls enabled. It fails the goal, because a read-only chat must offer no write.
  - A message about the ended edit, in a dialog or in a chat notice. It adds words that change nothing for the user. The tab keeps its old name, and the bar in place of the composer says why. The copy rules remove such a sentence.
  - Send the rename or the close and show the refusal of the server, as before the `write` guard. It fails the goal, because the editable field stays in a read-only view until the user acts.
  - End the edit only in the action that skips the write. It fails the goal for the same reason.
  - A new key or a new mount of the chat view. It fails the goal, because the kept controller holds the overlay, so the same edit shows again.
  - A change of the `done` latch of `RenameField` alone. It is A at another line, and it leaves an editable field in a read-only view.
  - A close question whose Stop and close becomes a browser close. Its words promise a stop that the chat cannot send. D gives the same close without a question.
  - A server change. The server already refuses each write of a suspended org and of an archived workspace.
- **Wider fix:** B. One overlay value that respects access reaches every reader of the overlay in both chat hosts. C is also structural, but it clears the edit only at the change, and it needs a guard where an edit opens.
- **Previous examples:** No earlier case in the primary history or in `plans/follow-ups/`. The org suspension change already ends three other open editors when access ends. The variable forms of `src/shell/settings/EnvVarsSection.tsx` live in `EnvVarsEditor`, which renders only while changes are permitted. The section rename of `src/shell/list/SectionHeader.tsx` and the new-section field of `src/shell/list/OrgList.tsx` show only while the list is not read-only.
- **Recommendation:** B. One derived overlay in `ChatBody` ends both edits for a suspension and for an archive. It also hides an edit that opens while the chat is read-only. C costs more, and its extra reach matters only if a route later lifts a suspension or an archive.
- **Action:** fix after merge, apply B, because the likelihood is Rare and the severity Medium, and the fix costs the same after the merge.
