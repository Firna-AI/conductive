# Choose how chat answers nest their lists

- **Severity:** Medium. **Likelihood:** Common. **Effort:** Medium. **Confidence:** High. **Harder later:** No.
- **Kind:** Needs decision.
- **Added:** 2026-11-10, from branch `calummoore/markdown-formatting-issue`, after the user reported that a chat answer "looks off".
- **Location:** `src/chat/components/agent-text.ts:109`, `src/files/markdown/markdown-lists.ts`, and the section "Formatting" of `docs/protocol/chat-markdown.md`.
- **Reason:** the protocol doc does not say how content under a list item shows, so each option sets a new requirement for the user to review.

- **Source:** Design. **Category:** Product bug.
- **Terms:**
  - **File preview:** the view that shows a Markdown file of the repository. Its full parser lives in `src/files/markdown/`, and it runs in a worker.
  - **CommonMark:** the Markdown standard that GitHub and the file preview follow.
  - **Work fold:** the folded steps of an ended turn. Each agent message in it is one line that opens to its full text, drawn by `src/chat/components/MessageLine.tsx`.
  - **Depth limit:** the most levels of lists inside lists that a view draws.
- **Background:**
  - The chat parser `textBlocks` in `src/chat/components/agent-text.ts` keeps every list flat. A change of list kind starts a new list. A list of the same kind joins the outer list. A blank line ends a list.
  - The chat parses the whole text of a message at each update, on the main thread. The chat answer and the work-fold line draw from that one parse.
  - The protocol doc `docs/protocol/chat-markdown.md` keeps a small Markdown set for the chat. It records three choices: the full Markdown of the file preview was rejected for the chat, a Markdown library was rejected because it needs a safety review, and one parser with a setting for each view was rejected because it needs more compatibility work.
  - For tables, the chat and the file preview share one reader, `src/markdown/table-rows.ts`, so that their rules cannot differ. The protocol rejected table rules for the chat alone.
  - Sandbox code can shape agent text, as "Trust boundaries" in `docs/architecture/data-and-trust.md` says. So a recursive parse needs a depth limit. The file preview nests at most 16 levels and shows deeper content as text. Options C, D, and E use the same limit.
- **Problem:** An indented list shows after its item, at the same level, so only the order shows which options belong to which decision. A numbered list under a numbered item joins the outer list. For example, an outer `2.` after the indented items `1.` and `2.` shows as "4.".
- **Impact if no action:** Each answer with nested lists keeps a flat look. Agents nest lists in most reports with decisions.
- **Root question:** How should the chat show the content that belongs to each list item, so that an answer keeps the structure that the agent wrote?
- **Options:**
  - **A.** Change nothing more. Lists stay flat, with the numbers and the indent that branch `calummoore/markdown-formatting-issue` fixed. Effort: Small.
  - **B.** Keep lists flat, but start a new list where the indentation of the markers changes. Numbers then restart for each level, such as 1, 1, 2, 2, all at one level. Screen readers still get flat lists. Effort: Small.
  - **C.** Nest lists only, with rules of the chat alone. An indented list goes inside the item above it, also after a blank line. An indented paragraph or code block still shows outside the list. It needs a mockup and a protocol update. Effort: Medium.
  - **D.** Nest all indented content, with rules of the chat alone. An item holds each line indented under it: lists, paragraphs, code blocks, and tables. Blank lines between items keep one list. An open work-fold line moves the whole list that holds the first table under the line. It needs a mockup and a protocol update. Effort: Medium.
  - **E.** Share the list reader of the file preview, as the chat shares the table reader. Move `listMarker` and `parseList` from `src/files/markdown/markdown-lists.ts` to `src/markdown/`, generic over the block type. `textBlocks` then reads the lines of each item with the chat's own block rules, so the result is D. The chat also gets the other CommonMark list rules, for example a new marker character starts a new list. A setting keeps task boxes as text. The move changes file preview code, which its tests cover. It needs a mockup and a protocol update. Effort: Medium.
  - **F.** Parse agent messages with the full parser of the file preview, with a setting that keeps the chat's small set. It reverses the recorded choice against one parser with a setting for each view. That parser runs in a worker, but the chat parses each update on the main thread, so F also needs a speed check. Effort: Large.
- **Left out:**
  - A Markdown library: E gives the same lists with tested code, no new dependency, and no safety review.
  - Extra indent for a flat list that the agent indented: screen readers still get a flat list, so it fails the goal.
  - List blocks in the chat events from the agent runner: E changes no event and no saved history, so E is better on every point.
  - Instructions that ask agents not to nest lists: old messages and other agents still nest, so it fails the goal.
- **Wider fix:** F. One parser for the chat and the file preview removes this class of gap. E removes it for lists.
- **Previous examples:** Commit `712afd8f`, "feat(chat): render Markdown tables in agent replies": tables showed as text with their pipes until then.
- **Related:** Parent item `plans/follow-ups/chat-nested-lists.md` holds the work. `plans/follow-ups/chat-nested-lists-indent.md` waits for this answer, and it applies only to C and D.
- **Recommendation:** E. It gives the result of D for the same effort, with list rules that are already tested, as the user chose for tables. The first draft recommended D. F best protects the codebase, at a Large effort.
- **Action:** ask the user, because the protocol doc does not say how content under a list item shows, so each option sets a new requirement.
