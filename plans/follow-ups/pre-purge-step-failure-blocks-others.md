# One failed pre-purge step blocks the others

- **Severity:** High. **Likelihood:** Rare. **Effort:** Medium. **Confidence:** High. **Harder later:** No.
- **Kind:** Fix after merge.
- **Added:** 2026-11-10, from branch `calummoore/workspace-archive-error`, pull request #138. It is review item 5: the wider fix of review item 3, with two older problems outside that diff, which the independent check of item 3 found the same day.
- **Location:** `worker/members/cleanup.ts:64-68` (the pre-purge steps of each deleted org), `worker/members/cleanup.ts:144-146` (the outer `catch`), `worker/members/deletion.ts:96-117` (`stopDeletedOrg` and its rethrow), `worker/members/archive-cleanup.ts` (`cleanupOrgArchives`), `worker/members/cleanup-lease.ts:9-35` (`withCleanupLease`), `worker/members/lifecycle-runner.ts:18-25` (`runLifecycleHook`), and `worker/application.ts:212-231` (the scheduled run).
- **Reason:** This branch fixes the Archive delete case at once, and the two remaining cases are older, so their fix reaches `worker/members/deletion.ts` outside this branch.

- **Source:** Review. **Category:** Product bug.
- **Terms:**
  - **Delete org window:** the 7 days after Delete org, before the purge. An admin can restore the org in this time.
  - **Pre-purge step:** one part of the scheduled cleanup of a deleted org in that window: the stop of each computer, the delete of each expired archived computer, the retention restarts, and the pending Org Restore handoff.
  - **Retention restart:** a brief restart of a stopped computer, 13 days after its stop, so that the provider keeps its disk.
  - **Org Restore handoff:** the step that gives the workspaces of a restored org back to their normal lifecycle.
  - **Cleanup lease:** the 5-minute ownership record of one cleanup run for one org, which each step checks before it writes or calls the provider.
- **Background:**
  - The scheduled Worker entry at `worker/application.ts:212-231` calls `cleanupDeletedOrgs`, then the lifecycle repair, then the software image repair and the approval emails. The last two each catch their error and write a fixed warning.
  - For each deleted org before its deadline, the run takes the cleanup lease through `withCleanupLease` in `worker/members/cleanup-lease.ts:9-35`. Then it calls `stopDeletedOrg`, `cleanupOrgArchives`, `maintainDeletedOrg`, and `finishPendingRestore`, in that order, at `worker/members/cleanup.ts:64-68`.
  - `withCleanupLease` releases the lease in `finally`, and turns each error that is not an `HttpError` into a 502 `org_cleanup_failed` error. The outer `catch` at `worker/members/cleanup.ts:144-146` then adds the org to `pending`.
  - Nothing reads `pending` in production. The scheduled entry ignores the result, and the outer `catch` writes no warning.
  - Delete org disarms the alarms of each workspace object, and the lifecycle repair skips deleted orgs. So this run is the only owner of retention restarts in the Delete org window.
  - A retention restart comes 13 days after a stop, from `DISK_KEEPALIVE_MS` in `worker/lifecycle/durable-types.ts:15`. The provider can remove a disk after 14 days. The Cron Trigger runs every 15 minutes, at `wrangler.jsonc:7`, so about 96 runs in a row must fail before a disk is at risk.
  - Each step checks ownership before it writes or calls the provider. `runLifecycleHook` at `worker/members/lifecycle-runner.ts:18-25` renews the lease and claims a generation first. The retention writes use `lifecycleWritePredicate`, and the restore read and cancel use the lease token.
  - A provider call times out after 30 seconds, at `worker/sandbox/transport.ts:88`, and the lease lasts 5 minutes, from `CLEANUP_LEASE_MS` in `worker/members/lifecycle-data.ts:1`. So one call cannot outlive the lease, and a lost lease fails the next step before any write. No error classification is needed to go on after a failed step.
  - The requirements:
    - The "Delete org" section of `docs/protocol/orgs-and-members.md` says that the work of every member stays safe for 7 days.
    - The "Stop and resume" section of `docs/protocol/workspace-life.md` restarts a stopped sandbox near day 14, so that the provider keeps its disk.
    - `worker/members/README.md` says that the cleanup interval plus its retries must fit the margin before day 14, that retention runs before each pending Restore handoff attempt, and that scheduled cleanup retries a failed handoff.
- **Problem:**
  - A step that throws ends the run of its org, so each later step of that run is skipped. The class has three cases:
    1. **The Archive delete, from this branch.** `cleanupOrgArchives` let each Delete error escape, except `not_found`, and its provider lookup could throw `ProviderAccountError`. It ran before retention and the handoff. A one-off check with real D1 left a retention date one day overdue with no Resume. Removing only the Delete fault sent Resume and Stop and renewed the date. Pull request #138 fixes this case with option B, at once.
    2. **The failed stop, older than this branch.** `stopDeletedOrg` tries the stop of every computer, then rethrows the first failure, at `worker/members/deletion.ts:117`. That is before the run reaches retention. So one computer that never stops blocks the retention of every other disk of the org. The stop step came with commit `24952894`.
    3. **The silent failure, older than this branch.** The outer `catch` at `worker/members/cleanup.ts:144-146` records `pending` with no warning, and nothing reads it. So a cleanup that fails for days stays silent.
  - The same throw also skips the scheduled retry of a pending Org Restore handoff. `pendingRestoreRequest` in `worker/members/restore-data.ts` needs a deadline in the future, and `markPurgeStarted` in `worker/members/deletion-data.ts` ignores a pending request. So a handoff that nobody retries ends in the purge. An admin can still retry Restore, because `restoreOrg` does not call `cleanupOrgArchives`.
- **Impact if no action:**
  - One cause that does not clear is enough to block the other steps, such as an account that the configuration no longer lists, or a 403 or 409 that repeats for one computer.
  - Another stopped computer of the org can then pass the 14-day disk limit. Its files and agent sessions can disappear before Org Restore ends.
  - Nobody sees the failure, because no warning is written.
- **Root question:** How does deleted-org cleanup keep making independent safe progress when one pre-purge step cannot finish?
- **Options:**
  - **A.** Change the order: run disk maintenance before the Archive delete and the stops. It protects retention from the steps before it, but a maintenance failure can then delay the deletes, and each new step needs a choice of place. Effort: Small.
  - **B.** Isolate the named steps directly: catch the error of each named step under the cleanup lease, try the next steps while ownership holds, and report the org pending after any failure. Pull request #138 applies B to the Archive delete. It covers only the steps that it names. Effort: Small.
  - **D.** Give the scheduled pre-purge run one default step runner in `worker/members/cleanup.ts`.
    - After the suspension step, run each independent step through one helper: the stop of each computer, the expired deletes, retention, and the pending Org Restore handoff.
    - The helper writes a fixed warning for each failed step and continues while the lease holds. At the end, it rethrows the first failure, so the org stays pending.
    - Each step keeps its own lease checks, and its provider lookup stays inside the isolated part, as `stopDeletedOrg` already does at `worker/members/deletion.ts:97-103`. A new step then gets isolation by default.
    - The Delete org and Restore org routes keep their behaviour.
    - It changes `worker/members/deletion.ts` outside this branch, and needs a regression case for a failed stop.
    - Effort: Medium.
  - **C.** Give the deletes, the stops, and disk maintenance separate durable tasks with their own retry schedules. It removes the shared run, but adds ownership, scheduling, and fencing work for each task. Effort: Large.
  - **E.** Make the existing Archive owner in the workspace object the only deleter of an expired archived computer, also in the Delete org window.
    - Delete org then leaves the Archive alarm armed, fenced by the org lifecycle generation, and the org run does no Archive delete.
    - It changes the `suspendOrg` contract in `worker/members/README.md`, and needs fencing between the workspace object, the cleanup lease, and the purge at day 7. Those need their own contract decisions.
    - It touches `worker/lifecycle/archive-state.ts` and overlaps the ownership design of `plans/follow-ups/unresolved-computer-request-ownership.md`.
    - Effort: Large.
- **Left out:**
  - Change nothing. It fails the rule that the work of every member stays safe for 7 days.
  - A retry inside the same run. The failing step still blocks the later steps.
  - A delay of the expired deletes to the purge at day 7. It breaks the delete 14 days after an Archive, which `docs/protocol/workspace-life.md` and the Privacy page state.
- **Wider fix:** D. It makes isolation the default for each pre-purge step, and covers the older failed-stop case too. B names the steps that failed, so it is a direct fix.
- **Previous examples:** commit `24952894`, "feat(members): add org membership and recoverable deletion", of 2026-11-06, added the stop step that rethrows the first failure before retention. Review item 3 of this branch is the Archive delete case. `cleanupDraftAttachments` at `worker/members/cleanup.ts:40-44` already warns and continues.

  - `plans/follow-ups/unresolved-computer-request-ownership.md`: option E here overlaps its ownership design, so E should follow that design. D does not wait for it.
  - `plans/follow-ups/org-deletion-lost-build-allocation.md`: the same Delete org code. Its option B changes the stop step and the deletion list that D wraps. Neither item waits for the other.
- **Recommendation:** D. It keeps one run under one lease, and gives each present and future step independent progress. Its duties:
  - Rethrow the first failure at the end, so the org stays pending.
  - Write one fixed warning for each failed step, with no request data, as `cleanupDraftAttachments` does.
  - Keep each step's lease checks, and the provider lookup inside the isolated part.
  - Keep the Delete org and Restore org routes as they are.
  - Add regression cases: a failed stop next to a due retention restart, and a failed delete next to a due restart and a pending handoff.
- **Action:** fix after merge, apply D, because it reaches `worker/members/deletion.ts` and the scheduled cleanup outside this branch. The Archive delete case is fixed now with B and is not deferred. E needs its own contract decisions and stays unapplied.
