# Folder record copy can miss saved variables

- **Severity:** Medium. **Likelihood:** Rare. **Effort:** Large. **Confidence:** High. **Harder later:** No.
- **Kind:** Fix after merge.
- **Added:** 2026-11-27, from the branch `calummoore/add-repo-not-added-faoc`, review finding 10. Two problems outside that review's scope with the same cause joined it.
- **Location:** the settle step `settle` in `worker/lifecycle/repository-change-publication.ts:91` and `:103-131`, the settle command `repositoryChangeSettleCommand` in `worker/lifecycle/repository-change-commands.ts:128-159`, the D1 save `recordClonedRepositoryLocation` in `worker/lifecycle/repository-location-data.ts:88-131`, which `completeCommand` calls at `worker/lifecycle/repository-change-command.ts:103-117`, the end rule `endAfterMove` in `worker/lifecycle/repository-change-end.ts:38-80`, the record writer `writeRepositoryFolderRecord` in `worker/lifecycle/repository-folder-file.ts`, the start writer in `worker/lifecycle/image-software.ts:113`, the software restart in `worker/lifecycle/software-restart.ts`, the runner launcher `image/runner-start.sh:14-15`, the terminal attach program at `worker/terminal/scripts.ts:147-150`, the terminal launcher at `:169-185`, the shell server script at `:190-197`, the folder of a new shell `terminalFolder` in `worker/terminal/bridge/folder.ts:16-31`, the service reader `NativeSettings` in `crates/cnd-services/src/settings.rs`, and the requirements in `docs/protocol/repository-folders.md` ("Folder variables" and "Folders over time") and `docs/protocol/services.md` ("The environment").
- **Reason:** A start of the cloud computer restores the copy, and the repair also reaches the software restart path and terminal code outside the clone branch.

- **Source:** Review.
- **Category:** Product bug.
- **Terms:**
  - **Folder record:** the saved list of repository folders and their variables, such as `CONDUCTIVE_REPOSITORY_LEDGER_DIR`. The Worker stores it in D1, in `workspace_runtime.repository_locations_json`.
  - **Start settings:** the file `/run/ascii-secrets/env.sh` with the org env vars and the app's own variables, such as `CONDUCTIVE_REPOSITORY_DIR`. Each start writes it, and it stays the same until the next start.
  - **Record copy:** the file `/run/conductive/repository-folders` on the cloud computer. Each start writes it from D1. The settle step of each repository change writes it again.
  - **Settle step:** the steps after a repository change is published. Each step only warns when it fails.
  - **Terminal bridge:** the program that opens each terminal tab in tmux. It takes the folder of a new shell from `/run/conductive/repository`, or else from the start settings.
- **Background:**
  - Since 27 November 2026, a repository change can clone a repository that the computer does not hold (repository clone decision 1 C). The Worker saves the new folder to D1 as soon as the clone succeeds.
  - The runner launcher, the terminal shell server, and services read the record copy after the start settings. The terminal attach program also reads it at each connection, and sets each variable in the global tmux environment.
  - Between two starts, the Worker writes the record copy only in the settle step, after publication.
  - The settle step runs its command only after a good D1 read of the folder record. A failed read skips the whole command and only warns.
  - The end rule after a move ends a job whose publication keeps failing for 10 minutes. It does so only while the workspace row in D1 still names the old repository. The job then ends without the settle step.
  - After a good publication, a failed copy write only logs a warning.
  - A software Restart runs the update check. Then it restarts the runner, the preview relay, and the terminal web service, but not the shell server. It writes no record copy, so the runner launcher reads the same stale copy.
  - Systemd also restarts a failed runner or shell server with no Worker step before it. The units `image/release/conductive-runner.service` and `image/release/conductive-terminal-sessions.service` set `Restart=on-failure`.
  - The same warn-only settle step writes the terminal folder file `/run/conductive/repository` and the tmux `CONDUCTIVE_REPOSITORY_DIR`. A failed settle step leaves new terminals in the old folder until the next start. This part is also true on `origin/main`.
  - The shell server script sets `CONDUCTIVE_REPOSITORY_DIR` from the start settings. After any repository change, a restart of the shell server gives new shells the old folder in this variable again.
  - `docs/protocol/repository-folders.md` says that after a change, `CONDUCTIVE_REPOSITORY_DIR` names the new folder. It requires: "Each process that starts after the change gets it: a new terminal, each command of a later agent turn, and the startup script at the next start."
  - The same doc requires: "A runner restart, a new terminal, and a new service get the folder variables from the workspace's record." `docs/protocol/services.md` gives each service the folder variables "from the workspace's current record".
- **Joined from the second item check (27 November 2026):** `settle` now reads the folder record from D1 before it runs the settle command. If that read fails, the whole settle command is skipped: the second context copy, the terminal folder file, and the tmux `CONDUCTIVE_REPOSITORY_DIR` too. On `origin/main`, these steps never depended on a D1 read. A direct fix runs the settle command without the record write when the read fails. F also covers it.
- **Problem:** A new terminal, a new service, or a restarted runner can miss the variable of a folder that D1 already holds, or start in the old folder, when publication or the settle step fails. Between two starts, `settle` at `worker/lifecycle/repository-change-publication.ts:103-131` is the only writer of the record copy, the terminal folder file, and the tmux variable.
- **Impact if no action:** Commands can lose the variable of a folder that exists, until the next start of the cloud computer.
- **Root question:** How do processes that start later on a running cloud computer get every folder variable of the saved record, and the current folder, whichever delivery step fails?
- **Options:**
  - **C.** Write the whole record copy in the clone command, right after the folder takes its name. The Worker passes the recorded locations. A failed write does not change the exit status, and the settle step still writes the copy. Extend `worker/lifecycle/repository-change-clone-native.test.ts`. Closes the clone gap with no retry state, but not a failed settle step or the current folder. Risk: the clone command runs before the D1 save. A save that keeps failing then leaves a copy that names a folder that D1 does not hold. Effort: Small.
  - **B.** Keep a retryable update of the record copy after the D1 save, apart from publication. Each retry reads D1 again and writes the whole file, so a late retry cannot replace a newer record. The retry state outlives the job. Use the same update before a software Restart. Add a case where the first write fails. It leaves the current folder of new terminals stale after a failed settle step or a shell server restart. Effort: Medium.
  - **F.** Do B for one cloud computer state that also holds the current folder. The runner launcher, the shell server, and the terminal bridge read `CONDUCTIVE_REPOSITORY_DIR` and the folder of a new shell from it. This also fixes the shell server restart and the warn-only settle step. Changes terminal code. Effort: Large.
  - **D.** Let the runner keep the copy: the Worker sends the full record over the runner socket at each connection and after each change, and the runner writes the file. Needs a new runner message and flag. Effort: Large.
- **Left out:** A retry only after a good publication fails when publication ends early. A read from the Worker by each process gives no folder variables to a terminal or service that starts while the Worker is out of reach. A weaker requirement, such as "at the next start", breaks `docs/protocol/repository-folders.md` and `docs/protocol/services.md`, and needs the user. Variables that each reader takes from a Git setting in the folder do not come from the saved record, and an agent can change them.
- **Wider fix:** F. One checked sync covers every copy of folder state.
- **Previous examples:** Commit `e4c53dbe9` made tmux open a new shell at the repository path, not at the current folder of the launcher. A restore can leave that folder in an old view of the disk. `plans/follow-ups/new-shell-keeps-old-branch-variables.md` records the same class for the branch variables.

- **Action:** fix after merge, apply F, because a start restores the copy and the repair reaches the software restart and terminal paths outside the clone branch.
