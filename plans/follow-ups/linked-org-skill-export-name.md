# Linked skill text can differ from agent text

- **Severity:** Medium. **Likelihood:** Rare. **Effort:** Medium. **Confidence:** High. **Harder later:** No.
- **Kind:** Fix after merge.
- **Added:** 2026-11-25, from branch `calummoore/skill-widget-tab-page-dtzl` (skill tabs), review round 1, finding 4.
- **Location:** `runner/sdk-helper/src/providers/skill-view.ts:37-83` (`exportSkills`), `runner/sdk-helper/src/providers/skill-view.ts:22-35` (`replaceMetadata`), `runner/sdk-helper/src/skill-org.ts:27-46` (`orgSkillView`), `runner/sdk-helper/src/skill-org.ts:80-110` (`readOrgSkill`), `runner/sdk-helper/src/providers/skill-metadata.ts:16-51` (`skillMetadata`).
- **Reason:** The case is rare, because it needs a link inside the copy and a `SKILL.md` without a name.

- **Source:** Review. **Category:** Product bug.
- **Terms:**
  - **Org skills copy:** the copy of the org's skills repository on the cloud computer. The runner removes each link that leaves the copy, so a link inside it stays.
  - **Safe form:** the text of an org skill that an agent gets. `safeSkillContent` in `runner/sdk-helper/src/providers/skill-metadata.ts` keeps only the safe front matter fields, and it writes the `name`.
  - **Export:** `prepareSkillView` in `runner/sdk-helper/src/providers/skill-view.ts`. At each agent start, it copies the org skills copy into a temporary view and rewrites each `SKILL.md` into its safe form.
- **Background:**
  - Without a valid `name` in its front matter, a skill takes the name of its folder (`skillMetadata`, `skill-metadata.ts:16-51`). A Codex skill also needs a description.
  - The skill tab and the skills list render the original file through the link, with the folder of the link (`orgSkillView` in `runner/sdk-helper/src/skill-org.ts:27-46`). So they give the name of the link's folder.
  - The export copies the links as links, and maps each link to its target in the view (`skill-view.ts:43-67`).
  - It then walks the view, a folder before its subfolders. For each `SKILL.md`, it reads the file through the link and writes the safe form in place of the link (`skill-view.ts:22-35`, `:68-82`).
  - So when the export rewrites the target first, it writes the target's folder name into the target. It then reads that name through the link, and the agent gets it.
  - `docs/protocol/org-skills.md:147` keeps a link that stays inside the copy. `docs/protocol/skill-tabs.md:95-98` says that the tab shows the text that its agent reads.
- **Problem:**
  - A run on 25 November 2026 with the branch code reproduced it. The copy `skills-repo` held a root `SKILL.md` without a name, and `skills/a/SKILL.md` as a link to it.
  - For Claude and for Codex, the exported `SKILL.md` of the skill `a` held `name: skills-repo`. The skill tab of `a` showed `name: a`.
  - Between two sibling skill folders, the order of `readdir` in the walk decides which name the agent gets.
- **Impact if no action:** The skill tab can show another `name` than the file that the agent gets. Two skills of the agent can then also share one name.
- **Root question:** How does each org skill get one derivation of its safe text, for the list, the tab, and the agent?
- **Options:**
  - **A.** Read the file of the agent's export for the tab. Cost: a copy to prepare and to clean up at each read. Effort: Medium.
  - **B.** Render each exported `SKILL.md` from the original file of the copy, with the function that the tab uses. Keep the map of the links apart from the rendering of the metadata. Add a regression case with a linked file. Effort: Medium.
  - **C.** Prepare one safe view for each agent, trust choice, and published copy. Lease it to the tab and to each agent start. Cost: disk storage and invalidation. Effort: Large.
  - **D.** Give the org skills one resolver for the choice, the scan, the skill read, and the export.
    - The resolver renders each skill from the original file of the copy.
    - Test a `SKILL.md` that links to a `SKILL.md` in a parent folder, such as the root `SKILL.md` above. The walk always rewrites that target first.
    - Keep the current read of the whole file in the export until `plans/follow-ups/skill-export-reads-whole-files.md` is answered.
    - Effort: Medium.
  - **E.** Let the runner replace each `SKILL.md` link inside the copy with a copy of its target when it publishes the copy. Cost: a change of the copy rules in the Rust runner. Effort: Medium.
- **Left out:** A sort of the export. It changes only which file the export rewrites first, and a chain of links can still read metadata that the export already rewrote.
- **Wider fix:** D. One derivation for each org skill makes the result independent of the order of the export, for every caller.
- **Previous examples:** The test of support links in `runner/sdk-helper/src/providers/skill-safety.test.ts:172` covers links inside the copy whose source already declares a name.
- **Related:**
  - `plans/follow-ups/skill-export-reads-whole-files.md` changes the same export. Its answer sets the read limit that D uses. Do both in one branch when the answer comes. D does not wait for it.
  - `plans/follow-ups/skill-reads-follow-links-out-of-folders.md` can change the shared reader of the skill files. D must keep a valid link inside the copy readable.
- **Recommendation:** D. It keeps valid links, and it gives the list, the tab, and the agent the same safe text.
- **Action:** fix after merge, apply D, because the case is rare, and the fix leaves the skill read command unchanged.
