# Terminal tabs wait for a later start

- **Severity:** Low. **Likelihood:** Common. **Effort:** Medium. **Confidence:** High. **Harder later:** No.
- **Kind:** Needs decision.
- **Added:** 2026-11-16, from the branch `calummoore/terminal-tabs-implementation-l5ml`, review finding 201.
- **Location:** `worker/terminal/service.ts:35`, `worker/lifecycle/software-restart.ts:38`, `image/install-system.sh:16`, `docs/protocol/terminal.md` (Older software).
- **Reason:** Each option that brings terminal tabs sooner changes Restart or the update policy, which are user decisions in force.

- **Source:** Review.
- **Category:** Product bug.
- **Terms:**
  - **Terminal tabs:** up to 10 shells in one workspace, each with its own tab in the Terminal tool. `docs/protocol/terminal.md` gives the rules.
  - **Terminal service:** the ttyd program in the cloud computer that joins each browser socket to a shell. Its launcher comes from the active software release when the service starts.
  - **Support marker:** a value that the start of the cloud computer writes and the Worker caches. It says whether the running terminal service can open more than one shell.
  - **Install at idle:** the runner installs a downloaded release while the workspace has been idle for 2 minutes, without a stop.
- **Background:**
  - A terminal service can open several shells only when it runs with the URL argument option of ttyd and the new attach program. The start of the cloud computer checks the running service and writes the support marker. Only the start saves that value.
  - An install at idle restarts neither the terminal service nor the preview relay's shells, as `docs/protocol/sandbox-software.md` under "Installs at idle" says. Restart in the workspace header restarts only the runner and the preview relay.
  - So a workspace that runs while the software update arrives keeps one terminal until its cloud computer starts again. The docs say "at a later start".
  - A restart of the terminal service keeps every shell, because the tmux server runs in its own unit. It drops the open terminal sockets, which reconnect.
- **Problem:** An existing workspace gets terminal tabs only at a later start of its cloud computer, also when its software is already new. A user who presses Restart still has one terminal.
- **Impact if no action:** Users of long-running workspaces wait for a stop and a resume before they can open a second terminal.
- **Root question:** When should a running cloud computer that has the new software start to offer terminal tabs?
- **Options:**
  - **A.** Keep the rule: tabs come at a later start. Effort: Small.
  - **B.** Make Restart also restart the terminal service after the runner applies the newest download, then run the support check again, save it, and make the app read the terminal state again. Open terminals already disconnect during a Restart. It extends the user's decision on Restart, which names only the runner and the relay. Effort: Medium.
  - **C.** Let the Worker activate the new terminal service when no terminal socket is open: at a state read with a false marker, check for the attach program, block new sockets, restart the service, check, and save. It adds a privileged command, a socket block, and an event for other tabs. Effort: Large.
  - **D.** Carry the terminal ID inside the socket stream, so an older ttyd can open several shells with no restart. It adds a second ID channel beside the URL argument, which needs its own security review, and computers from before the terminal bridge still wait. Effort: Large.
- **Left out:** Applying the newest release before the terminal step of each start. It breaks the rule that a start never waits for a download.
- **Wider fix:** None. One activation rule covers every workspace.
- **Previous examples:** The preview relay restarts at each install since PR #406, because it kept an old release until the next start.
- **Recommendation:** B. It uses a control that the user already presses to apply new software, and it keeps every shell.
- **Action:** ask the user, because each option except A changes Restart or the update policy.
