# An HTML tab can open from a saved Ready state

- **Severity:** Medium. **Likelihood:** Rare. **Effort:** Small. **Confidence:** High. **Harder later:** No.
- **Kind:** Fix after merge.
- **Added:** 2026-11-18, from the review of branch `calummoore/preview-html-file-c42r`, finding 105.
- **Location:** `src/shell/workspace/previews/use-html-preview.tsx:116`, `:147`, `:155`, `src/previews/filesPreview.ts`, `src/shell/workspace/previews/kept-files-preview.ts`, `src/shell/workspace/WorkspaceScreen.tsx:85`.
- **Reason:** A Rare product bug of Medium severity waits for a later branch under the fix rule, and its fix must build on the answer of `plans/follow-ups/needs-input-hides-starting.md`.

- **Terms:**
  - **Files preview:** the preview on the preview domain that shows the page of an HTML file in its tab.
  - **Visit:** one mounted view of a workspace, from the press that opens it until the member leaves it.
  - **Connection count:** the counter of the files preview store that marks the opens of one visit, so that an answer of an ended visit changes nothing.
- **Background:**
  - A return to a workspace first draws its saved state, then the visit reads the current state (decision 87).
  - The HTML tab opens the files preview when the shown state is Ready. On a return, the first renders can use the saved Ready state, also when the cloud computer stopped while the member was away.
  - The Worker then refuses the open at once with 409 `sandbox_not_ready`.
  - When the refusal arrives after the state turned Ready again, its connection count still matches. The tab then shows a failure, and Try again or a new show is needed.
  - The return test `src/shell/workspace/previews/HtmlTabReturn.test.tsx:76` answers the refusal before Ready, so it misses the case.
- **Problem:** A return can send an early open that the Worker refuses, and a late refusal can leave the tab on a failure until Try again.
- **Impact if no action:** In a rare timing, the member sees "The preview couldn't open" after a return, and must press Try again.
- **Root question:** How should an open of the files preview, and its answer, count only in the running state that this visit confirmed?
- **Options:**
  - **A.** Wait for the visit's read of the state before the first open, and drop answers of an earlier state. Effort: Small.
  - **B.** Give the files preview connection a running period that the workspace screen confirms from `WorkspaceModel.opened`. A change of the period ends `opening`, and an `opened` or `open-failed` answer of an older period changes nothing. Add a regression with held replies. Effort: Small.
  - **C.** Move the automatic open into the workspace model, after a confirmed Ready. Effort: Medium.
  - **D.** Open at once, but keep a failed open hidden, with the tab in its wait, until the visit's read confirms the state. Effort: Small.
  - **E.** Treat `sandbox_not_ready` as a wait, not a failure, and change the failure rule of `docs/protocol/html-file-preview.md`. Effort: Small.
  - **F.** Put the confirmed running state into `WorkspaceContext` once, for the HTML tab and for the port preview parts on `main`: `kept-previews.ts:46`, `use-tab-preview.ts:69`, and `preview-centre.tsx:86`. This also stops a port Preview tab from opening from the saved state after a return. It changes parts on `main`, so it needs the user's approval. Effort: Medium.
  - **G.** The Worker publishes a running-period number with the workspace state. Effort: Large.
- **Left out:** No change, because it fails the goal. A held open in the Worker, because B is better on every point. A timed retry, because it breaks the rule of one open for each show. `resumingAtOpen` for each return, because it shows a false Starting.
- **Wider fix:** B for the HTML tab. F and G go wider at a higher cost.
- **Previous examples:** Commit `46769d979` made file pages wait for the cloud computer. Commit `8c49081e3` added visit state to prevent wrong first renders.
- **Related:** `plans/follow-ups/needs-input-hides-starting.md`: decide it first, because B must read the signal that it chooses.
- **Recommendation:** B. It removes the early open and the old answer at their one cause, with the counter that the store already has.
- **Action:** fix after merge, apply B, because a Rare product bug of Medium severity waits for a later branch under the fix rule.
